# add-doc

## 目标

在不改变现有业务逻辑的前提下，为代码添加清晰、准确且简洁的文档。

## 1. 文件范围

- 若未指定文件，则检查 Git 工作区中所有未提交的代码变更（包括已暂存和未暂存的变更）。
- 若指定了文件，则仅处理用户明确选定的文件，不得将范围扩大至其他文件。
- 保留用户现有的变更，不得覆盖、回退或丢弃任何未提交的内容。
- 不得修改与文档任务无关的代码或文件。

## 2. 工作流程

1. 确认待处理的文件范围。
2. 阅读相关代码，理解其实际功能与逻辑。
3. 遵循项目既有规范，添加或更新文档。
4. 检查文档是否准确、简洁、与代码实现保持一致，并确认注释位置正确，使文档工具能够将其关联到预期的声明。
5. 审查最终变更，确保不包含无关的修改。

## 3. 撰写指南

- 优先更新现有文档，避免创建重复文档。
- 重点关注功能、参数、返回值、异常及复杂逻辑。
- 遵循项目既有的语言、注释风格及文档格式。
- 将文档注释放在语言及文档工具要求的位置，确保其对应预期的类、方法或字段。更新现有注释时，应在选定范围内纠正位置不当的注释。
- 实现逻辑的注释应靠近其说明的代码，并遵循项目既有规范。
- 不得臆造代码行为或添加冗余注释。
- 不得更改业务逻辑、接口行为或无关文件。

## 4. 各语言的文档注释位置

### Java — Javadoc

- 类、方法、构造器或字段的 Javadoc 必须紧邻声明的整个注解块上方。
- 若声明没有注解，则将 Javadoc 直接放在声明上方。
- 不得将 Javadoc 插在多个注解之间，或放在注解与声明之间。

```java
/**
 * 返回用户的显示名称。
 */
@Override
@Nullable
public String getDisplayName() {
    return displayName;
}
```

## 5. 输出要求

完成后，简要说明：

- 修改了哪些文件。
- 添加或完善了哪些文档。
- 执行了哪些检查及其结果。

## 6. 核心原则

保持范围明确、文档准确、变更最小化，并维持现有代码行为不变。
