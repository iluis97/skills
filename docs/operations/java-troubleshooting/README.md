# java-troubleshooting

## 做什么

排查**运行中**的 Java 服务出现的异常——响应变慢、无响应、资源占用异常、内存持续增长、线程异常等。先还原实际表现，再从宿主机资源、运行环境限额（Docker 时）、JVM 到应用代码逐层归因，以可复核证据支撑结论；资源和性能结论带基线、波动范围与限制因素。优先使用 Arthas，不可用时回退 JDK 原生工具。当前提供[中文技能入口](../../../skills/zh-CN/operations/java-troubleshooting/SKILL.md)，以及面向人的[命令速查表](commands-cheatsheet.md)（不进入技能执行，供手动查用）。

## 什么时候使用

通过 `$java-troubleshooting` 显式调用，描述服务、部署形态和实际现象；异常时间窗优先确定。

```text
$java-troubleshooting
api-service 容器，最近半小时接口响应普遍变慢，CPU 看起来不高，帮忙排查。
```

```text
$java-troubleshooting
order-service 单实例错误率从 0.1% 升到 8%，进程正常运行，内存持续上涨。
```

需要同时看日志时，可在同一请求中指定两个技能：

```text
$java-troubleshooting $log-analysis
api-service 最近一小时间歇无响应，同时排查 JVM 状态和对应时段日志。
```

## 常见问题

- **服务反复重启、启动即退出能查吗？** 不能。这是启动/退出问题，Arthas 挂不上去，证据在容器退出码与启动日志里；Agent 会提示改用 `$log-analysis`。
- **会预设是 GC 还是锁问题吗？** 不会。按实际表现（影响范围、时间特征、CPU 高低、伴随现象）决定优先查哪层，结论由证据驱动。
- **没有 Arthas 能查吗？** 能，改用 JDK 原生工具（jcmd/jstack/jstat/jmap）等价观察，不会为排查主动安装 Arthas。
- **宿主机部署（非 Docker）能用吗？** 能。Docker 只增加“容器限额”这一层，其余归因思路相同。
- **会改 JVM 参数或重启服务吗？** 不会。排查只读，Arthas 用完会 `stop`，调优建议由你决定执行。
- **指标波动大怎么办？** 先补基线、观察时长、运行次数和波动范围；差异小于波动、单次采样或口径不一致时，不作为证据，也不据此宣布异常或优化效果。
- **和 log-analysis 什么关系？** 互补——本技能查运行时状态与资源，日志侧证据由 `$log-analysis` 提供，互不自动调用。

## 如何判断执行符合预期

- 范围包含服务、部署形态、异常时间窗；先把用户说的现象还原成可观测的表现，再决定下探哪层，不走固定全量流程。
- 启动/退出类问题被正确挡在本技能之外，并给出 `$log-analysis` 的出口。
- JVM 层优先 Arthas，命令按表现选择而非逐项跑完；Arthas 用完有 `stop` 记录。
- 结论区分事实与推断，指标、命令输出、代码位置可逐一复核。
- 资源和性能结论带基线、观察时长、运行次数和波动范围；差异小于波动或口径不一致时没有被写成结论。

## 专属维护要求

- 技能范围固定为**运行期异常**：不把某个具体表象（如“卡顿”）写成技能范围，表象只作为入口举例；不把启动/退出问题纳入本技能。
- 只保留分层归因框架与工具选择原则，不追加原因清单或阈值，避免约束 Agent 现场推理。
- Arthas/JDK 原生命令映射与 Docker 限额细节维护在包内 `references/diagnostics.md`，按需读取；调整归因层级、范围或工具选择时同步技能入口与本说明。
