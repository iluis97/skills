## 阶段 1：规则修订与真实行为验收

当前优先工作。职责保持 owner、planner、builder、verifier，推进条件由 progression.md 统一维护，其他资料说明执行方法并引用编号。

- [x] 将推进规则组织为稳定编号、明确输入、条件、动作和影响，保留未知情况及事件次序。
- [x] 明确规模的实际工作安排、方案接收、问题分流、证据覆盖及关键记录同步。
- [x] 将规则传递给实际角色，保留配置、授权、独立性及宿主能力边界。
- [x] 建立与规则编号关联的验收场景和证据要求。
- [x] 完成本轮文件及规则对照核对，记录发现与修订，具体范围及校验器不兼容见 acceptance.md。
- [ ] 按 acceptance.md 执行实际场景，保留成果、操作和记录变化证据。
- [ ] 在安装后的新会话复跑原中等规模需求及必要异常场景，验证完整宿主行为。

前四项仅表示文本已落地。文件核对也不证明实际行为；规则对照、实际场景执行和宿主真实调用分别记录，不能因为写了场景就勾选通过，未执行的项目保持未运行。

## 阶段 2：基于 Markdown 的小型规则引擎

由后续明确的实现任务开展，本轮不实现。以 progression.md 为权威来源，先确定输入契约、判断结果和动作接口，再映射稳定编号。

- [ ] 明确由负责人或角色提供的判断、可直接查询的事实，以及各自的依据来源。
- [ ] 映射开始、接受、分流、复核、等待、完成及恢复中止的适用条件，正确处理未知和局部有效结果。
- [ ] 关联规则判断、事实依据和实际动作，不能只写状态而不执行。
- [ ] 使用阶段 1 的代表性输入和场景核对引擎实现，不以规则条数或任务完成数作为成功指标。

引擎不预设复杂框架、数据库、多角色体系或自动质量裁决。若机器格式、持久化或适配接口确有需要，再在该实现范围内设计并验证，不由本路线图自动授权。

## 阶段 3：按缺口补充运行保障

规则引擎的条件判断与实际运行能力分别建设，优先复用宿主已有机制。

- [ ] 核对真实执行 ID、查询、取消、权限隔离和写入冲突能力，列明具体缺口。
- [ ] 必要时补充冲突保护、执行尝试关联和中断后的现场核对。
- [ ] 对明确纳入支持范围的外部操作处理幂等、查重和结果不明，避免盲目重放。
- [ ] 验证取消未生效、未知写入、旧结果迟到及恢复等实际场景。

只有新增能力确实有效，才更新对应状态。任务分工不等于锁，取消请求不等于终止确认，日志不等于恢复保障。

## 维护与交付

规则含义改变时同步规则引用、配套方法和场景；各层验证只报告已实际发生的内容。不新增文档校验脚本或测试类，必要引擎测试随未来代码实现另行建设。

仓库源码与安装副本独立。安装需按用户授权检查目标、备份并保留个性化配置；后续引擎或框架建设也需有明确任务范围，路线图不是全部候选能力的执行授权。
