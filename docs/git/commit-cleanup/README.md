# commit-cleanup

## 做什么

整理提交历史：把混在一起的变更拆开、碎片提交合并、顺序理顺、提交信息补全。只改提交组织方式，仓库内容在改写前后完全一致（用树哈希校验）。当前提供[中文技能入口](../../../skills/zh-CN/git/commit-cleanup/SKILL.md)。

## 什么时候使用

通过 `$commit-cleanup` 显式调用，通常在提交合并前、发起 PR 前，或发现自己提交得一团乱时。

```text
$commit-cleanup
最近 6 条提交混了两个需求和一次格式化，帮我理顺。
```

## 常见情况

| 情况 | 处理 |
| :--- | :--- |
| 一次提交包含多个需求或多个 bugfix | 拆分 |
| 格式化、重命名与逻辑修改混在一起 | 拆分：机械改动单独成提交 |
| 重构与功能改动混在一起 | 拆分：重构提交不改变行为 |
| 依赖升级与适配代码混在一起 | 拆分 |
| 生成的代码、锁文件与手写源码混在一起 | 拆分 |
| WIP、typo、反复修补等碎片提交 | 合并 |
| commit 与 revert 成对出现 | 一并删除 |
| 重复 cherry-pick 造成的重复提交 | 合并或删除 |
| 反复 merge 主干造成的噪音 | 拉直历史 |
| 依赖倒置、顺序无法独立理解 | 重排 |
| 提交基于错误基线分支 | rebase 到正确基线 |
| 提交信息空洞或语言不统一 | 改写信息 |
| 作者邮箱错误、共同作者丢失 | 改写信息 |
| 误提交 `.DS_Store`、IDE 配置 | 移除并补 `.gitignore` |
| 误提交大文件或密钥 | **停止改写**，按安全流程处理 |
| 换行符或大小写重命名导致异常 diff | 先统一属性再整理 |

完整命令见包内 `references/commands.md`。

## 常见问题

- **会改代码内容吗？** 不会。改写只重组提交，结束时会校验树哈希与改写前一致；顺带发现的问题单独提出。
- **同一个需求要合并成一条提交吗？** 不用。只有同一阶段内的碎片（WIP、typo、反复修补）才合并；需求的不同阶段各自能独立说明时保留多条。
- **已经 push 过的分支能整理吗？** 默认不动。需要你明确确认后才改写，并且 force-push 会再次单独确认。
- **提交里混了密钥怎么办？** 技能会停止并提示风险；清除密钥需要专用历史过滤工具，同时要作废并轮换密钥。
- **可以顺便评审代码吗？** 不评。这里只整理提交组织方式，代码质量属于评审。

## 如何判断执行符合预期

- 每条提交能独立说明做了什么，顺序符合依赖。
- 改写前后树哈希一致，`git diff` 与备份分支为空。
- `git range-diff` 新旧序列逐条对应，未配对的提交有说明；每条提交的文件归属与计划一致。
- 签名、tag、force-push 等副作用被如实报告。
- 未在改写过程中修改代码内容。

## 专属维护要求

- 技能只写判断标准与操作原则，不维护情况清单；新增情况优先在本文档补充，不扩充技能入口。
- 拆分、合并、重排的具体命令与恢复预案维护在包内 `references/commands.md`，按需读取；调整护栏或验证要求时同步技能入口与本说明。
- 涉及密钥、大文件时保持“停止并转人工”的边界，不因便利而扩大技能职权。
