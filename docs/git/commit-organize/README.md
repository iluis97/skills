# commit-organize

## 做什么

把工作区未提交的改动按变更单元分组，生成符合项目风格的提交信息并逐组提交，直接产出清晰的历史。只决定哪些改动进入哪条提交，不修改代码内容、不改写已有历史。当前提供[中文技能入口](../../../skills/zh-CN/git/commit-organize/SKILL.md)。

## 什么时候使用

通过 `$commit-organize` 显式调用，通常在改完一批代码、准备提交时。

```text
$commit-organize
这次改了结算和优惠券，还顺手格式化了两个文件，帮我分开提交。
```

调用后先输出分组计划，确认后才执行提交。

## 与 commit-cleanup 的区别

| 技能 | 输入 | 用途 |
| :--- | :--- | :--- |
| `commit-organize` | 工作区未提交改动 | 直接生成一组新提交 |
| `commit-cleanup` | 已有的提交历史 | 整理已经提交的历史 |

正常流程是先 organize；如果已经提交乱了，再用 cleanup。

## 常见问题

- **会直接提交吗？** 不会。先给分组计划和提交信息，确认后才执行。
- **一个文件里的改动属于两个需求怎么办？** 按 hunk 分离（`git add -p`）；无法干净分离时说明取舍，由你决定。
- **同一个需求要合成一条提交吗？** 不用。需求的不同阶段（如 schema、核心逻辑、装配、测试）各自能独立说明时，就分成多条提交。
- **提交信息会漏内容吗？** 要求覆盖全部实质改动（含配置、测试、文档），执行后会校验工作区无遗漏。
- **密钥或本地配置会被提交吗？** 不会。密钥、本地配置以及 IDE/Agent 客户端等工具目录检测到就排除并提示；项目明确跟踪的目录按项目约定处理。
- **会反复读取文件吗？** 不会。无依赖的只读检查合并执行；未跟踪文件登记后一次读取，不逐个文件往返。
- **会改写之前的提交吗？** 不会。改写历史属于 `commit-cleanup`。

## 如何判断执行符合预期

- 每条提交对应一个可独立说明的目的，顺序符合依赖。
- 提交信息简洁且覆盖完整改动，不逐文件罗列。
- 执行后工作区与暂存区清空，没有遗漏；每条提交可用 `git show` 复核。
- 未提交密钥、本地配置或工具目录（项目明确跟踪的除外）。

## 专属维护要求

- 技能只写分组原则与流程，不维护“情况清单”；新增情况优先在本文档补充，不扩充技能入口。
- 分组命令、撤回与失败处理维护在包内 `references/commands.md`，按需读取；调整流程或校验要求时同步技能入口与本说明。
- 保持“先计划、后执行”的约束，不因便利改为自动提交。
