# dev-workflow 首版方案

日期：2026-11-19

## 1. 主旨与范围

持续持有用户目标，按需组织工作，以实际成果和有效证据判断是否完成。

推导顺序：用户希望得到什么 → 怎样算真正达到 → 还缺哪些信息 → 采用什么方案 → 如何组织执行 → 如何判断结果。

角色、任务、产物与检查服务于目标，不能用已有检查表反推或缩小目标。难以量化的观感、自然度和易用性需要具体化、寻找参照并观察真实成果，不能被替换成能运行或无报错。

新技能名为 `dev-workflow`，以 CrewAI 的任务与协作设计为基础，按本次讨论取舍实现；不依赖 CrewAI 运行时，不以旧 `dev-flow` 作为迁移基线。当前仅提供中文包，不修改旧技能、历史提案或已安装副本。

**小而完整的推进规则方案待设计。**

首版是可显式调用的指令型技能，提供组织工作和核对成果的方法。尚未实现自动调度、状态转换校验、依赖就绪判定、程序门禁、证据版本失效及自动恢复引擎；不能据此宣称这些能力已经完备。后续先设计规则，再判断哪些机械操作值得脚本化。

## 2. 设计来源与取舍

### CrewAI 提供基础方法

| 参考点 | 首版采用方式 |
| --- | --- |
| 任务设计优先于 Agent 设计 | 任务说清目标、输入、边界和完成条件，再决定谁执行 |
| 不因步骤多增加 Agent | 搜索、阅读和分析可以属于一个任务；按可独立交付的目标拆分 |
| 角色与任务分开 | 角色承担稳定责任，任务描述本次具体工作，不为每个小步骤新建角色 |
| 按需委派 | 需要独立调查、不同能力或有效并行时委派，无固定助理角色 |
| 显式上下文依赖 | 只传相关目标、事实、约束和资料引用，不默认复制全部历史 |
| 明确预期输出 | 执行前约定结果和判断依据，普通委派使用自包含消息即可 |
| 结构化输出按需使用 | 需要程序解析时再使用结构化结果，不强制全部任务回传 JSON |
| 结果检查与反馈 | 交接时检查是否服务目标、成果是否充分，缺项反馈具体问题 |
| 人工反馈区别于正常对话 | 调研与澄清连续进行；确认针对需要用户决定的事项或实际成果 |
| 验证分层 | 文档核对不等于真实调用有效，后续宿主效果在新会话观察 |

不照搬其固定字数示例、长篇角色履历或框架 API；不把每个操作拆成 Crew 任务。

参考资料：[仓库](https://github.com/crewAIInc/skills)、[design-agent](https://github.com/crewAIInc/skills/blob/main/skills/design-agent/SKILL.md)、[design-task](https://github.com/crewAIInc/skills/blob/main/skills/design-task/SKILL.md)、[build-flow](https://github.com/crewAIInc/skills/blob/main/skills/build-flow/SKILL.md)。以上是设计来源，不是运行时必须读取或调用的外部技能。

### 本次讨论确定的选择

- 以用户目标为导向，不以流程合规代替成果达成。
- 四种主职责：负责人、规划者、实现者、核验者；职责不等于固定 Agent 数量。
- 无固定助理角色，各主角色按需委派，保留综合判断及最终交付责任。
- 主角色可分别配置模型和思考强度，局部委派默认继承直接委派者；优先宿主原生继承，未知时不猜，不把配置要求写成已生效事实。
- 调研与澄清交替进行，规划者从原始需求开始参与，不以需求完全明确为前提。
- 明确、实现、核验作为默认工作形态，不构建固定阶段引擎，不要求每轮重新走全套。

### 旧技能的参考范围

1. **任务记录与按需产物**：一个权威记录保存目标、当前方案、任务分工、待决问题、结果依据和执行状态；方案、交付说明、日志与截图按需生成，不强制四份文件，不重新建设大型通用工作流引擎。
2. **自动识别需求规模**：负责人初判，规划者调研后修正，按不确定性、影响面、依赖、取舍和验证成本组织投入，不单靠文件数判断。
3. **角色执行配置与简要播报**：用一个轻量配置文件区分默认值和角色覆盖；派发简述角色、任务、模型与思考强度，区分配置要求、实际提交和宿主确认，不迁移配置快照和登记命令。

不迁移旧角色注册表、阶段契约、审计系统、重试路由、知识沉淀流程、语言及 SQL 专项、历史状态兼容或旧状态脚本。角色执行偏好可编辑，不固化为流程门禁；此前试写的状态脚本及技术专项目录不纳入首版。

## 3. 四种职责

| 角色 | 责任 | 委派后仍需亲自完成 |
| --- | --- | --- |
| 负责人 `owner` | 用户目标、沟通、授权、组织与交付 | 判断需要问用户什么，协调取舍，整合交付结论 |
| 规划者 `planner` | 调研、影响分析、技术取舍、方案、实施安排与验收设计 | 综合事实、比较取舍、制定方案 |
| 实现者 `builder` | 代码、必要测试、相关文档、整合与自检 | 核心实现判断、变更整合与一致性检查 |
| 核验者 `verifier` | 独立审查、真实验证、目标达成判断 | 检查整体成果及证据充分性，给出结论 |

负责人由主线程承担。规划职责始终明确：常规和复杂任务优先独立规划，轻量任务可由主线程承担简短规划；不为角色齐全机械创建 Agent。代码或行为变化需要未参与实现的执行者独立核验；纯说明性修改可自检并明确说明。宿主能力不足时如实披露缺口，不宣称独立核验已经完成。

## 4. 自动识别需求规模

| 规模 | 依据 | 组织方式 |
| --- | --- | --- |
| 轻量 | 目标明确、影响局部、实现路径清楚 | 简短规划，减少交接与独立文档，通常不拆子任务 |
| 常规 | 需要一定调研，有关联变更或局部取舍 | 明确方案和验证方式，按需委派 |
| 复杂 | 目标不确定、跨模块依赖多、取舍或风险较大 | 深入调研，处理依赖，分批实现和验证 |

首次判断不要求额外调查流程，负责人依据已有上下文及适量阅读给出暂定结论；规划者按新事实调整。理由简短写入权威任务记录，不生成规模分析报告，不让用户选档。

规模变化只调整投入和组织方式，不降低目标或必要验证，不清空已有工作，也不自动扩张用户范围。

## 5. 默认工作形态

### 明确

原始需求交给规划者，必要时负责人先自行或委派查明局部事实。规划者自主选择已授权范围内的资料、代码和参照物，不需要逐文件审批。

能查明的事实先查证；业务目标、偏好、范围和验收取舍交由负责人联系用户。回答反馈规划者，继续补充调研与方案。连续复用上下文，不因普通澄清重建 Agent 或计算失败重试。

明确目标、约束、当前方案、必要实施顺序及判断成果的依据；篇幅与任务相称。需要用户决定时展示具体材料；已有明确决定和授权不重复询问，不新增全任务统一审批步骤。

### 实现

按方案实现完整行为，包含实际必要的测试和相关文档。可并行独立工作时委派，写清边界和文件所有权，复核整合结果。发现实质方案问题交规划者分析，涉及用户选择时由负责人沟通。

### 核验与交付

从用户目标、当前方案和真实成果判断差距，选择能证明目标的检查，区分通过、失败、阻塞、未运行。局部通过不能代替整体达成，关键缺失不能写成普通风险后放行。

按任务需要检查实际 diff、运行效果、测试和其他证据；纯文档不为流程形式新增测试。感知成果使用适合媒介的实际预览与运行观察，截图不能单独证明动效正确。

需要人工体验判断或用户指定验收时，展示当前成果并取得结论。未达到目标时继续改进，或明确协调目标变化；没有满足完成条件就如实保留未完成状态。

## 6. 按需委派

每次交代目标、输入、边界和完成条件，传递必要上下文。委派者复核成果、处理矛盾并承担责任，不能原样转包本角色全部职责。

写入任务明确所有权，避免共同写同一文件；权限不超过委派者。核验执行者不能参与被核验成果的实现。需要进一步拆分时交回委派者协调，避免无边界转派。

### 角色配置与继承

包内 `assets/roles.json` 只保存 `defaults` 与四种角色的 `model`、`reasoning_effort`，职责继续由 `references/roles.md` 定义。模型默认继承，思考强度默认 owner 继承、planner high、builder medium、verifier high；这些是可编辑的执行偏好，不是固定门禁。模型可按角色改为宿主支持的具体名称，档位以对应模型和宿主实际支持为准。

主角色派发按字段采用“用户对本次任务的明确指定 → 目标角色字段 → defaults 字段”，字段缺失继续查下一层；选中 `inherit` 就继承直接委派者对应的实际配置，两层都缺失时也按继承处理。局部委派默认继承直接委派者，不按工作内容重新套用 planner、builder 或 verifier 配置；明确安排新的主角色时才应用目标角色配置。用户对子任务的明确指定仍优先。

Owner 由主线程承担，配置保持继承；主线程兼任规划或实现也不代表配置切换，要求与会话不一致时说明差异。负责人代发不改变逻辑上的继承来源，不能静默用根线程配置代替直接委派者配置。

继承配置与继承对话不是同一件事。派发前核对宿主真实工具 schema，只给具体值传覆盖参数，不提交字面值 `inherit`。优先宿主原生继承；必须显式传值时要有可靠依据。需要隔离上下文才能覆盖配置时传自包含任务消息，不能同时满足配置与上下文要求时说明限制。业务角色与宿主执行类型分开，不让预设类型意外覆盖模型配置。

配置不可读、值无效或宿主不支持指定配置时，报告问题并暂停受影响的派发，其他独立工作可以继续。已有用户授权的替代配置可直接使用并说明变化，否则不静默换模型、降档、忽略覆盖或改为主线程执行。不建立模型兼容性数据库或自动重试链。

### 简要派发说明

Owner 派发前用一句话介绍角色、任务、模型与思考强度；启动后结合进度说明执行事实。例如：

> 交给规划者调研现有实现并形成方案；模型：继承当前负责人，思考强度：high（计划使用）。
>
> 规划者已启动；模型：继承（具体型号未回报），思考强度：high（已提交）。

仅有配置时称配置要求；真实调用已传入覆盖参数时称已提交；只有宿主明确回报当前执行对应字段及来源时称已确认。模型与思考强度分别判断，句柄和模型自述不证明配置生效。省略覆盖参数而无回报时保留继承且具体值未知。

子角色自行委派也简述配置，Owner 不重复播报。配置变化时补一句原因，正常进度不反复介绍身份，最终交付不默认附模型表。必要配置依据保存在现有权威任务记录中，不新建请求 JSON、快照或执行日志文件。

并发、超时和重试依据任务、风险及宿主限制设置必要停止条件，首版不统一固化人数或次数。工具能力不足或执行失败时说明事实，不伪造句柄、成果和配置生效。

## 7. 任务记录与产物

默认权威记录为 `{项目根}/artifacts/dev-workflow/{任务名}/task.md`。当前任务只有一个权威记录；已有合适位置时可以沿用并明确指向，不再建立第二份状态。

记录目标、规模与理由、当前方案、分工、待决问题、结果依据和当前状态；派发时在分工中补充真实执行者、模型与思考强度的配置要求、实际提交或宿主确认依据及重要变化原因。轻量任务几条内容即可，复杂任务再展开。模板仅辅助记录，不按标题数量或字数判完成。

负责人维护权威记录，子任务返回成果供整合；目标、方案和用户决定变化时留下简短原因及已失效结论，不把推断写成确认。独立方案、交付说明和证据按需生成，权威记录链接它们，不复制成多份事实。

首版提供 start、resume、status、abort 的对话操作约定，没有同名 CLI 或自动调度服务。恢复和中止由负责人核对记录及真实宿主现场后执行；记录本身不是程序保障。

```text
  assets/task-record.md

  references/scale.md

```

技能包自包含，按条件读取；首版不附脚本、语言专项或外部技能依赖。根 README 和使用说明提供入口，设计文档不作为运行时执行依赖。

本轮检查入口、命名、显式调用配置、包内链接及方案一致性，不为文档维护新增测试类或校验脚本。

后续新会话观察以下行为：自动识别规模及按事实调整；原始需求下能调研并澄清；角色不机械增员；主角色配置按字段解析，局部委派默认继承直接委派者；派发简述配置且不冒充实际生效；配置不受支持时如实处理；产物按需生成；实际成果回指目标；未完成、无法验证及宿主限制如实披露。上述观察尚未等同于自动推进和门禁设计完成。
