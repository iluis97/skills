# dev-workflow 维护设计

初版日期：2026-11-19；本次改造：2026-11-20。

## 目标与本次问题

技能围绕用户目标组织调研、规划、实现和核验。真实成果、必要证据和有效用户决定支撑交付，组织形式服务于目标。当前仅提供中文包，旧 `dev-flow` 和安装副本独立维护。

试用复盘暴露了：规模已明确但组织要求缺少落实；方案参数和验收条款冲突流入实现；未运行混入通过；工程问题转交用户；负责人仅报告差距；记录与现场脱节。部分行为已经违反旧规则，也暴露了规则分散、停止出口不一致、委派约束传递和行为验收不足。

本次改造收束推进语义，明确角色交接、规模基线与证据范围，并保留后续搭建小型规则引擎的依据。本次不实现引擎、宿主适配器、数据库、锁或自动调度。

后续同日改版增加两种独立委派方式：默认子 Agent，用户可对需求、角色或任务指定 thread 并混合使用。目标是保留默认组织效率，同时为需要观察和直接介入的工作提供可见会话；本轮只落实规则与宿主方法资料，不创建实际 thread 或安装副本。

本次进一步落实强制方案用户验收：负责人在方案内部检查就绪后主动通知用户，取得对当前方案的明确认同后才放行相关实施及后续执行。解决原文以清晰需求、自主设计委托或内部接收直接放行的冲突；用户可以在主对话或规划 thread 中讨论和认可，负责人核对来源及范围，无需重复批准。

## 推进规则的组织

progression.md 使用 PR-01 至 PR-19 稳定编号，每条规则具有六个明确要素：触发事件、判断依据、成立条件、处理动作、不成立或未知、结果影响。PR-01～PR-18 保留原编号，PR-19 增加方案用户验收。编号用于追踪与映射，不作为业务任务的固定执行阶段。

规则按事件评估，区分成立、不成立、未知；在工作开始、成果交接、等待及完成等决策处综合适用条件。事件次序说明先处理取消、现场及依据变化，再判断交接和下一步，避免用局部通过覆盖否决条件。

当前输入可以用简短文本表达。后续引擎实现时，可将这些概念映射为明确字段与操作接口；应先确定输入契约及可信来源，再实现条件判断。新增机器格式须与本文件所链接的规则一致，不能因便于解析改变原有授权和质量要求。

## 判断、推进与运行能力的边界

| 层面 | 负责内容 | 所需依据 |
| --- | --- | --- |
| 负责人和各角色 | 理解目标、判断质量与证据充分性、分类问题、分析变更影响、选择工作 | 原始要求、实际成果、工具观察及专业判断 |
| 推进规则及未来引擎 | 基于有依据的输入判断允许动作、必要处理和受影响工作 | 各规则明确的输入及条件，未知保持未知 |
| 宿主或项目能力 | 派发、查询、取消、实际读写、权限及必要的冲突和幂等保障 | 真实调用及返回、现场和外部结果 |

规则通过不证明成果真实或操作已完成，记录状态也不提供锁和恢复保障。后续引擎应能关联条件依据和允许动作，但成果质量仍需观察和判断；操作结果不明时查证，不能盲目重放。

## 组织与成本控制

保留 owner、planner、builder、verifier 四种职责，实际人数由任务需要及能力决定。用户说明规模是组织输入，中等任务的实际规划与核验安排可被追踪；复用已有充分成果时记录来源和复核依据。

轻量任务减少独立产物与交接，仍保留真实核对和必要独立核验；常规及复杂任务通过稳定目标标识连接方案、成果和证据。按关键事件同步一个任务记录，方案、截图和日志按需引用，不逐操作新增文件。

角色模型配置继续使用 [roles.json](../../../skills/zh-CN/coding/dev-workflow/assets/roles.json)，保留字段优先级、直接委派者继承及配置事实分层。配置缺口依赖真实宿主处理，不能通过改角色名称或口头声明补足。

技能包不内置语言或数据库专项，也不主动调用其他手动技能。`grilling` 作为可选能力按用户显式授权衔接；项目另有必需技能时按对应要求落实。

## 两种委派方式的适配

选择顺序、切换门槛和跨任务用户介入由 PR-17、PR-18 定义，方式资料只说明如何调用宿主。默认不增加提问，角色职责和规模要求不随方式改变；不另建方式配置文件，以用户指示和任务记录保存当前选择。

| 共同概念 | 子 Agent 方法 | Thread 方法 |
| --- | --- | --- |
| 执行者关联 | Agent ID 与逻辑委派者 | Thread ID、标题、父负责人和已读取位置 |
| 必需输入 | 自包含任务及适当上下文继承 | 简短启动消息引用可访问的任务记录及资料，不假设历史自动继承 |
| 结果接回 | 原生消息、等待或查询后核对成果 | 通知提示后增量读取消息及成果，再核对用户变更 |
| 用户控制 | 按真实宿主能力暂停、取消和核对 | 直接介入、暂停或接管按来源及范围同步；消息、归档不证明终止 |
| 配置 | 宿主支持的覆盖或原生继承 | 按实际创建接口支持情况应用，默认不冒充直接委派者继承 |

当前 thread 提示接口有长度上限，没有思考强度参数，也没有已确认的停止、完成订阅及自动唤醒保证。不能通过换方式丢掉现有配置要求；已有明确默认策略授权时采用并记录，否则披露具体缺口。实际能力以目标宿主 schema 和测试为准。

主 thread 维护整体唯一记录，工作 thread 返回局部成果及重要变更；需要进一步拆分的 thread 由负责人统一建立和关联，原委派者继续整合。共享工作区继续落实所有权，必要 worktree 单独安排整合；thread 不自动提供隔离。

用户在工作 thread 的直接指示先由该执行者遵循，跨任务影响由负责人核对来源并同步。读入内容仍受宿主信任边界约束，不能将转述升级为新授权。未解除的暂停或接管阻挡相关自动续跑；切换前核对旧执行现场，未知写入不启动替代者。

## 方案验收与讨论职责

PR-05 只判断方案内部质量和可提交范围，PR-19 判断当前方案是否取得可用的用户认同；开始、交接、依赖及恢复均引用该门槛。负责人持续承担主动通知、组织验收、核对及放行责任，不能只写文件等用户发现，也不能由规划者自报替代核对。

子 Agent 规划由负责人承接用户讨论；规划 thread 可直接开展讨论和多轮调整，用户在该处明确认同同样有效。记录将方案内容引用或版本、通知依据、认同来源与范围、待落实调整及失效范围分开，不新建批准状态文件。跨 thread 来源须按宿主信任边界核对，不能升级不可信转述，也不因模式不同要求用户重复认可。

所有规模均适用方案验收，轻量方案不强制独立文档；清晰需求减少澄清，自主委托允许自行设计，二者不替代当前方案认同。实质方案调整使受影响认同失效，方案内技术细节及修复实现偏差不重新审批。等待认同时可继续独立调查和修订，不能后台实施。仅分析、设计任务保留原范围，方案认同不自动授权实现；方案验收和最终交付验收分别判断。

## 验证与后续建设

先核对规则结构、语义、引用和文件职责，再按 acceptance.md 的原始输入进行实际场景执行，最后在安装后的新会话观察完整宿主行为。场景推演不能冒充真实运行，真实运行也只支持已观察的配置和场景。

每批修改后用对应场景检查，并关注是否仍有可执行工作却停下、未运行误标通过、工程缺陷转交用户、旧结果覆盖新依据等行为。代码或引擎建设应以实际缺口和具体收益为前提。当前阶段和未验证内容见 [roadmap.md](roadmap.md)。
