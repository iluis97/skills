# dev-workflow

围绕用户目标组织调研、规划、按需委派、实现与核验，按规模落实工作深度，收到成果后核对、处理问题并继续推进，用一个权威任务记录保持连续性。当前提供[中文技能入口](../../../skills/zh-CN/coding/dev-workflow/SKILL.md)。
维护设计见 [design.md](design.md)，建设与验证状态见[实施路线图](roadmap.md)，真实调用及后续引擎映射的验收资料见 [acceptance.md](acceptance.md)。旧 `dev-flow` 保留独立，新技能不读取或依赖旧包。

## 适合怎样的工作

- 从原始需求出发，需要先查资料或现有实现再澄清目标。
- 希望根据轻量、常规、复杂程度决定调研深度、分工和产物详略。
- 需要规划者明确方案，各角色按实际需要委派任务。
- 希望判断真实成果是否满足目标，并保留后续继续工作所需的记录。

## 如何使用

```text
$dev-workflow start 为订单查询增加归档数据查询能力
$dev-workflow start 中等规模：制作一个本地打开的动效页面，包含暂停和恢复交互
$dev-workflow status order-history
$dev-workflow resume order-history
$dev-workflow abort order-history
```

也可以传入负责人实际建立的任务记录路径；任务名以上一次回复为准。上述是对话操作，不是终端命令。仓库修改不会自动同步安装副本。

默认记录为 `artifacts/dev-workflow/<任务名>/task.md`；已有合适位置时可以沿用。方案、交付说明和证据按实际需要生成，不保证或强制每个任务有相同文件集合。

## 如何选择委派方式

未指定时默认子 Agent，不额外提问。可以用自然语言为整个需求或某项工作指定 thread，便于在宿主任务列表中查看并直接介入：

```text
$dev-workflow start 用多 thread 完成订单查询需求
$dev-workflow start 规划和核验用子 Agent，实现单独开 thread，我要随时调整
```

具体任务或角色的指定优先于需求整体指定，未覆盖部分沿用需求默认方式。选择 thread 不会为每个步骤创建任务，也不要求固定数量。恢复时沿用已记录选择；用户中途切换会先协调原执行者并交接有效成果，避免重复写入。

共同方法见 [tasks-and-delegation.md](../../../skills/zh-CN/coding/dev-workflow/references/tasks-and-delegation.md)，分别按需读取 [subagent.md](../../../skills/zh-CN/coding/dev-workflow/references/subagent.md) 和 [threads.md](../../../skills/zh-CN/coding/dev-workflow/references/threads.md)。用户在工作 thread 直接调整后，由执行者报告、负责人接回并协调影响，无需在各任务重复转述。暂停或接管的范围不会自动续跑；归档不代表停止。

方式及配置能否实际使用取决于宿主。当前已知 thread 创建接口没有思考强度参数，不能承诺直接应用现有 high/medium 配置；选择 thread 不等于接受宿主默认。已有明确的默认配置或替代授权可采用并记录，否则说明配置缺口，不静默降级。可见性、消息接回、运行中介入及唤醒效果需要在目标宿主验证。

## 如何配置角色

编辑所使用技能副本内的 [assets/roles.json](../../../skills/zh-CN/coding/dev-workflow/assets/roles.json)，可为 planner、builder、verifier 填写不同的宿主支持模型名及思考档位；模型默认继承，思考强度默认分别为 high、medium、high。Owner 由主线程承担并保持继承，填写配置不会切换当前会话。具体解析规则见[角色说明](../../../skills/zh-CN/coding/dev-workflow/references/roles.md#执行配置)。

主角色派发读取对应配置，局部委派默认继承直接委派者。Owner 派发前简述角色、任务和计划配置，启动后区分实际提交与宿主确认；普通进度不重复模型信息。例如：

> 规划者已按默认子 Agent 启动；模型：继承（具体型号未回报），思考强度：high（已提交）。

宿主不支持配置时应说明问题，不能静默换模型或降档。修改仓库配置后仍需按实际安装方式更新副本，切勿用仓库默认值覆盖安装副本中已有的个性化配置。

## 任务怎样推进

独立的[推进规则](../../../skills/zh-CN/coding/dev-workflow/references/progression.md) 是判断何时开始、交接、等待、完成及恢复中止的权威来源。PR-01 至 PR-19 使用稳定编号，分别写明触发事件、判断依据、成立条件、处理动作、不成立或未知情况及结果影响；PR-17、PR-18 管委派选择、切换及用户跨任务介入，PR-19 管强制方案用户验收，原有编号保持稳定。规则为后续小型引擎提供映射依据，当前仍由负责人实际执行。

核验发现实现缺陷就修复后检查新成果；方案参数或条款矛盾先修方案；真实用户选择先展示材料，其他独立工作继续。已经披露差距仍须处理授权内可执行的必要工作；方案待验收时可以调查、讨论和修订，不能以持续推进为由后台实施。

用户说明“中等”即按常规任务安排，记录中能看到实际调研、规划和验证组织。角色收到目标、约束、有效成果和相关执行资料；检查按具体行为保留证据覆盖范围。接回成果时同步接受范围、问题、责任方和下一步，恢复核对现场，中止说明取消结果及遗留工作。

## 何时讨论方案

清晰要求直接沿用，缺少事实先调查，普通技术细节在授权内决定；存在未委托的关键歧义或取舍时先讨论方向。方案完成并通过内部检查后，**负责人必须主动通知用户并组织验收，取得对当前方案的明确认同后才推进相关实施及后续执行**。这条要求适用于轻量、常规、复杂任务，也适用于清晰需求和自主设计委托。轻量方案可以用几句话表达，无需独立文档；已有同一方案的有效认同可直接复用。规则及沟通方法见[需求明确程度与用户决策](../../../skills/zh-CN/coding/dev-workflow/references/clarification.md)。

规划采用子 Agent 时，用户在主对话与负责人讨论，负责人把反馈交回规划者；采用规划 thread 时，用户可直接与规划者讨论、调整和认可，负责人仍负责主动通知、核对当前方案及认同来源并记录放行，无需用户回主对话再次确认。多轮调整后，明确指向当前方案的“可以了”“按这个做”可以作为认同；只提出修改、没有回复或开头的“开始改造”均不算后续方案已验收。实质方案变化需重新验收受影响部分，已认同方案内的工程细节和实现纠偏不反复审批。

需要深入澄清时可以使用可选技能 `$grilling`，需单独可用且由用户显式指定或在当前会话明确授权，例如：

```text
使用 $dev-workflow 完成这个需求；关键决策不清晰时使用 $grilling 澄清。
```

`grilling` 不随本包安装。仅调用 `dev-workflow` 不会隐式加载它；缺失时会说明，普通澄清仍可继续。使用该技能时按其规则达成共同理解并取得确认；已有清晰要求或自主设计委托时不强制进入问答。

## 常见问题

- **需要安装 CrewAI 吗？** 不需要，技能借鉴其任务与协作设计，使用宿主已有能力。
- **每次都会创建四个 Agent 吗？** 不会。四种职责保持明确，实际人数按任务和宿主能力组织。
- **可以只把实现放在 thread 吗？** 可以，明确指定实现用 thread，其余独立工作未指定时默认子 Agent；角色职责、证据及独立核验要求不变。
- **指定方式不可用会自动换一种吗？** 不会。没有已授权替代时说明具体缺口，其他独立工作继续；也不默默改成主线程代做。
- **关闭主 thread 后一定会自动接回吗？** 不保证。使用宿主实际通知和唤醒能力，没有可靠机制时说明接回或恢复方式，不承诺永久后台调度。
- **有助理角色吗？** 没有。各主角色可按需发起有明确目标、输入、边界和完成条件的任务。
- **可以让不同角色用不同模型吗？** 可以，在角色配置中分别填写；是否支持取决于宿主。主线程兼任职责时不因此切换模型。
- **委派会自动降低模型或思考强度吗？** 主角色应用用户指定或角色配置；局部委派默认继承直接委派者，不因任务拆小自行降档。配置不支持时应说明，不静默降级。
- **需求规模由谁判断？** 用户明确说明时直接采用，“中等”对应“常规”；未说明时负责人判断。实际工作安排要体现规模，调整时说明依据及影响，不因单文件静默削减投入。
- **中等任务一定创建固定数量的 Agent 或文件吗？** 不固定数量，但默认独立规划；已有充分方案可以复用并说明复核依据。行为变更仍需独立核验，精简文件不取消职责。
- **推进和门禁规则实现了吗？** 已提供独立、带编号和明确条件的 Markdown 规则；没有自动规则引擎、强制门禁或调度服务。后续引擎可据已核对输入判断允许动作，成果质量仍需实际观察和专业判断。
- **方案验收等于最终成果验收吗？** 分别判断。所有方案都须按 PR-19 取得用户认同；最终感知成果应展示，团队先处理可检查的问题，最终是否等待用户验收按用户要求和交付约定判断，不代写用户满意。
- **每次都要重新确认方案或重走流程吗？** 当前方案需要有效用户认同；同一方案已有有效认同则复用，恢复不重问。实质方案变化重新验收受影响部分，工程细节及实现纠偏不重复审批，也不机械重走全部流程。
- **用户应该和谁讨论方案？** 子 Agent 规划时由负责人承接，规划 thread 模式可直接和规划者讨论；负责人始终负责通知验收、核对认同及放行，规划者转述“已获同意”不能单独作为依据。

## 如何判断符合预期

- 目标被具体化并贯穿方案与成果，没有缩小为“能运行、无报错”。
- 规模有来源，并落实为调研、方案、组织和验证安排，没有只填标签或机械增员。
- 调研能回答的事实自行查明，需要业务选择时才联系用户。
- 清晰描述不会被重复盘问；方案就绪后负责人主动通知验收，当前方案的明确认同可追溯，等待认同时不后台实施，`grilling` 按授权衔接。
- 委派有清楚边界，委派者保留综合判断，主角色配置与局部继承区分明确。
- 方式按用户指定及默认准确选择，恢复不重置；thread 中用户变更能接回并同步，暂停和接管不被自动覆盖。
- 派发简述角色、任务和配置，配置要求、实际提交与宿主确认没有混为一谈。
- 结果先检查再用于依赖任务；参数与条款矛盾先消解，缺陷和证据缺口实际处理，不只汇总风险，也不原样无限重试。
- 等待说明原因与解除条件，独立工作继续；相关变更后的旧结论重新核对，恢复不盲目重复派发。
- 一个记录能说明做到哪里、还缺什么；独立文件与证据只在实际需要时生成。
- 未运行、受阻及目标差距如实呈现，不以局部检查通过代替整体达成。

## 专属维护要求

- 推进条件集中维护在包内 progression.md，其他资料按规则编号引用；改变条件时同步引用和对应验收场景，不在使用说明新增另一套执行规则。
- 规则编号保持稳定，不按章节移动重新编号；调整规则含义时同步事件次序、引用及场景。角色方法、配置解析、核验方法和记录格式各归所属资料。
- 子 Agent 和 thread 共用同一组推进条件；宿主操作分别维护在对应包内资料，不能通过适配方法增加另一套授权、完成或停止规则。
- 方案内部质量检查、用户方案认同及最终成果验收分别维护；改变方案验收要求时同步 PR-19、开始与依赖规则、角色交接、讨论路径、记录模板及场景，避免清晰需求或自主委托绕过门槛。
- 包内执行不依赖本目录。验收资料面向维护者，区分规则对照、实际场景推演和宿主真实调用；只有发生并有证据的验证才能记为通过。
- 仓库修改不会更新安装副本；同步需另按用户授权核对目标、备份并保留个性化角色配置。

文件核对与规则对照只能说明结构和语义检查情况。宿主真实调用、角色配置生效、委派继承、任务推进及恢复中止效果仍需在安装后的新会话中观察，当前状态见路线图及验收资料。
