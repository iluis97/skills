# dev-workflow 实施路线图

本路线图面向技能维护者，分阶段建设和验证 `dev-workflow` 的协作能力。它不是使用技能处理业务任务时必须执行的阶段列表，也不代表所列能力已经实现。当前设计见 [design.md](design.md)，实际执行规则以[技能入口](../../../skills/zh-CN/coding/dev-workflow/SKILL.md)及其包内资料为准，运行时不要求读取本文件。

## 建设原则与当前进度

保持三个架构边界：规则不替代 Runtime，状态不替代成果真实性，负责人不退化为固定任务列表的执行器。先验证规则能指导工作，再按真实执行缺口补充保障，存在稳定的重复需求后才增加编排自动化；可靠性验证随能力同步建设。

| 阶段 | 当前状态 | 下一步或启动条件 |
| --- | --- | --- |
| Phase 1：规则层落地与验证 | 已有首版指令及人工场景推演；试用发现用户未参与关键设计决定的问题，已修订规则，待复测，完整场景验收未完成 | 复测清晰需求直接执行与关键歧义先讨论，继续其他场景验收 |
| Phase 2：最小 Runtime 保障 | 尚未建设技能专用运行层；执行能力依赖宿主 | 明确实测缺口、宿主已有能力及必须补充的保障范围 |
| Phase 3：动态编排增强 | 已有负责人动态判断规则，尚无自动编排引擎 | 出现稳定的重复组织需求，且所依赖的运行能力已验证 |
| Phase 4：可靠性与可观测性 | 尚未建立系统级测试及指标体系 | 随新增运行能力开展必要验证，再按长任务需求扩展 |

后续阶段是候选建设范围，不承诺全部实现或引入特定框架。进入下一阶段应有具体使用问题、预期收益和可验证范围，不能仅因上一阶段结束就启动开发完整工作流引擎。

## Phase 1：规则层落地与验证

第一优先级。目标是让现有 Agent 团队遵循一致的推进协议，同时保留负责人的目标判断。

沿用现有 Owner、Planner、Builder、Verifier，不新增 Supervisor、Coordinator、Worker 角色体系；推进规则入口沿用 `references/progression.md`，不另建 `task-progress.md`。

- [x] 写入开始条件、结果检查、问题分流、依赖、完成及恢复中止规则。
- [x] 明确现有四种职责、委派边界、写入所有权和核验独立性要求；这些说明不代表宿主已落实权限控制或文件锁。
- [x] 约定交接需包含成果、必要依据及未解决问题；按需记录真实执行者、状态和配置依据，不强制全部任务回传 JSON。
- [x] 在规则中区分任务结论、真实执行现场、实际成果及核验依据，不为区分概念建立多套状态文件。
- [x] 补充失败分类、有限重试、旧结果适用性检查、结论复核及恢复规则。
- [x] 明确基于真实成果的核验和整体目标完成条件。
- [x] 根据试用反馈区分清晰需求直接执行与关键决策先讨论，接入按用户授权使用的可选 `grilling`；内部方案审查不代替用户决定。
- [ ] 在安装后的新会话中完成典型场景验收，保留必要证据并修订实际发现的问题。

以上已勾选项仅表示相应指令已落地，不证明进程管理、权限或恢复保障已经实现。

验收时观察负责人是否正确处理以下情况：

| 场景 | 预期行为 |
| --- | --- |
| 任务返回 | 检查实际成果及依据后再接受，不直接采信执行者状态 |
| 用户描述清晰或已委托自主设计 | 按描述或委托推进，不强制问答或重复确认 |
| 关键方向未明确且未委托 | 先提出初步方向并讨论，按授权衔接 grilling；内部审查通过不触发依赖未决方向的正式实现 |
| 用户要求先审阅或使用 grilling | 遵守具体审阅要求及所调用技能的共同理解确认规则；关键决定未解决时不后台派发依赖实现 |
| 未授权或未安装 grilling | 不隐式加载或假称执行，说明调用方式或缺失，普通必要澄清仍可继续 |
| 实现或方案失败 | 按问题性质修复、调整方案或处理外部阻塞，不无依据原样重试 |
| 用户修改目标 | 判断影响并更新相关任务、依赖和旧结论，保留有效成果 |
| 旧结果迟到 | 先检查适用性，不覆盖新方案或新成果 |
| 局部完成 | 明确可用部分及剩余差距，不宣称整体完成 |
| 必需前置成果不齐或局部阻塞 | 等待受影响任务，继续其他独立工作 |
| 整体完成 | 依据当前目标、真实成果、必要验证及需要的用户验收给出结论 |
| 恢复、中止与查询 | 恢复先核对现场，不重复派发状态未知的写入者；取消不冒充终止；status 保持只读 |

进入 Phase 2 前，应能区分规则表达或执行问题与宿主实际能力缺口，并列明需要补充保障的具体场景。文件核对和人工推演不能替代上述实际调用验收。

## Phase 2：最小 Runtime 保障

第二优先级。目标是解决实际多 Agent 协作中的执行冲突和现场不确定性；优先复用宿主能力，不重复建设已有的执行管理。

- [ ] 核对宿主已有的执行 ID、状态查询、取消及权限隔离能力，确定需补充的最小范围。
- [ ] 为每次实际执行关联唯一 ID；已有宿主句柄可以复用，业务任务与执行尝试分别关联。
- [ ] 记录真实执行者、写入范围和必要的冲突保护；所有权记录不能冒充锁。
- [ ] 查询真实执行现场，区分运行、结束、失联及未知情况。
- [ ] 区分取消请求、终止确认和无法确认，不在未知现场重复启动写入者。
- [ ] 对明确纳入支持范围的外部操作提供幂等或查重保护，并处理操作结果不明的情况。
- [ ] 关联成果位置和核验依据，避免从执行状态推导成果正确性。
- [ ] 支持中断后核对现场、已发生操作及有效成果，再安全决定恢复动作。
- [ ] 随上述能力同步验证冲突、重复执行、取消未生效、失联和外部副作用不明等场景。

幂等保障按操作定义：查询、本地写入、创建外部对象或发送消息分别处理；优先使用服务端幂等键和结果查询，无法确认成功与否时先查证，不默认安全重试。恢复能力的初始范围是重建已知现场、识别未知情况并选择安全下一步，不承诺任意操作自动重放。

可以研究 Temporal、LangGraph 的执行与恢复思路，不预设部署这些项目。验收需证明纳入范围内的真实执行保障有效，并说明能力边界；仅新增日志或 Markdown 状态不算完成。

## Phase 3：动态编排增强

目标是减少稳定、重复的组织操作。负责人从 Phase 1 起就按目标和证据动态判断，本阶段增强自动化，不把决策交给固定流水线。

- [ ] 辅助根据目标拆分可独立交付的任务，保留负责人对范围和完成条件的判断。
- [ ] 根据角色能力、用户要求及可用配置选择执行者。
- [ ] 根据有效前置成果、所有权和运行条件动态安排并行。
- [ ] 根据结果调整计划，按失败性质选择修复策略。
- [ ] 根据成果影响范围提示或触发必要复核，保留未受影响的有效依据。
- [ ] 在实际需求明确时支持局部委派者管理子团队，同时保持责任、配置继承、依赖及取消范围清楚；当前进一步拆分仍按现有委派规则协调。

可评估 CrewAI 或 LangGraph 的局部能力，先说明具体收益再决定是否引入。验收应证明自动化减少组织成本且不削弱目标判断、授权边界和核验独立性；不得以自动生成任务数量作为成功指标。

## Phase 4：可靠性与可观测性

目标是支持复杂、多轮、长时间任务。必要测试随 Phase 2、Phase 3 的能力同步开展，本阶段扩展系统性覆盖和长期观测。

- [ ] 建立必要的执行事件历史，关联业务任务、执行尝试、成果和核验依据。
- [ ] 建立恢复、并发冲突及外部副作用测试，覆盖重复请求和结果不明情况。
- [ ] 完善超时、失联、取消失败和恢复后旧结果迟到的处理。
- [ ] 按实际需求增加成本、并发和资源管理，避免无边界运行。
- [ ] 建立整体目标完成率和核验质量的评估方法，区分已验证、未验证和用户反馈，不只统计状态字段或任务完成数量。

验收应依据代表性长任务和异常场景说明恢复能力、冲突处理和观测范围；同时控制数据保留与实现成本，不默认建设大型监控平台。

## 维护方式

依据实际成果和验证证据更新进度，重要能力补充范围、限制及依据；未验证的项目保留待验证，不能因文档更新而勾选完成。实施中可按问题调整阶段范围，可靠性工作可以跨阶段进行。

路线图获认可不等于授权安装框架、迁移状态、访问外部服务或实现全部候选能力。某项能力确定实施后，同步设计方案、技能执行规则及使用说明，避免未来计划与当前能力混淆。
