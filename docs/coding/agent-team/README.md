# agent-team

围绕用户目标统筹开展调研、设计、实现与审查，由 Leader 持续推进，并以实际成果和有效证据判断交付。当前提供[中文技能入口](../../../skills/zh-CN/coding/agent-team/SKILL.md)。

## 核心理念：一版契约，宿主实现，不参与决策与干预

`agent-team` 只维护**一版宿主无关的角色职责契约**，不绑定任何特定的 Agent Harness（如 Claude Code、Codex、OpenClaw 等）。

技能本身只定义“团队有哪些职责、谁对什么负责、上下游如何交接、交付底线是什么”，**不参与也不干预各 Agent Harness 的具体实现与运行时决策**：

| 关注点 | `agent-team`（技能层） | Agent Harness（宿主层） |
| :--- | :--- | :--- |
| 角色职责与边界 | 定义 Leader、Designer、Builder、Reviewer 的职责与隔离约束 | 决定由多少个执行者承担（单 Agent 兼任、Subagent、多 Agent 团队或 Workflow） |
| 模型与推理配置 | 不指定模型名、供应商或推理档位 | 结合宿主能力与任务需要自行选择或继承 |
| 调度与并发方式 | 不规定串行/并行规则或编排脚本 | 自行决定何时派发、是否并行、如何委派局部任务 |
| 状态与上下文传递 | 要求维护唯一任务记录与明确交接依据 | 自行决定任务记录格式、存储位置、消息传递与恢复机制 |
| 工具与权限控制 | 只约束写入所有权与只读调研/独立审查边界 | 自行实现工具调用、沙箱、权限审批与异常重试 |

这样做的目的是让各 Agent Harness 充分发挥自身的原生编排与调度能力，避免技能层硬编码状态机、模型配置或工具协议，从而在多宿主环境下保持长期稳定与可维护性。

## 做什么

技能明确四种角色职责，实际由多少执行者承担、如何分工以及是否并行，由宿主结合自身能力与任务需要决定：

- **Leader**：贯穿任务全过程，负责对齐需求与验收标准、组建与配置团队、统筹推进与交接，并依据实际成果和有效证据判断交付。
- **Designer**：负责只读调查现场、识别待决事项、制定覆盖目标与验收标准的可执行方案，并响应反馈修订方案。
- **Builder**：负责在有效方案与写入边界内完成实现、局部整合、必要测试与自检，并针对审查缺陷定向修复。
- **Reviewer**：负责独立检视实际成果与目标/验收标准之间的差距，按风险验证并区分证据范围、归因缺陷与复核修复；**不参与当前被审查成果的实现**。

具体行为约束与交接要求以[技能入口](../../../skills/zh-CN/coding/agent-team/SKILL.md)为准，本文档不重复展开执行细则。

## 什么时候使用

适合需要明确“规划—实现—独立审查”职责分工、希望由宿主自主决定执行方式的任务，例如：

- 需求涉及多模块改动、方案取舍或明确验收标准，需要避免边想边改或自写自审。
- 在不同 Agent Harness 中使用同一套团队协作标准，希望直接复用宿主原生的 Subagent、Team 或 Workflow 能力。

## 如何使用

当前技能允许按需自动触发，也可以在对话中显式调用：

```text
使用 $agent-team 完成这个需求：……
```

调用后，宿主会作为或指派 Leader 接管任务：先与用户对齐需求、范围与验收标准，再根据任务规模与自身能力决定团队形态（如单人兼任多角色或派发多个独立执行者）并推进交付。

## 常见问题

- **为什么包内只有一份 `SKILL.md`，没有 `roles.json`、脚本或状态机？**
  `agent-team` 刻意保持极简，只维护角色职责与协作边界。模型选择、任务存储、并发调度和重试机制属于 Agent Harness 的实现范畴，交由宿主原生能力处理。
- **单 Agent 或不支持子代理的宿主能用吗？**
  可以。四种角色代表职责而非必须创建四个进程；宿主在单执行者模式下也可按阶段切换职责视角完成工作，但仍需守住调研只读、确认边界与独立核验要求。
- **它和 `dev-flow` / `dev-workflow` 有什么区别？**
  `dev-flow` 与 `dev-workflow` 在技能层内置了较完整的阶段流转、推进规则、记录格式或角色配置模板；`agent-team` 则只保留最核心的团队职责契约，把所有调度与实现决策交还给宿主。
- **为什么技能不直接决定何时并行或派发几个成员？**
  不同 Agent Harness 的并发能力、上下文隔离机制和成本模型差异很大，由技能强行干预反而会限制宿主判断。因此仅规定“由 Leader 结合宿主能力与任务需要决定”。
- **修改仓库中的 `SKILL.md` 后会立即影响已有会话吗？**
  仓库源码与已安装副本独立，修改后需按宿主要求同步到安装目录，并在新会话中验证实际效果。

## 如何判断符合预期

- **职责清晰且守住底线**：调研阶段未提前修改生产实现；关键未决取舍先向用户确认，未擅自拍板；Reviewer 未参与当前成果实现，未自修自批。
- **宿主自主调度生效**：团队人数、串并行方式、模型与工具调用均由宿主自然决定，未出现生硬套用不存在的外部状态机或脚本的情况。
- **交接与交付有据可依**：Builder 交付附带真实自检结果而非虚构通过；Reviewer 区分静态检查与动态运行证据；Leader 依据实际成果与有效证据向用户汇总交付，不把子角色口头报告直接当作完成。

## 专属维护要求

- **只维护一版通用契约**：不针对特定 Agent Harness（如 Claude Code、Codex、OpenClaw 等）分叉出多套实现，也不在技能中引入宿主专属工具名、模型名或平台配置。
- **严禁下沉到实现细节**：不在 `agent-team` 中新增调度引擎、固定状态机、强制文件模板或模型配额决策，保持“职责定义”与“宿主实现”的清晰边界。
- **不另存执行规则**：本文件仅作说明与索引，修改角色职责或约束时直接更新[技能入口](../../../skills/zh-CN/coding/agent-team/SKILL.md)，并保持本说明与入口定位一致。
