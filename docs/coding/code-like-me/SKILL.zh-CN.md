# code-like-me

本文是 [英文执行规则](../../../skills/coding/code-like-me/SKILL.md) 的中文阅读版，供人阅读和维护，不作为技能入口。在遵循项目约定与接口契约的前提下应用个人编码偏好。

## 目标

像我一样思考和组织代码：职责清晰、命名直观、复用现有抽象与工具，保持代码易读、易改、易扩展。

按用户要求完成实现与必要验证；仅要求分析或建议时，按该范围输出。

## 1. 规则优先级与适用范围

- 优先级：任务明确要求 → 项目规范 → 同模块维护良好的相邻实现 → 本技能偏好。始终保证正确性与接口兼容性。
- 通用规则适用于各语言，按其惯用方式实现；语言专节仅在使用对应语言时叠加应用，未列出的语言以项目规范为准。
- 已有项目延续局部约定，新增模块按实际需求设计；不要照搬参考项目的包名、框架或业务模型。
- 个人习惯以多个一致实现为依据。不要从单个特例、生成代码或其他作者代码推断；质量规则是约束，不代表历史代码全部满足。
- 保留用户已有改动，仅修改任务所需文件。不要为统一风格扩大范围、格式化整个项目、升级依赖或重构无关模块。

## 2. 执行流程

1. **明确边界**：识别需求、接口、兼容要求和已有改动；仅在缺失信息影响业务行为且上下文无法判断时提问。
2. **阅读上下文**：检查项目说明、构建与语言版本、目录、相关调用方、实现和测试；若同模块存在类似实现，选取两到三个确认与任务相关的约定，阅读范围与改动相称。语法与
   API 必须兼容目标版本。
3. **选择实现**：先复用类型、接口和工具，再根据当前需求判断是否新增抽象；复杂流程梳理稳定步骤与变化点，简单需求直接实现。
4. **完成修改**：按单一职责与逻辑完整原则组织方法或函数，依据契约实现必要的边界校验与失败处理。
5. **验证与审查**：按影响选择编译、静态检查、现有或针对性新增测试，重点覆盖分支、状态与边界；按文末清单审查差异并交付。

## 3. 通用编码规则

### 设计原则与模式

- **职责与契约**：以职责清晰、接口精简、低耦合为目标，按需运用 SOLID
  与迪米特法则；受容器管理的依赖沿用项目注入方式。修改既有能力时保持接口契约，不额外收紧输入条件或暗改返回、异常、副作用语义。
- **复用与协作**：优先已有组件与扩展机制、组合和委托；继承用于真实替换关系或稳定模板流程。
- 按当前需求直接实现；新增抽象应解决已有重复业务知识、明确变化点或隔离需求，维护成本应与实际收益相称。
- **禁止**：仅为“以后可能扩展”引入接口、抽象基类、策略、工厂或配置层。单一实现或少量逻辑本身不是抽象依据，项目已有约定和明确隔离需求可以构成依据。
- **组件协作**：复杂流程检查依赖方向、资源所有权、生命周期、顺序、并发与失败传播；验证替换和扩展不破坏契约。

### 命名与逻辑组织

- 类型、方法、函数、变量表达业务概念与用途，沿用项目英文命名、缩写和类型后缀。
- 方法或函数名体现动作与对象，布尔命名沿用项目惯例；名称应准确区分查询、转换、校验与执行，不得隐藏写入或外部调用。
- **单一职责，逻辑完整**：一个方法或函数围绕一个明确的职责，完成一段语义完整的逻辑；属于同一职责的判断、计算与处理应保持连贯，不混入无关职责。
- 主流程按业务步骤在同一抽象层次展开；提取方法应有独立语义、复用价值，或明显改善主流程可读性。编排方法可以协调共同完成其职责的多个步骤。
- **禁止**：仅为缩短方法机械拆分，或增加没有独立职责的转发与包装；框架适配或有明确隔离职责的委托按实际职责判断。
- 布尔结果直接表达，不用等价的 `if/else` 包装或重复判断当前分支中仍成立的条件；有独立处理或副作用时保留分支。
- 前置条件不满足、合法无操作和失败分支可优先提前退出，让正常流程顺序展开；退出时保持资源释放、事务和必要副作用正确。
- **禁止**：用静默退出代替业务失败，或将需并列比较的正常业务分支强行拆成零散的提前返回。仅在契约允许无操作时直接返回，清晰的
  `if/else` 可以保留。
- 重复业务规则归入所属领域或服务；跨业务通用且无状态的能力才放入工具模块。

### 固定值与业务编码

- 状态码、类型码、阈值和默认值等业务固定值，优先复用已有常量、枚举、配置或所属类型能力；没有合适定义时，在所属范围命名。
- **禁止**：在判断、赋值、查询或计算中散落业务魔法值，如 `status == 2`，或重复定义已有常量；即使只出现一次，也应表达业务含义。
- `count > 0` 等语义明确的局部字面量无需提取；不要机械提取每个字面量，也不要在没有配置需求时将固定业务定义改成配置项。

### 数据与状态建模

- 数据对象承载数据与必要局部行为，服务负责业务编排；实体与对外契约遵循分层约定。
- 有限稳定的类型、状态和操作集中建模，减少散落值与重复分支；复用的编码查找、描述获取和判断归入所属类型或转换组件。
- 明确空值与未知编码的返回、默认或异常契约；接口、持久化与消息使用稳定编码。不要擅自将未知编码视为正常状态，也不要随意修改已发布编码。
- 状态类型封装自身属性相关的简单行为；服务依赖、数据库或外部调用等复杂行为归入策略或业务组件。

### 校验与防御边界

- 按输入来源、类型、契约和业务规则设置校验：入口负责格式与必填项，服务负责存在性、权限、状态与业务约束，沿用既有职责边界。
- **禁止**：重复检查同一调用路径中上游已保证且仍成立的条件，包括必需依赖、已校验参数和契约保证非空的返回值；不要仅因理论上可能为空逐层判空，或为不可能发生的情况增加兜底。
- 新入口、新信任边界、允许缺失的查询结果及可能变化的状态保留必要检查；精简时保留权限、业务状态、写入范围、并发及一致性保障。

### 异常与日志

- 按既有异常契约报告失败，复用校验工具、业务异常与错误码，消息说明业务原因；捕获用于恢复、补充上下文或转换语义，其余沿用统一处理。
- **禁止**：无业务或接口依据地返回空集合、空值、默认对象、零值或成功结果，跳过异常数据或吞错后继续；契约允许的空结果、恢复与降级正常保留。
- 面向调用方的错误消息不暴露堆栈或底层细节。
- **日志服务于排查**：沿用日志框架与级别，用参数化日志记录关键变化、外部失败和排查上下文；涉及序列化或较重计算时先检查级别。
- **统一业务日志表达**：同一业务流程各环节的日志使用统一、可检索的业务关键字前缀，保留关键业务标识，写明处理步骤或结果，便于串联过程、定位问题。
- **不要重复记录异常或输出敏感信息**：避免无意义高频输出和重复异常日志；当前层需要记录异常时保留堆栈，不输出凭据、令牌或完整敏感对象。

### 集合、转换与数据访问

- 优先现有集合、字符串、转换与数据访问工具；标准库足够时，不为相同能力新增依赖。
- 过滤、映射、分组使用清晰的语言惯用写法；复杂分支、副作用或提前结束优先用循环。
- 明确空集合、空元素、重复键与顺序语义；合并数据时按业务定义冲突策略，不要随意保留一条来消除冲突。
- 明确数值默认值、精度、舍入与比较语义；不要依赖未经确认的工具隐含行为，也不要无业务依据地将零视为缺失。
- 沿用对象转换与字段映射方式，核对必填、类型与含义；不要用通用复制掩盖字段差异。
- 复用数据访问组件或服务查询；可批量查询的数据不要在循环中逐条查询，批量操作考虑批次与事务语义。
- 事务按业务原子性划定，遵守框架事务与回滚规则；外部调用、缓存、消息的失败补偿沿用既有机制。
- 写库后维护缓存时，核对并复用提交后回调机制，明确无事务与回调失败的处理；不要让数据库回滚后仍保留本次写入产生的缓存变化。
- 重复且可可靠失效的热点中间结果可缓存；优先现有组件，明确键、生命周期、写后失效与并发语义，不要照搬容量或 TTL。
- 更新、删除与批处理明确范围和重复执行行为，保留必要条件、返回值检查与并发控制。

### 注释与格式

- 沿用缩进、导入、换行、声明标记排列及注释语言，使用现有格式工具。
- 类引用通过 import 引入；仅当存在同名类冲突或导入会产生歧义时，才在使用处写全路径，并保持局部写法一致。不要在无冲突的代码中直接使用全路径类名。
- 中文业务注释说明意图、约束、算法步骤与取舍；公共能力、复杂方法或函数与关键字段按项目要求描述实际参数、返回与异常。不要逐行翻译代码。
- 文档注释放在语言和文档工具要求的位置，局部说明靠近实现，行为变更同步更新注释。不要编造作者、日期、性能保证或未实现能力。

## 4. 各语言的补充规则

处理 Java 代码时，在选择实现和修改前阅读 [references/java.zh-CN.md](references/java.zh-CN.md)。其他语言沿用项目规范，不加载 Java 专属规则。

## 5. 完成前检查与交付

- [ ] 差异满足任务范围与适用约定，没有意外改变行为或覆盖用户改动。
- [ ] 方法或函数职责单一、逻辑完整，拆分具有语义；业务固定值使用已有定义或在所属范围命名，没有散落的业务魔法值。
- [ ] 新增抽象、校验、兜底与提前退出均有当前需求或契约依据，没有冗余判断、重复防御或静默吞错，必要保障仍然完整。
- [ ] 验证覆盖受影响的契约、边界与失败路径，注释与最终实现一致。

交付时简述修改、验证结果，以及未执行或受阻的相关检查；仅解释影响使用或维护的关键取舍，不复述技能规则。
