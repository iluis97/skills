# Agent 实际场景验收流程

本流程供用户验证 Agent 在真实开发任务中使用 `code-like-me` 的实际表现，也可用于比较技能版本或 Agent 配置，包含场景选择、执行步骤、证据要求和结果模板。执行规范以实际安装的 [SKILL.md](../../../skills/zh-CN/coding/code-like-me/SKILL.md) 及适用的 [Java 编码规则](../../../skills/zh-CN/coding/code-like-me/references/java.md) 为准。

一次验收按“选任务 → 固定初始状态 → 新会话执行 → 收集证据 → 分项判定 → 记录结果”完成。只验证当前 Agent 时运行一侧即可；比较版本时，两侧从相同初始材料分别开始。本流程不要求每次跑完全部场景。

## 1. 选择真实任务并填写任务卡

优先选择近期遇到、能说明问题且结果可检查的真实任务。一次验收围绕一个明确目标，例如修复单条数据更新、调整一处日志或只读评估一个方法。将需求、契约和必要原始事实交给 Agent；预期实现、评分表及历史验收结论留给验收人。

先在验收记录中填写以下内容。尖括号中的内容由实际任务替换，不把模板占位符直接发给 Agent。

```text
场景编号与名称：<例如 S05，按编号修改当前租户规则名称>
验收目标：<本次要验证什么行为>
项目与起点：<仓库、分支、提交或文件快照；已有未提交改动>
任务文件及必要上下文：<目标实现、调用方、接口契约、项目规范、既有检查>
已知问题：<当前行为、复现输入及实际结果>
目标行为：<正常、边界、失败路径应怎样表现>
必须保持的契约：<参数、返回、异常、权限范围、副作用等>
允许操作范围：<允许修改的模块；只读时明确不修改、不跑测试>
验证办法：<已有测试、编译命令或人工复现步骤及预期结果>
已知环境限制：<依赖、凭据、网络或外部服务缺失；没有则填无>
```

事实缺失可以作为验收内容，但要能判断 Agent 是否应从项目查明或向用户询问。不要一边运行一边补充只对其中一侧可见的业务条件，再将两侧当作相同输入比较。

### 场景选择表

下表使用固定编号，便于关联任务和复验结果。选择最贴近实际任务的一项，准备对应事实和可验证路径即可。读取主题仅供验收人定位，不是发给 Agent 的文件白名单；项目实际涉及其他主题时应叠加检查。

| 场景 | 运行前准备的事实与材料 | 运行后重点核对 |
|---|---|---|
| S01 局部缺陷修复 | 一个无数据访问和副作用的局部问题，例如姓名拼接；提供空白、缺失值等合法边界。 | 结果符合契约，修改集中；无固定设计报告或无关抽象。 |
| S02 声明与业务分支 | 模型及服务；明确字段单位、空值含义、编码和到期边界，任务需要新增字段、分支及私有方法。 | 正常及到期边界正确，编码兼容；适用声明和业务分支注释的覆盖与内容正确。 |
| S03 语义不变的分支调整 | 可简化的业务分支、相关检查，以及纯技术防护与业务判空的事实。 | 行为不变，修改过的业务分支仍满足注释要求，不批量改写无关历史代码。 |
| S04 精简重复校验 | 提供上游校验依据、调用链、权限检查、可变状态及条件写入机制。 | 仅删除已由上游保证且仍成立的重复检查；权限、状态和竞争保护保留，交付说明取舍依据。 |
| S05 统一数据范围 | 仓储已按当前租户统一过滤；准备本租户、其他租户和不存在记录。 | 修复更新逻辑；其他租户不被修改，服务层没有重复建设已有范围保障。 |
| S05U 服务负责范围 | 仓储没有统一过滤，由当前服务负责权限；准备相同三类数据。 | 补齐本层范围约束，阻止越权，保持返回和不存在时的异常契约。 |
| S06 外部失败 | 外部客户端接口、成功返回、原异常传播契约、负责记日志的层次及敏感字段；使用替身或隔离环境。 | 原异常按契约传播，日志次数、事件标识和堆栈正确，不泄露敏感内容，不擅自增加重试。 |
| S06L 局部日志 | 明确允许记录的标识和结果字段，用虚构 token、payload 检查敏感信息。 | 日志符合要求，返回行为保持；不引入无关依赖或框架。 |
| S06M 消息重投 | 提供已有原子去重 API 及成功、重复、失败释放占用的契约。 | 副作用在原子机制内执行；重复完成不再执行，失败按原契约传播，再次处理可成功。 |
| S07 只读调查 | 指定方法、调用上下文与契约，例如无记录可返回空值、数据库故障必须传播。 | 指出问题并给出依据，区分违规与可选改进；不改文件、不运行测试，允许无 Git 差异。 |
| S08 已有修改及验证限制 | 保留一项可识别的未提交修改；在项目说明中注明一项确实无法运行的验收及原因。 | 原有修改未被覆盖，能做的验证已完成；未验证项和原因明确，未将部分通过说成整体验收完成。 |
| S09 提交后缓存 | 提供事务、已有提交后回调及其失败传播契约；可检查提交前、提交成功和回滚。 | 沿用既有机制，提交前及回滚后不留下新缓存值；提交后行为、回调失败语义保持。 |
| S10 资源释放 | 明确资源由本函数创建并拥有，提供正常、缺失字段和解析失败输入，以及合法默认值契约。 | 各路径释放本层资源，不越权关闭借用资源；默认值和异常传播保持。 |
| S11 类型与领域建模 | 外部输入为字符串或 `Map`，同一实体存在多个需同步的阶段布尔；目标语言支持枚举、状态机或有限变体且项目已使用。 | 外部输入在边界解析为领域类型；多个状态改为状态机、枚举或有限变体；未用类型擦除或强制转换承载已知结构；项目未使用的特性不被强行引入。 |
| S12 内部 API 迁移 | 内部接口需调整，无外部兼容要求，调用方可同批修改；仓库内有测试和调用方。 | 同批迁移全部调用方并删除旧路径，不保留平行实现；调用方、测试和文档同步，未擅自保留兼容层。 |
| S13 量化结论 | 性能任务提供单次前后耗时，未给基线、运行次数或波动范围；另有可复跑的构建或测试入口。 | 补齐基线、运行次数和波动范围；差异小于波动时不报告提升或回归；结论保留限制因素，未用单次结果代替。 |
| S14 批量机械改动 | 需要跨多个文件做同类重命名或替换，项目有可运行的检查。 | 先手工完成一个单元并验证，再写确定性脚本或 codemod 完成其余部分；脚本可重跑，交付包含脚本或说明；少量显而易见修改才纯手工。 |
| S15 功能实现与接口设计 | 方案文档只给业务字段和权限范围，接口与数据形状未定；有相邻模块可参考。 | 先定数据形状和接口；抽象能追溯到方案；无目标外扩展；真实入口验证正常、边界和失败路径。 |
| S16 缺陷最小修复与根因 | 缺陷旁边有可见死代码和更大的结构问题；提供复现输入与预期。 | 先复现并定位根因；只改证据路径；不顺带重构、格式化或调依赖；同面复验并回归受影响路径。 |
| S17 行为保持重构 | 外部行为清晰，有可运行的真实入口或既有检查；目标结构需要调整命名、分层或数据形状。 | 先固定行为特征测试（pin）或等价性检查；调用方同批迁移并删除旧路径（无外部兼容要求时）；真实路径冒烟；无收益或行为漂移时回退。 |
| S18 性能结构性改造 | 提供基线、目标值、运行次数和波动范围；瓶颈需改算法、数据结构或批量方式。 | 允许瓶颈路径内的结构性改造，不被“最小改动”误拦；前后同环境对比；行为契约保持；报告波动与限制。 |
| S19 场景判断与冲突 | 方案文档写“修缺陷”，上下文像重构；或用户要求性能优化但方案强调最小改动。 | 说明采用的场景和依据；按主目标执行；不静默扩大或缩小授权；跨场景按依赖顺序组合。 |

首次摸底可选择 S01、一个实际涉及的专项场景，以及 S07 或 S08，分别观察局部任务、专项规则和操作边界。调整技能入口或跨主题规则时，再按影响覆盖相关场景；对完整场景集的验收才运行上述全部 22 项。

### 按需补充的边界

当真实任务涉及以下条件时，在对应场景中补充材料和观察点；无需为每次验收单独运行全部变体。

| 关联场景 | 补充材料 | 观察重点 |
|---|---|---|
| S01、S04 | 分别提供已明确的设计要求和留有实现选择的需求。 | 已定要求直接落实，未定选择按影响自行判断，不借分析改写既定要求或对工程细节逐项请求确认。 |
| S01、S04 | 单次使用但有独立业务语义的步骤，以及只转发一次调用的包装方法。 | 判断拆分的职责与可读性收益，不因单次使用就合并，也不强行合并不同业务规则。 |
| S02 | 新增、语义变化、仅格式变化及重写的声明。 | 正确判断注释范围及例外，不为补注释改写生成机制。 |
| S02 | 外部协议、平台模型与内部枚举使用不同编码，且已有集中定义。 | 核对单位、编码体系、空值与默认值，合理引用已有定义，不重复维护同一说明。 |
| S05、S06、S09 | 少量事务、共享状态或跨系统副作用代码，已有提交后与失败处理机制。 | 不按修改量降低检查深度，不误信本地事务或提交后回调能独自保证跨系统一致性。 |
| S06 | 契约允许的空结果、降级、恢复或跳过，以及真正的失败路径。 | 保留合法行为，恢复或降级失败按契约传播，不将真实失败伪装成成功。 |
| S02、S08 | 项目指令引用独立规范，或规范文件读取失败、关键内容被截断。 | 实际读取引用规范，补齐必要内容；无法取得时明确未确认。 |
| S08 | 最终修改偏离最初计划，或功能通过但仍有规范遗漏。 | 按最终差异与实际影响复查，不以最初计划或功能检查代替规范核对。 |
| S15、S17 | 方案文档已定接口，或只给业务目标；有/无先例。 | 方案已定直接落实；无先例且结构影响大时比较候选；不新增目标外扩展点。 |
| S16、S18 | 任务同时要求修缺陷和优化性能，或性能改造涉及行为契约。 | 按依赖顺序组合；性能改造默认保持行为；需要行为变更时先确认授权。 |
| S19 | 用户口头说“优化”，方案写“重构”或“修缺陷”；或场景来源冲突。 | 以用户明确指定和方案文档为准，说明依据；不按关键词判断。 |

## 2. 固定项目、技能和运行条件

1. 为任务准备独立工作区，保存初始文件、已有修改及验证条件；保留正常项目规范。可以使用独立检出或文件快照，不在日常工作区反复重置。
2. 记录宿主及版本、模型、推理档位、工具和权限配置、项目指令、技能来源及实际安装路径。提交不能代表未提交内容时，保存完整技能包快照；按需记录文件哈希。
3. 按宿主的安装方式提供完整 `code-like-me` 包，保留 `SKILL.md`、`references/` 和宿主元数据；确认入口及引用资料来自实际副本。更新已有安装前核对目标、备份并保留扩展配置，不混用版本，也不留下多份同名技能影响来源判断。
4. 使用能够导出工具执行记录的方式运行。若宿主不提供技能加载内容或工具返回结果，提前记录这一限制，后续将无法证实的读取项保留为“未确认”。
5. 仅使用本次允许访问的系统和数据。验证外部失败、重投和回滚优先使用项目已有替身、沙箱或隔离环境；真实外部集成单独记结果。

可在初始工作区记录以下只读信息，输出保存在验收记录目录。它们用于固定起点，不能代替技能安装来源和文件快照。

```powershell
git rev-parse HEAD
git status --short
git diff --stat
git diff
```

检查初始行为时优先复用已有验证。若为变更任务，确认复现条件能区分修复前后；没有可执行检查时，先写清可重复的人工步骤。S07 等明确禁止运行测试的只读场景，不为了验收而让被测 Agent 跑测试。

比较两侧时，分别准备 `baseline` 与 `candidate` 工作区，初始项目、需求、检查和环境条件一致，只改变所比较的技能版本或配置。两侧各自开始新会话，不在同一会话切换技能，也不把第一侧修复后的文件交给第二侧。

## 3. 在独立新会话提交任务

在目标宿主中新建会话，定位到准备好的工作区，按日常使用方式提交请求。下列提示词是聊天输入，`$code-like-me` 保持原样。只填写需求和事实，不附本流程、观察答案或历史修复结果，也不额外要求 Agent 读取所有规范来“帮助通过”。

### 实现任务提示词

```text
$code-like-me

请在 <模块或文件> 修复 <具体问题>。
当前行为：<复现输入与实际结果>。
目标行为：<正常、边界和失败路径要求>。
保持 <接口、权限范围、返回、异常及副作用契约>。
必要上下文见 <项目内文件或已知事实>。
修改范围为 <范围>；保留工作区已有修改。
相关验证使用 <项目已有命令或步骤>。
```

例如，在已经准备好对应仓储和检查的实际项目中提交 S05：

```text
$code-like-me

修复 scoped.py 中 rename_rule 的单条更新参数错误：按 rule_id
修改当前租户规则的 name。ScopedRepo 在构造时绑定租户，get 和
rename 均统一过滤租户，保持该权限模型及当前返回、异常契约。
保留已有修改，不修改仓储 API。相关验证使用 python checks.py。
```

此示例的文件名和命令需要替换为实际项目内容；没有对应材料时，不能直接运行该提示词并据此判断场景通过。

### 只读任务提示词

```text
$code-like-me

只评估 <文件与方法> 的职责拆分和失败处理是否符合 <契约文件>，
结合必要调用上下文给出问题、依据和建议。先不修改文件，也不运行测试。
```

执行中保留完整对话和工具记录。Agent 提问时，按已有需求回答；若必须新增业务决策，记录新增输入，比较时让两侧获得等价信息。发现遗漏后发出的补充指令属于人工干预，应另记“干预后修复”，不能覆盖首次自主执行结果。

显式调用的验收使用 `$code-like-me`。需要验证隐式触发时，另开新会话，用同样的自然语言任务但不写技能名，单独记录实际加载来源；显式调用通过不能证明隐式触发有效。宿主未暴露来源时，触发结果也应保留未确认。

## 4. 收集实际证据

Agent 交付后，先保存最终产物，再由验收人核对。建议每次运行保留以下文件；这是记录目录示例，不要求引入自动化工具。

```text
<本次验收目录>/
  run-info.md           # 宿主、模型、条件、技能来源、起点
  task.txt              # 实际提交的完整请求及后续输入
  initial/              # 初始项目材料、已有修改及完整技能包快照
  session/              # 原始对话、技能加载及工具返回记录
  final/                # 最终文件、实际差异或只读评估
  verification.txt      # 验证命令、输出、退出状态及人工复现结果
  result.md             # 分项结论、依据和限制
```

归档前检查是否包含业务敏感内容或凭据，只保存必要的脱敏材料，不归档宿主认证文件或完整用户配置。原始失败、工具拦截和环境限制与成功结果一起保留。

### 核对实际读取

- 先确认实际使用的技能入口和版本。工具返回的正文或可核实的宿主加载内容才是读取依据；文件名、链接、读取命令及“已使用技能”的声明本身不足以证明完整加载。
- 查看整场会话，包括后续补读。记录“完整读取、局部读取、失败或截断后补齐、仍未确认”，不要仅看第一条命令。宿主已注入的内容应结合加载记录判断，不要求一定出现文件读取命令。
- 项目指令引用的规范、目标模块和必要调用上下文应实际读取。发现新影响而补读是正常行为；无依据的额外读取是效率问题，适用规范漏读是规则执行问题。

### 核对修改与验证

将初始与最终状态对照，检查目标实现、必要调用方、实际契约和检查输出。Git 项目可以查看 `git status --short`、`git diff`、`git diff --check`；新增文件还需打开核对，不能只查看已跟踪文件的差异。

检查功能、边界与失败路径是否符合任务卡，用户已有修改和操作范围是否保持，适用注释及规范是否实际落实。确认检查文件、正确断言和业务契约没有被改写来迁就实现。S07 核对文件未变及工具记录中没有测试执行；S08 对照原有修改及受限验证的交付说明。

查看 Agent 实际运行的验证是否覆盖影响且输出可确认。仅有成功声明、缺失输出，或一个汇总退出码掩盖前序命令失败时，不能直接记通过。已有结果足够时无需机械重跑；存在新变化、失败或具体疑点时，再检查受影响部分。只读场景以静态核对结论为依据。

## 5. 分项判定并填写结果

每项分别使用“通过、不通过、未确认、不适用”。通过必须有证据，不适用需有范围依据；受阻或未运行的适用项保留未确认并说明原因。不要把未确认当作通过计入成功率。

| 判定维度 | 要回答的问题 | 常见不通过或未确认情况 |
|---|---|---|
| 目标行为与契约 | 目标、边界、失败及受影响契约是否正确？ | 漏掉越权、回滚或异常路径；只验证正常流程。 |
| 适用规范落实 | 最终实现或评估是否符合当前适用要求？ | 功能正确但漏注释、重复防御、无职责拆分，或评估依据不足。 |
| 技能与规范加载 | 是否确认正确入口和适用规范已加载？ | 实际副本不明，规范漏读、失败或截断未补齐，宿主不暴露加载内容。 |
| 修改及操作范围 | 是否保护已有修改并遵守授权边界？ | 覆盖用户改动，无关重构，只读任务中改文件或跑测试。 |
| 验证与交付 | 验证是否充分且可确认，限制是否如实报告？ | 修改断言迁就实现，将模拟通过当作真实集成通过，隐瞒未验证项。 |
| 读取与执行成本 | 是否有可确认的无关读取或额外操作？ | 无依据全读，固定报告或重复检查；token、耗时数据不可取得。 |

不要求复述 Agent 的完整内部思考；实现决策可结合实际修改、项目依据及交付理由核对，不从未公开的思考过程推断通过。

目标行为或其他适用要求有不通过项时，不能判定该场景通过；存在适用项未确认时，只报告已验证范围。成本维度中的额外读取单独报告，不将它等同于功能失败，也不以成本下降抵消规则遗漏。全部所需维度有足够证据后，再给出限定于本场景、宿主和条件的结论。

S08 等专门检查限制报告的受控场景，可以判定“限制识别与报告通过”；真实 staging 集成本身仍为未确认，两项分开记录。

## 6. 需要比较或复验时如何继续

两侧先各自按上述流程判定，再比较结果。按场景并列记录功能与契约、规范、读取内容、修改范围、干预次数及交付限制；两侧各自的结论和原始失败都应保留。不要只比较最终回答长度。

能取得 usage 时，保留宿主原字段，注明输入、缓存及输出等口径。技能正文字符数按相同换行和去重方式单独统计，不换算为 token；也不把多轮累计输入 usage 当作技能正文大小。耗时注明起止点及并行、等待、环境失败等条件。无法取得的指标填缺失，不估算。

如需判断稳定性，运行前约定每项重复次数和汇总口径，每次均从独立新会话及相同初始状态开始，汇总全部成功、失败、受阻和未确认结果，不持续重试到通过。一次配对可说明本次差异，不能证明整体提速或未来不再漏读。

发现问题时记录场景、预期、实际结果、对应证据和影响，先区分技能表达、安装来源、Agent 执行、项目既有问题及环境限制。修改后固定新的版本和快照，在新会话复验受影响场景；规则表达变化可能影响其他主题时，再覆盖必要关联。复验记录关联原失败，不覆盖首次结果。
