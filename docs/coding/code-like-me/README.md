# code-like-me

## 做什么

在需求、项目规范和接口契约内应用个人编码偏好，保持职责清楚、主流程连贯和实现简洁。根据任务复杂度与实际风险选择分析和验证深度，减少机械拆分、无价值抽象、重复校验和掩盖失败的兜底。

技能采用一个入口与两份条件参考资料：通用流程、编码与设计偏好、注释、适用规则读取和完成判定集中在入口；数据与异常、Java 细节按任务内容补读，减少普通任务中的文件跳转。已有禁止项在各主题末尾以独立的“禁止项”小节呈现，加粗具体问题名称，正文说明错误行为、判断条件与例外，便于扫描和核对。

目前提供[中文技能包](../../../skills/zh-CN/coding/code-like-me/SKILL.md)，暂未提供英文版本，现行执行规范以技能包为准。

## 什么时候使用

通过 `$code-like-me` 显式调用，用于功能实现、缺陷修复，以及需要保持个人编码习惯的代码调整。

```text
$code-like-me
修复订单查询遗漏归档状态的问题，沿用当前模块的组织方式，保持返回结构不变。
```

也可以仅要求评估，不修改代码：

```text
$code-like-me
评估这个方法是否拆分过度，给出建议，先不改代码。
```

需求和设计明确时直接实现；缺失的事实优先从项目查明。只有影响正确性且无法自行判断的业务选择，才需要补充输入。

## 常见问题

- **简单修改也会进行完整设计吗？** 执行深度随影响调整，局部修改不要求分级报告或设计文档；少量代码涉及权限、事务或并发时，仍需检查对应风险。
- **怎样判断“像我一样”？** 参考当前模块多个一致且维护良好的实现，关注命名、职责、流程、注释等组织习惯。依据不足时遵循项目规范和语言惯例。
- **个人偏好与项目规范冲突怎么办？** 以用户明确要求和项目规范为先，个人偏好不能破坏业务正确性或必要保障。
- **没有设计方案也会做三问吗？** 会。三问用于任务中尚未明确的实现选择，不以存在设计方案为前提，也覆盖校验与规则调整；具体要求见入口“实现决策的三问”。分析由 Agent 内部完成，落实后简要总结理由、影响和验证结果，不要求用户逐项回答。
- **设计方案或用户已经明确要求了，还会重新论证吗？** 直接按要求落实，三问只处理未明确的选择，不用于自行否决或替换既定方案。
- **会强制增加接口、设计模式或测试吗？** 是否增加取决于当前职责、实际复用和验证需要，不为形式上的扩展性或测试数量增加内容。
- **其他编程语言能用吗？** 通用规则适用于各语言；Java 有补充资料，其他语言遵循项目约定和语言惯例，不引入无关 Java 规范。
- **每次都要读取全部资料吗？** 按任务选择适用规范与资料，普通局部任务不必无条件展开全部参考文件；资料能否复用及补读条件见入口的“适用规则与资料”。
- **怎样判断参考资料真的读过？** 查看会话中的加载内容或文件读取记录；入口中的链接和“已使用技能”的声明不能单独证明读取。检查时还要区分读过规则与实际执行了规则。
- **测试通过就算完成吗？** 还需核对适用规范和任务要求。未检查或依据不足的事项不能算通过，具体完成条件见入口。
- **个人偏好有独立文件吗？** 通用偏好和识别当前模块习惯的方法集中在入口，语言与运行时细节保留在对应资料中，避免多处重复维护同一规则。
- **简单分支也要写注释吗？** 本次新增或修改的业务分支需要说明业务场景、处理意图或原因；纯 NPE、数组越界等技术防护可豁免，具体范围见入口的“分支注释”。
- **字段注释会要求补齐整个项目吗？** 不会。新增或语义变化的业务声明是检查重点，已有准确注释可以保留，集中定义可引用；具体适用范围与例外见入口的注释主题。
- **Java 文档只检查位置吗？** 还检查适用声明的覆盖范围、内容和准确性；私有方法、继承文档和生成内容的处理边界见 Java 资料中的 Javadoc 主题。
- **只读复查会自动修改或运行测试吗？** 不会。按指定范围核对依据并报告实际发现，区分规则违反、可选改进和既有问题，也不要求交付完整内部清单。
- **更新仓库后安装副本会同步吗？** 不会。需核对安装位置、备份并保留扩展配置后，另行复制完整技能包；本次仓库改造不修改外部安装副本。

## 如何判断执行符合预期

可以在安装后的新会话中，用以下任务观察实际效果：

| 场景                             | 观察重点                                                               |
|----------------------------------|------------------------------------------------------------------------|
| 契约明确的局部逻辑修复           | 能否直接实施，避免无关阅读和冗长分析，并完成相关验证                   |
| 少量权限、事务或共享状态修改     | 是否识别实际风险，保留数据范围、回滚和并发保障                         |
| 单一实现或仅使用一次的处理步骤   | 是否避免空洞包装，同时保留有独立语义或改善主流程的合理拆分             |
| 契约允许空结果、恢复或降级       | 是否保留合法行为，同时正确传播真正的失败                               |
| 目标文件已有未提交修改           | 是否保留原有修改，最终差异只覆盖任务所需内容                           |
| 检查无法运行或执行失败           | 是否如实区分已执行、受阻和未解决事项                                   |
| 涉及职责调整或正在考虑新增抽象   | 是否在作出设计决定前应用入口中的设计规则，并依据真实问题判断           |
| 只有需求或设计未覆盖实现细节     | 是否依据已有约束使用三问作出必要且合理的选择，避免擅自补设业务要求     |
| 设计方案或用户已明确要求         | 是否直接落实，避免用三问重新决定是否执行或自行替换方案                 |
| 校验项与规则项调整存在未定选择   | 是否使用同一三问评估必要性、实际后果与方案合理性，并总结实际变更       |
| 普通局部修改与数据、异常处理修改 | 是否按实际主题选择资料，既不无条件全读，也不遗漏失败处理和运行时保障   |
| 项目指令引用了独立规范文件       | 是否实际读取并将适用要求纳入实现和复查，而非只检查技能入口             |
| 适用资料未加载或关键内容被截断   | 是否补齐必要内容；无法取得时如实保留限制，避免据此宣称检查通过         |
| 实际变更与最初计划存在差异       | 是否基于最终变更及必要上下文核对，而非按计划或修改记忆判定             |
| 功能验证通过但仍有规范遗漏       | 是否处理本次遗漏并复查受影响部分，避免用测试结果替代规范检查           |
| 检查依据不足或要求不适用         | 是否区分未确认与不适用，并为排除检查提供合理依据                       |
| 新增或修改业务分支及基础技术防护 | 是否为业务分支提供有实际含义的注释，并正确区分纯技术防护与业务判断     |
| Java 声明新增、语义变化或重写    | 是否正确判断 Javadoc 覆盖、完整性和继承文档的适用边界                  |
| 新增或语义变化的业务字段与枚举项 | 是否检查实际声明及必要使用点，准确说明业务含义和适用的单位、编码等信息 |
| 协议、平台模型与内部枚举编码不同 | 是否注明编码体系及转换依据，并引用已有集中定义，避免重复维护编码说明   |
| 用户仅要求只读复查               | 是否遵守只读范围，区分实际问题与可选建议，避免自动修改或运行测试       |

比较不同版本时，在相同宿主的新会话中使用相同任务，同时观察执行轨迹、结果、资料读取次数、耗时及可获取的 token
数据。以旧版为基线，确认减少文件跳转的同时没有遗漏适用规则；文件数减少本身不能证明执行更快或更可靠。

验收同时核对资料的实际读取、代码或复查结果，以及最终完成判定；找到部分问题或声明已遵循技能，均不足以证明适用要求已完整落实。可使用真实反馈构造不同任务，不只重复单一案例。

文件核对和场景推演只能检查规则表达与结构，不能证明宿主中的实际调用效果；后者需要在新会话中确认。文字指令仍依赖 Agent 执行，不能据此保证永不漏读或漏查。

## 维护说明

以下要求适用于本技能已有语言包及本使用说明，通用维护要求见根目录 [AGENTS.md](../../../AGENTS.md)。

- 按主题或执行流程组织内容，不拆成统一的“建议遵守”和“绝对不要”两大章。
- 普通编码任务共同需要的流程、偏好和核对要求集中在入口；仅将条件明确、能让无关任务免读的细节放入参考资料，不按执行阶段重新拆成多份必读文件。
- 先说明期望的代码形态与判断依据，再在对应位置明确禁止已观察到的错误，并就地写清适用条件和例外。
- 使用简短条目，一个条目表达一个主要判断；条件和例外融入对应句子，不使用“期望写法／禁止行为／适用边界”三段模板。
- 每个主题中已有的禁止项集中到该主题末尾的“禁止项”小节，先说明正向要求，再列出具体禁止行为；不跨主题汇总，不为没有禁止项的章节凑条目。
- “禁止项”条目加粗具体问题名称，如“**机械拆分**：”，正文描述可观察的错误行为与判断条件，不只加粗“禁止”二字。
- 禁止项优先描述代码形态、操作或结果，不以“不为……”等动机描述代替行为判断；确需表达目的条件时可以保留，不机械替换句式。
- 正向要求用于描述期望结果；禁止项用于约束容易反复违反的具体行为，不为每条建议机械配一条禁令，也不因假设中的问题不断追加禁止项。
- 将新反馈修订或合并到所属主题的现有规则，避免在文末堆积补丁或建立独立的反模式总表。同一问题集中说明，完成前清单仅作简短检查，不重复展开规则。
- 从实际反馈中提炼可复用的规则或执行机制；具体案例用于效果验收，不将每次遗漏转写为专用检查流程。
- 保留项目优先级、接口契约和必要保障；仅在确实没有例外时使用绝对措辞。
