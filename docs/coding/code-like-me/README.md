# code-like-me

## 做什么

先按用户指定、方案文档或上下文确定开发场景（功能实现与变更、缺陷修复、重构、性能优化或只读调查），由场景界定目标与改动授权，再由风险决定分析和验证深度。在需求、项目规范和接口契约内应用个人编码偏好，保持职责清楚、主流程连贯和实现简洁；减少机械拆分、无价值抽象、重复校验和掩盖失败的兜底。用类型和领域结构表达状态与约束，以读者负担衡量结构，并对量化结论保留基线与波动范围。

技能采用一个入口与五份条件参考资料。开发场景与改动边界、通用流程、编码与设计偏好、类型与领域建模、读者负担、注释、适用规则读取和完成判定集中在入口；运行时资料分为异常与日志、数据与事务、缓存与并发、资源与性能四组，Java 细节单独保留。场景决定目标与改动授权，风险决定分析与验证深度，两者叠加。入口直接路由，完整读取命中的主题文件，不依赖从合并文件中截取小节。内部清单简短提示关键检查项，三问结论与实际取舍在交付处简要说明。禁止项在各主题末尾集中呈现，说明具体错误行为、判断条件与例外。

目前提供[中文技能包](../../../skills/zh-CN/coding/code-like-me/SKILL.md)，暂未提供英文版本，现行执行规范以技能包为准。

## 什么时候使用

用于五类开发场景：功能实现与变更、缺陷修复、重构、性能优化和只读调查；场景由用户明确指定、方案文档或任务上下文确定。可通过 `$code-like-me` 显式调用；任务符合上述场景时也允许 Agent 自动触发，实际是否加载以宿主和技能配置为准。

```text
$code-like-me
修复订单查询遗漏归档状态的问题，沿用当前模块的组织方式，保持返回结构不变。
```

```text
$code-like-me
新增订单导出能力，方案只定了业务字段和权限范围；先定数据形状和接口，再按当前模块方式实现。
```

```text
$code-like-me
优化订单查询性能，目标是 P95 降到 200ms 以内；先记录基线，再按瓶颈路径改造。
```

也可以仅要求评估，不修改代码：

```text
$code-like-me
评估这个方法是否拆分过度，给出建议，先不改代码。
```

需求和设计明确时直接实现；缺失的事实优先从项目查明。只有影响正确性且无法自行判断的业务选择，才需要补充输入。

## 常见问题

- **简单修改也会进行完整设计吗？** 执行深度随影响调整，局部修改不要求分级报告或设计文档；少量代码涉及权限、事务或并发时，仍需检查对应风险。
- **最小改动会不会压住性能优化？** 不会。场景决定目标与改动授权，最小化只在场景边界内生效；性能场景中，测量确认的瓶颈路径允许结构性改造。
- **场景怎么判断？** 用户明确指定优先，其次方案文档（设计、需求、验收文档），再次任务上下文；以主要目标判断，不靠关键词。判断有歧义且影响授权时，说明采用的场景和依据，不要求用户逐项选择。
- **场景判断错了怎么办？** 按实际目标调整，并在交付中说明影响；不静默扩大或缩小授权。
- **会强制写设计文档或做多个原型吗？** 不会。只有没有先例且选择会影响结构时，才用最小成本比较两三个候选，选定后删除试验代码；方案已定或局部修改不要求。
- **重构和功能变更怎么区分？** 外部行为不变、只调整结构按重构；新增或改变可观察行为按功能实现。跨场景按依赖顺序组合，例如先修缺陷再优化性能。
- **性能优化可以改变外部行为吗？** 默认保持行为契约；任务明确授权变更时按授权处理。
- **怎样判断“像我一样”？** 参考当前模块多个一致且维护良好的实现，关注命名、职责、流程、注释等组织习惯。依据不足时遵循项目规范和语言惯例。
- **个人偏好与项目规范冲突怎么办？** 以用户明确要求和项目规范为先，个人偏好不能破坏业务正确性或必要保障。
- **没有设计方案也会做三问吗？** 会。三问用于任务中尚未明确的实现选择，不以存在设计方案为前提，也覆盖业务实现中的校验与规则调整；具体要求见入口“实现决策的三问”。分析由 Agent 内部完成，落实后简要总结理由、影响和验证结果，不要求用户逐项回答。
- **设计方案或用户已经明确要求了，还会重新论证吗？** 直接按要求落实，三问只处理未明确的选择，不用于自行否决或替换既定方案。
- **会强制增加接口、设计模式或测试吗？** 是否增加取决于当前职责、实际复用和验证需要，不为形式上的扩展性或测试数量增加内容。
- **会强制用状态机或复杂类型吗？** 不会。只有多个需要同步的状态标记或持续增长的分支才改为状态机、枚举或表；形态清楚、局部且短期不会增长的代码保持直白。record、sealed 等类型特性以项目和目标版本已使用为前提。
- **性能数字需要哪些信息？** 基线、运行次数、波动范围和限制因素；没有这些不声称提升或回归。
- **批量改动要写脚本吗？** 非平凡的机械批量改动先手工完成一个单元，再写可复跑的脚本或 codemod；少量显而易见的修改直接手工处理。
- **内部 API 变更要保留兼容层吗？** 无外部兼容要求且调用方能同批迁移时，迁移全部调用方并删除旧路径；存在外部兼容要求时按契约保留并说明范围。
- **其他编程语言能用吗？** 通用规则适用于各语言；Java 有补充资料，其他语言遵循项目约定和语言惯例，不引入无关 Java 规范。
- **每次都要读取全部资料吗？** 入口按任务直接选择主题文件，同一任务可以命中多份；单条数据访问、局部日志、消息和外部调用也按其涉及主题处理，不以风险低为由免读。资料复用及补读条件见入口的“适用规则与资料路由”。
- **怎样判断参考资料真的读过？** 查看会话中的加载内容或文件读取记录；入口中的链接和“已使用技能”的声明不能单独证明读取。检查时还要区分读过规则与实际执行了规则。
- **测试通过就算完成吗？** 还需核对适用规范和任务要求。未检查或依据不足的事项不能算通过，具体完成条件见入口。
- **个人偏好有独立文件吗？** 通用偏好和识别当前模块习惯的方法集中在入口，语言与运行时细节保留在对应资料中，避免多处重复维护同一规则。
- **简单分支也要写注释吗？** 本次新增或修改的业务分支需要说明业务场景、处理意图或原因；纯 NPE、数组越界等技术防护可豁免，具体范围见入口的“分支注释”。
- **字段注释会要求补齐整个项目吗？** 不会。新增或语义变化的业务声明是检查重点，已有准确注释可以保留，集中定义可引用；具体适用范围与例外见入口的注释主题。
- **Java 文档只检查位置吗？** 还检查适用声明的覆盖范围、内容和准确性；私有方法、继承文档和生成内容的处理边界见 Java 资料中的 Javadoc 主题。
- **只读调查会自动修改或运行测试吗？** 不会。按指定范围核对依据并报告实际发现，区分规则违反、可选改进和既有问题，也不要求交付完整内部清单。
- **更新仓库后安装副本会同步吗？** 不会。需核对安装位置、备份并保留扩展配置后，另行复制完整技能包；本次仓库改造不修改外部安装副本。

## 如何判断执行符合预期

验证 Agent 的实际任务表现时，按[实际场景验收流程](acceptance-workflow.md)准备任务卡、固定环境、启动独立新会话、收集证据并分项判定。流程包含 22 类场景、按需补充的边界、版本比较方法，以及可复制的任务提示词和结果表；可据此选择本次要跑的项目任务。

以旧版为基线，同时观察无关读取、输出长度、修改范围、耗时和可取得的 token 数据。先确认适用规则没有遗漏，再判断是否有改善；行数或读取次数减少本身不能证明执行更快或更可靠。找到部分问题或声明已遵循技能，也不足以证明适用要求已完整落实。

涉及性能或量化结论时，能看到基线、运行次数、波动范围和限制因素，而不是单次结果。

文件核对和场景推演只能检查规则表达与结构，不能证明宿主中的实际调用效果；后者需要在新会话中确认。文字指令仍依赖 Agent 执行，不能据此保证永不漏读或漏查。

## 维护说明

以下要求适用于本技能已有语言包及本使用说明，通用维护要求见根目录 [AGENTS.md](../../../AGENTS.md)。

- 按主题或执行流程组织内容，不拆成统一的“建议遵守”和“绝对不要”两大章。
- 开发场景与改动边界集中在入口，按“目标 + 改动边界 + 完成证据”描述；参考资料只补充条件细节，不重复场景规则。外部原则清单不照搬进包内，不要求交付时输出场景名或原则名。
- 普通编码任务共同需要的流程、偏好和核对要求集中在入口；仅将条件明确、能让无关任务免读的细节放入参考资料，不按执行阶段重新拆成多份必读文件。
- 先说明期望的代码形态与判断依据，再在对应位置明确禁止已观察到的错误，并就地写清适用条件和例外。
- 使用简短条目，一个条目表达一个主要判断；条件和例外融入对应句子，不使用“期望写法／禁止行为／适用边界”三段模板。
- 每个主题中已有的禁止项集中到该主题末尾的“禁止项”小节，先说明正向要求，再列出具体禁止行为；不跨主题汇总，不为没有禁止项的章节凑条目。
- “禁止项”条目加粗具体问题名称，如“**机械拆分**：”，正文描述可观察的错误行为与判断条件，不只加粗“禁止”二字。
- 禁止项优先描述代码形态、操作或结果，不以“不为……”等动机描述代替行为判断；确需表达目的条件时可以保留，不机械替换句式。
- 正向要求用于描述期望结果；禁止项用于约束容易反复违反的具体行为，不为每条建议机械配一条禁令，也不因假设中的问题不断追加禁止项。
- 将新反馈修订或合并到所属主题的现有规则，避免在文末堆积补丁或建立独立的反模式总表。同一问题集中说明，完成前清单仅作简短检查，不重复展开规则。
- 从实际反馈中提炼可复用的规则或执行机制；具体案例用于效果验收，不将每次遗漏转写为专用检查流程。
- 保留项目优先级、接口契约和必要保障；仅在确实没有例外时使用绝对措辞。
- 调整触发方式时同步 SKILL.md frontmatter 与 agents/openai.yaml；用户明确指定分宿主策略时除外，并在本说明记录理由。
