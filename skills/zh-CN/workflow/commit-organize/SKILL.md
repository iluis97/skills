# 提交组织

从工作区未提交的改动出发，识别变更单元、分组、生成信息，确认后逐组提交。目标是一次产出清晰的历史，而不是事后整理。

依据按优先级取：用户本次提示、当前会话已完成的改动、暂存区与工作区差异。

## 1. 收集与核对

- 查看 `git status`、`git diff --staged`、`git diff`，区分已暂存与未暂存内容。
- 用户已有提示时先与差异核对；提示与改动不一致，指出差异再确认，不按提示编造。
- 查看近期提交风格 `git log -n 20 --format='%s'`，沿用类型前缀、语言、是否带 issue 编号等习惯。

## 2. 识别变更单元

按目的归组，不按文件归组；同一文件的不同 hunk 可分属不同单元。

- 一条提交等于一个可独立说明的目的，不为凑数拆得过细；同一需求的不同阶段可分成多条提交，只要每条能独立说明，不把整个需求强行压成一条。
- 相关改动不拆散：接口与其调用方、字段与迁移脚本应属同一条。
- 机械改动（格式化、重命名、批量替换）单独成条。
- 测试与文档跟随其服务的变更；项目有不同惯例时从其惯例。
- 不为可编译强行合并；中间态不可编译属于正常取舍，说明即可。

## 3. 排序

依赖优先：配置与 schema → 核心逻辑 → 装配集成 → 接口与入口 → 测试与文档。每条提交在不看后续提交时仍能理解。

## 4. 出计划并确认

表格列出每组：序号、包含的文件或 hunk、提交信息、依赖关系。确认前不提交任何内容。

提交信息要求：

- 标题一句话说明做了什么，不加句号；正文写为什么、关键取舍与影响，没有可说的就不写。
- 简洁且完整：覆盖本次全部实质改动，包括配置、测试和文档，每个变更单元一句话；不逐文件罗列。
- 不写未验证的效果或未发生的改动；密钥、内网地址、个人信息不写入。

## 5. 执行

- 逐组 `git add` 后提交；需要按 hunk 分离时用 `git add -p`，新文件先 `git add -N`。
- 只提交计划内的内容，不夹带计划外改动。
- 检测到密钥、大文件、本地配置（`.env`、`*.local`、IDE 目录）时排除并提示，不静默提交。
- 同一 hunk 混有多个目的且无法干净分离时，说明取舍，由用户决定。
- 提交失败或被钩子拒绝时如实报告，不绕过钩子。

## 6. 校验与交付

- 工作区与暂存区清空，没有遗漏的改动；确有需要保留的未提交内容时明确说明。
- 每条提交的内容与计划一致，可用 `git show` 复核。
- 交付：提交列表（hash 与信息）、分组依据、无法干净分离的遗留项。

## 边界

- 不改写已有历史、不 force-push；整理历史时提示用户使用提交整理技能。
- 不修改代码内容，只决定改动进入哪条提交。
- 具体命令见 [references/commands.md](references/commands.md)。
