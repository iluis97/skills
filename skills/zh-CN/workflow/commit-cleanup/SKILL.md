# 提交整理

把一组提交整理成能独立说明、按依赖顺序排列的历史。只改历史组织方式，仓库内容在改写前后必须完全一致。

## 判断标准

看这组提交能否让人不看代码就说清每一步做了什么。不能，就属于以下一种或几种问题：一条提交混了多件事；一件事被拆成多次碎片提交；顺序与依赖倒置；提交信息无法说明变更。按问题选择操作，不逐条套用清单。

## 四种操作

- **拆分**：一条提交包含多个可独立说明的变更时，按变更单元重新提交，不按文件机械切分；同一逻辑改动可以跨多个文件。
- **合并**：只合并同一阶段内的碎片——WIP、typo、反复修补，以及净变更为零的提交（成对的 commit/revert 一并删除）。同一需求的多个阶段（如 schema、核心逻辑、装配、测试）各自可独立说明时保留为多条，不压成一条。
- **重排**：按依赖顺序排列，使每条提交在不看后续提交时仍能理解；基于错误基线的提交先 rebase 到正确基线。
- **改写信息**：提交信息说明做了什么和为什么，保留共同作者等归属信息。

## 三条硬护栏

- **先备份、后改写**：创建备份分支并记录改写前的树哈希；结束时 `HEAD^{tree}` 必须与记录值一致，不一致就停止排查，不推送。
- **共享历史默认不动**：已推送的远程分支、已合并进主干的历史、已发布 tag 指向的历史，未经用户明确确认不改写；确认后仍需单独确认 force-push。
- **检测到密钥或大文件立即停止**：不自行执行历史过滤工具；说明风险并给出后续建议。

## 执行顺序

1. 确认工作区干净，创建备份分支，记录树哈希。
2. 给出整理计划：每条目标提交包含哪些变更、顺序和提交信息；确认后再动历史。
3. 执行拆分、合并、重排或改写信息；冲突时停下核对，不猜测取舍。
4. 验证并交付。

## 验证与交付

逐级校验，前一级不通过就停止：

1. **内容一致**：`git diff <备份分支> --stat` 为空，且 `HEAD^{tree}` 与改写前记录值相同。
2. **序列对应**：`git range-diff <备份分支>...HEAD` 确认新旧提交一一对应；未配对的提交说明是合并、拆分还是删除。
3. **分组符合计划**：逐条 `git show --stat` 对照计划中的文件归属，确认没有改动落在错误的提交里。
4. **副作用**：检查 GPG 签名、tag 指向、作者与共同作者信息、空提交，如实报告。

交付说明：原提交数到新提交数、每条提交覆盖什么、未配对的提交如何处理、是否已 force-push、遗留问题。

## 边界

- 改写历史时不同时修改代码内容，否则无法用树哈希验证；顺带发现的问题单独提出。
- 不评价提交内容质量，那是评审的事。
