# 唯一任务记录

## 建立与定位

`start` 时以当前项目为工作区，检查项目指令和已有修改。默认位置为 `{项目根}/artifacts/dev-workflow/{任务名}/task.md`，任务名用简短字母、数字、点、下划线或连字符，不能包含路径跳转。

用户已指定记录位置，或项目已有适合本任务的记录时沿用，并在对话中明确其位置。已有同名任务先检查是否继续，不直接覆盖；确为新工作时选新任务名。

参考 [../assets/task-record.md](../assets/task-record.md) 创建记录，替换占位内容并按规模删减。只有一个权威记录；独立方案、交付说明、日志和截图按需创建，并在记录中引用，不另建一套流程状态文件。

记录不依赖脚本、Git 仓库或特定语言；存在 Git 时读取其实际工作区差异，无 Git 时按项目可用工具核对文件和成果。

## 最少保留的信息

| 内容 | 用途 |
| --- | --- |
| 用户目标、范围与约束 | 持有原始期待及当前已澄清含义，不用内部任务列表替代目标 |
| 当前规模与理由 | 解释采用的调研深度和组织方式，发现变化时修正 |
| 当前方案 | 保留关键选择、必要实施安排，复杂时引用独立方案 |
| 任务分工 | 每项任务的目标、责任方、依赖和完成条件，需接回时记真实执行者；派发时补充模型与思考强度的配置要求、实际提交或宿主确认依据及重要变化 |
| 待决问题 | 区分可继续查证、需要用户选择和外部阻塞 |
| 结果依据 | 关联实际成果、检查结果、必要证据和用户反馈 |
| 执行状态与下一步 | 已做什么、正在做什么、还缺什么、下一步为何如此 |

轻量任务可以几条内容完成，不检查标题数量、最少字数或固定 JSON 字段。表格、列表及其他格式按可读性选择。

## 维护方式

负责人维护权威记录，角色与子任务返回结果供整合，避免并发改写同一份记录。关键目标、方案、分工、待决问题或结论变化时及时更新，保留影响后续工作的变更原因和已失效结论，不抹去失败或把推断写成用户决定。

只记录有助于继续工作和判断结果的信息，不保存凭据、全量提示词、工具响应或流水账；证据按需另存并引用，任务记录本身不证明真实执行。

执行配置可在任务分工中用短句或表格记录，遵循 [roles.md](roles.md#简要派发说明)。配置要求不能代替实际调用参数，实际提交不能代替宿主确认；两个字段分别标明已知依据，无回报就保留未知，不从配置反填执行事实。配置变化保留原因，不改写之前的执行依据；不要求另建机器状态、请求文件或配置快照。

## 对话操作

- `status`：只读记录与必要现场，说明目标进展、当前工作、阻塞和下一步，不写记录或派发。
- `resume`：核对当前方案、成果、待决问题及仍在运行的执行者；现场变化就先更新判断，不能只凭旧“通过”继续。用户要求恢复已中止任务时核对剩余范围，不自动重做已有成果。
- `abort`：尽力取消可控执行者，保留已有成果，记录原因、剩余任务及无法终止的执行者；实际仍运行时不能声称全部终止。

这些是负责人执行的操作约定，没有同名 CLI。任务推进和门禁的完整程序规则尚未设计，首版不提供原子状态更新、自动依赖调度或自动恢复保证。
