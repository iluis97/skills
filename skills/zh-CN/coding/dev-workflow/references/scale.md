# 自动识别需求规模

规模用于匹配组织投入，不替代目标、风险或授权判断，也不用于降低交付要求。

## 判断与使用

负责人根据原始需求、已有上下文和适量阅读暂定规模及一两句理由。规划者调研后核对，发现新事实时调整。无需等待完整调研才初判，不单独建立规模分析任务或报告，不要求用户选档。

| 规模 | 判断依据 | 执行影响 |
| --- | --- | --- |
| 轻量 | 目标明确、影响局部、实现路径清楚、验证直接 | 简短规划，减少交接与独立产物，通常不拆子任务 |
| 常规 | 需要调研，有关联变更、局部取舍或一定验证成本 | 明确方案与验收依据，按需要委派和核验 |
| 复杂 | 目标或技术路径不确定，跨模块依赖多，取舍、风险或验证成本较高 | 深入调研，显式处理依赖，按成果分批实现与验证 |

综合考虑：

- 用户希望得到的结果是否明确，是否存在需要用户选择的目标差异。
- 影响是否跨模块或涉及公开契约、数据、权限、运行环境等重要边界。
- 能否直接复用已有实现，是否需要调查和比较技术路径。
- 工作之间的依赖、可并行性和整合成本。
- 要证明目标达成，需要哪些真实环境、工具、交互或人工体验判断。

文件数量仅是线索；单文件可能涉及复杂动效或重要契约，大量机械变更也未必需要复杂组织。

## 动态调整

规模、理由和变化原因写入唯一任务记录。新发现使任务变复杂时增加必要调研、分工或验证，变简单时合并不必要工作；保留已有成果，不清空记录或重启整套流程。

例如“改一个页面”若涉及整体观感、动效联动及交互，不能因单文件就判轻量；“调整多个文件的同一说明”若规则明确且无行为变化，也不因文件多就机械拆团队。

规模变化不意味着获得扩大任务范围、访问权限或额外外部写操作的授权。
