# 从用户目标核验成果

## 先确定需要证明什么

对照用户目标、当前方案及实际成果判断差距，再选择检查与证据。遵守目标项目约定，按影响检查相关契约和风险，不套用通用语言、数据库或服务端清单。

规划时说明怎样判断目标达到，核验时检查是否遗漏重要行为。结构存在、命令无报错和构建成功只是部分证据，不自动代表成果完整或体验合格。

普通检查保持清晰文本即可；目标较多或存在多人交接时使用稳定标识关联成果和依据，避免各任务重新降低验收要求。

## 看真实成果

- 核对实际改动及成果，而非只看执行者自述；按任务需要查看 diff、新文件、删除、运行结果和相关文档。
- 选择证明行为所需的最窄验证，复用项目已有工具和测试体系；只在行为与风险需要时补测试，不为流程形式新增框架或测试。
- 通过、失败、阻塞、未运行明确区分。环境不可用不能写成不适用，未执行不能说已经验证。
- 证据与当前成果相符；目标、方案、实现或运行条件变化时重新判断受影响的结论，可信且未受影响的依据可复用。
- 核验者综合局部结果及相互影响，不能只收集各任务“通过”。核心目标缺失不能改写为普通风险后宣告完成。

## 感知与交互目标

用户期待观感、自然度、易用性或动态表现时，先形成具体质量描述或参照，方案决策持续回指目标。需要用户作方向选择时展示可判断的预览，最终展示实际成果，不只给文字报告。

静态画面可以截图，动效及交互需运行观察、录屏、时间采样或合适的实际操作验证。截图不能单独证明动态联动，DOM 数量不能证明好看。

用户偏好及人工体验结论由用户作出，不能代写满意；缺少实际观察条件时明确未验证及影响。

## 反馈与交付

结果缺项交执行者补充，实现问题由实现者修复，方案问题交规划者分析，用户取舍由负责人沟通。修正与复核范围匹配，不机械重跑整套工作。

需要用户确认时展示具体选择或当前成果，已有明确决定与授权不重复询问。正常澄清不等同于批准，未回应或空反馈不能视为通过。

负责人根据核验事实和用户反馈给出整体结论。目标未达到时继续改进、协调目标变化，或如实说明未完成；方案、交付说明和证据按实际审阅及交付需要生成，不按固定文件数判断完成。

首版依靠执行者真实检查、负责人判断和任务记录维持连续性，不包含程序化门禁或证据失效引擎。
