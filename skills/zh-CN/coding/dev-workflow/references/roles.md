# 角色协作

## 执行配置

组织角色及派发前读取 [../assets/roles.json](../assets/roles.json)。该文件只管理模型与思考强度，职责以本文为准，不维护阶段、角色提示词路径或宿主类型注册表。

- `defaults` 提供缺省字段，`roles` 按 `owner`、`planner`、`builder`、`verifier` 覆盖；模型与思考强度分别解析。
- 主角色派发按“用户对本次任务的明确指定 → 目标角色字段 → defaults 字段”选择；选中 `inherit` 就继承直接委派者对应的实际配置，不再向下查找。字段缺失继续查下一层，两层都缺失时按继承处理。
- 可将角色的 `model` 改为宿主支持的具体模型名，各角色可以不同；`reasoning_effort` 使用对应模型和宿主支持的档位或 `inherit`。默认值是执行偏好，不是任务规模门禁。
- 局部委派默认继承直接委派者的模型与思考强度，不重新应用主角色配置；用户对该子任务有明确指定时按指定处理。明确安排新的主角色职责时才应用目标角色配置，不能仅凭“写代码”或“查资料”自动切换。
- 负责人代发时保留逻辑上的直接委派者；不能把代发主线程当成继承来源。无法实现时说明限制，不能静默改用根线程配置。
- Owner 由主线程承担，配置保持继承。主线程兼任其他职责时也沿用当前会话，不通过读取角色配置宣称已切换模型或思考强度；若配置要求与实际会话存在差异，应说明该差异。

实际调用、配置不兼容及上下文继承的处理见 [tasks-and-delegation.md](tasks-and-delegation.md#配置与宿主能力)。

## 简要派发说明

Owner 派发前用一句话说明角色、任务、模型和思考强度；此时使用“配置为”或“计划使用”，不提前宣称已启动。例如：

> 交给规划者调研现有实现并形成方案；模型：继承当前负责人，思考强度：high（计划使用）。

宿主实际返回执行者后，结合正常进度简述启动及配置依据：

> 规划者已启动；模型：继承（具体型号未回报），思考强度：high（已提交）。

模型和思考强度各自判断依据：仅有配置时称“配置要求”，真实调用中传入了覆盖参数才称“已提交”，宿主明确回报当前执行对应字段及来源时才称“已确认”。省略覆盖参数而无实际回报时称“继承（具体值未回报）”；句柄、模型自述或回答风格都不能证明配置生效。

子角色自行委派时也简要说明；Owner 仅汇总必要进展和配置变化，不重复播报。派发失败时报告失败，不称已启动；配置变化时补一句“原配置 → 新配置：原因”。正常进度不反复介绍身份，最终交付不默认附模型表。

配置要求、实际提交或确认依据、真实执行者及重要变化记在现有任务记录中；不额外要求请求 JSON、配置快照或执行日志文件。

## 负责人 owner

主线程承担。持续持有完整用户目标，判断当前工作与成果是否仍服务目标，而不仅是任务是否被标记完成。

- 将原始需求、上下文和已知约束提供给规划者，不先猜出完整需求。
- 按 [scale.md](scale.md) 判断和调整规模，优先采用用户主动说明，结合规划者等角色的事实建议决定组织投入，不要求用户选档。
- 可自行或委派查明沟通所需的局部事实；需综合影响、比较方案时由规划者负责。
- 提问前核对已有对话和可查事实，只把业务取舍、偏好、范围及验收选择交用户判断。
- 组织必要决定和授权，维护唯一任务记录，协调依赖、写入冲突、恢复与取消。
- 按 [progression.md](progression.md) 核对开始条件、任务结果和依赖，选择并执行下一步；等待时说明解除条件，不因一个局部阻塞停掉所有独立工作。
- 综合核验事实与用户反馈，给出交付结论；目标未达到时继续处理或明确说明差距。

## 规划者 planner

从原始需求开始参与，对“怎样实现用户目标”负责。主线程可以承担轻量任务的规划职责；常规和复杂任务优先独立规划，不按固定人数组织。

- 自主选择已授权范围内的资料、代码、调用链和参照物，无需逐文件审批。
- 区分事实、推断、技术疑点与用户待决事项；能查则查，需要取舍时向负责人说明依据与影响。
- 调研与澄清交替，复用上下文；新事实出现时修正方案，向负责人提供规模调整建议及依据，不自行定档。
- 综合事实，选择服务目标且符合项目约定的方案，说明必要变更、依赖、实施安排及验证方式。
- 对观感和交互目标给出具体质量描述或参照，不用结构数量替代体验要求。
- 可委派局部调查，仍须亲自综合分析、比较取舍和制定方案；不通过委派提前修改生产实现。

## 实现者 builder

对完整实现、整合与自检负责，可由主线程或独立 Agent 承担。

- 根据当前方案完成实际行为、必要测试与受影响文档，沿用目标项目的工程约定。
- 可委派有边界的模块、测试或文档工作，明确所有权，保留其他修改并复核整合。
- 自己把握核心实现判断和整体一致性，不能将整个职责原样转交后只转述结果。
- 发现实质方案问题交规划者分析，目标或授权选择交负责人沟通，不自行降标。
- 交回实际改动、结果依据和未解决问题，核验发现缺陷时按具体事实修复。

## 核验者 verifier

对真实成果与目标之间的差距给出独立判断。代码或行为变化使用未参与实现的执行者，纯说明性修改可自检并明确标注；不要把同一执行者换个名字称为独立核验。

- 依据用户目标、当前方案、真实成果和必要 diff 核对，不把实现者摘要当成结论。
- 选择能证明目标与风险的验证，检查证据充分性，区分未完成、未运行和通过。
- 可委派局部检查，但完整成果、交叉问题和最终结论由自己综合判断。
- 自己和参与核验的子任务执行者不得参与当前成果实现；发现问题反馈责任方，不自行修补后给自己批准。
- 需要用户体验判断的内容由负责人展示成果并取得用户结论，不能代写用户满意。

## 协作原则

四种职责保持明确，不要求四个固定 Agent。规模影响组织成本，不取消必要独立判断。没有独立执行能力时明确记录缺口及当前能完成的工作，不制造虚假派发或完成结论。

角色可以委派执行，不能转移综合判断与最终责任；需要继续拆分时交原委派者协调，避免无边界转派。
