# 角色协作

## 执行配置

组织角色及派发前读取 [../assets/roles.json](../assets/roles.json)。该文件只管理期望的模型与思考强度，职责以本文为准；委派方式按 [progression.md](progression.md) PR-17 由用户指定或默认子 Agent，不在角色配置中增加另一套方式默认值。

- `defaults` 提供缺省字段，`roles` 按 `owner`、`planner`、`builder`、`verifier` 覆盖；模型与思考强度分别解析。
- 主角色派发按“用户对本次任务的明确指定 → 目标角色字段 → defaults 字段”选择；选中 `inherit` 就以直接委派者对应的实际配置为继承要求，不再向下查找。字段缺失继续查下一层，两层都缺失时按继承处理；实际应用必须有宿主支持及依据。
- 可将角色的 `model` 改为宿主支持的具体模型名，各角色可以不同；`reasoning_effort` 使用对应模型和宿主支持的档位或 `inherit`。默认值是执行偏好，不是任务规模门禁。
- 局部委派默认继承直接委派者的模型与思考强度，不重新应用主角色配置；用户对该子任务有明确指定时按指定处理。明确安排新的主角色职责时才应用目标角色配置，不能仅凭“写代码”或“查资料”自动切换。
- 负责人代发时保留逻辑上的直接委派者；不能把代发主线程当成继承来源。无法实现时说明限制，不能静默改用根线程配置。
- Owner 由主线程承担，配置保持继承。主线程兼任其他职责时也沿用当前会话，不通过读取角色配置宣称已切换模型或思考强度；若配置要求与实际会话存在差异，应说明该差异。

实际调用、配置不兼容及上下文继承的处理见 [tasks-and-delegation.md](tasks-and-delegation.md#配置与宿主能力)。

角色职责独立于子 Agent 或 thread；业务上的直接委派者也不因 thread 由负责人技术代建而改变。thread 的创建默认、模型覆盖及思考强度能力见 [threads.md](threads.md)，子 Agent 见 [subagent.md](subagent.md)。没有原生继承或可靠显式传值依据时不能称继承成功；具体值仅在工具支持且授权允许时提交。期望配置无法应用时依 PR-02 处理，用户已有接受宿主默认或其他替代的明确授权时可在其范围使用并记录，不能将选择 thread 等同于忽略角色配置。

## 简要派发说明

Owner 派发前用一句话说明委派方式及来源、角色、任务、模型和思考强度；此时使用“配置为”或“计划使用”，不提前宣称已启动。例如：

> 按默认子 Agent 交给规划者调研现有实现并形成方案；模型：继承当前负责人，思考强度：high（计划使用）。

宿主实际返回执行者后，结合正常进度简述启动及配置依据：

> 规划者已启动；模型：继承（具体型号未回报），思考强度：high（已提交）。

模型和思考强度各自判断依据：仅有配置时称“配置要求”，真实调用中传入了覆盖参数才称“已提交”，宿主明确回报当前执行对应字段及来源时才称“已确认”。省略覆盖参数且宿主有原生继承语义但无实际值回报时称“继承（具体值未回报）”；连继承语义也无依据时称“宿主默认（具体值或来源未确认）”，并说明采用该默认的授权。句柄、模型自述或回答风格都不能证明配置生效。

子角色自行委派时也简要说明；Owner 仅汇总必要进展和配置变化，不重复播报。派发失败时报告失败，不称已启动；配置变化时补一句“原配置 → 新配置：原因”。正常进度不反复介绍身份，最终交付不默认附模型表。

方式及来源、配置要求、实际提交或确认依据、真实执行者及重要变化记在现有任务记录中；不额外要求请求 JSON、配置快照或执行日志文件。

## 负责人 owner

主线程承担。持续持有完整用户目标，判断当前工作与成果是否仍服务目标。推进条件统一见 [progression.md](progression.md)，本文件定义职责与配置，不另设停止或放行条件。

- 将原始需求、上下文和已知约束提供给规划者，不先猜出完整需求。
- 按 [scale.md](scale.md) 采用用户说明或判断规模，并落实相应工作深度；结合事实建议调整组织安排，不要求用户选档。
- 可自行或委派查明沟通所需的局部事实；需综合影响、比较方案时由规划者负责。
- 提问前核对已有对话和可查事实，只把业务取舍、偏好、范围及验收选择交用户判断。
- 按 [clarification.md](clarification.md) 判断需求是否足以规划：清晰要求直接沿用，关键未决事项组织讨论；按用户授权衔接 `grilling`，内部方案审查不冒充用户认可。
- 方案经 PR-05 检查就绪后，必须主动通知用户并组织验收，提供当前方案及讨论入口；按 PR-19 核对明确认同后才放行相关实施。子 Agent 规划承接用户讨论并转交反馈；规划 thread 允许用户直接讨论和认可，核对接回后不要求重复确认。持续持有通知、核对和放行责任，不能转给规划者自行宣布。
- 组织必要决定和授权，维护唯一任务记录，协调依赖、写入冲突、恢复与取消。
- 登记任务与 Agent ID 或 thread ID 的关联；接回工作 thread 的用户介入，更新跨任务影响。用户暂停或接管的范围不自动续跑，归档不作为终止依据。
- 按 [progression.md](progression.md) 核对开始条件、任务结果和依赖，选择并执行下一步；等待时说明解除条件，不因一个局部阻塞停掉所有独立工作。
- 接回时判断接受范围、依据、未解决问题及责任方，同步记录后实际执行下一步；等待和交付分别适用 PR-12、PR-13，报告差距不代替继续处理。

## 规划者 planner

从原始需求开始参与，对“怎样实现用户目标”负责。主线程可以承担轻量任务的规划职责；常规和复杂任务默认独立规划，已有充分方案可复用并复核，不按固定人数组织。

- 自主选择已授权范围内的资料、代码、调用链和参照物，无需逐文件审批。
- 区分事实、推断、技术疑点与用户待决事项；能查则查，需要取舍时向负责人说明依据与影响。
- 用户描述清晰时沿用并补充工程安排；存在关键未决选择时先交回初步方向和讨论材料，不将假设直接定稿，也不要求用户决定普通技术细节。
- 调研与澄清交替，复用上下文；新事实出现时修正方案，向负责人提供规模调整建议及依据，不自行定档。
- 综合事实，选择服务目标且符合项目约定的方案，说明必要变更、依赖、实施安排及验证方式。
- 检查关键参数、单位、联动关系及验收条款是否一致，明确自由裁量边界；交回验收方法、事实依据、假设及未决事项，供负责人按 PR-05 接收。方案冲突由规划职责消解，不留给实现或核验事后解释。
- 按 PR-19 配合方案验收和修订：子 Agent 将讨论材料交负责人，规划 thread 可直接与用户讨论。交回当前方案内容引用或版本、调整落实情况及实际用户反馈来源，区分待验收与明确认同；不以自己报告“用户已同意”代替负责人核对，不自行派发依赖未认可方案的实现。
- 对观感和交互目标给出具体质量描述或参照，不用结构数量替代体验要求。
- 可委派局部调查，仍须亲自综合分析、比较取舍和制定方案；不通过委派提前修改生产实现。

## 实现者 builder

对完整实现、整合与自检负责，可由主线程或按 PR-17 选定的独立执行者承担。

- 根据当前方案完成实际行为、必要测试与受影响文档，沿用目标项目的工程约定。
- 直接收到用户调整时按 PR-18 判断局部处理、跨任务通知或暂停，不以旧派发覆盖新指示，不自行更新整体权威记录。
- 核对交接的用户要求、工程选择、当前方案的有效认同范围和待决事项；缺少 PR-19 放行依据或依赖未明确且未委托的关键决定时反馈负责人，不以“规划已完成”、需求清晰或自主设计委托作为越过依据。
- 可委派有边界的模块、测试或文档工作，明确所有权，保留其他修改并复核整合。
- 自己把握核心实现判断和整体一致性，不能将整个职责原样转交后只转述结果。
- 发现方案参数、验收条款或可行性问题时反馈规划者分析；涉及目标或授权选择交负责人沟通，不自行降标。
- 交回实际改动、自检依据、相对方案的偏差和未解决问题，核验发现缺陷时按具体事实修复。

## 核验者 verifier

对真实成果与目标之间的差距给出独立判断。代码或行为变化使用未参与实现的执行者，纯说明性修改可自检并明确标注；不要把同一执行者换个名字称为独立核验。

- 依据用户目标、当前方案、真实成果和必要 diff 核对，不把实现者摘要当成结论。
- 读取 [verification.md](verification.md)，选择能证明目标与风险的验证，交回逐项检查、证据范围、结论、遗漏及缺陷，按 PR-07 区分检查结果。
- 可委派局部检查，但完整成果、交叉问题和最终结论由自己综合判断。
- 自己和参与核验的子任务执行者不得参与当前成果实现；发现问题反馈责任方，不自行修补后给自己批准。
- 检查可观察的交互、联动及明显体验缺陷；真正需要用户作出的偏好或验收结论由负责人展示成果并取得，不能代写用户满意。

## 协作原则

四种职责保持明确，不要求四个固定 Agent 或 thread。规模影响组织成本，不取消必要独立判断。没有独立执行能力时明确记录缺口及当前能完成的工作，不制造虚假派发或完成结论。

角色可以委派执行，不能转移综合判断与最终责任；需要继续拆分时交原委派者协调，避免无边界转派。
