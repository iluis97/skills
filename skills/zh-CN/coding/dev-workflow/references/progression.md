# 围绕目标推进任务

首次开始、恢复任务，以及收到任务结果、用户反馈、失败或重要现场变化时读取。负责人按本规则决定下一步，委派者据此组织局部工作；角色职责、模型配置和核验方式仍以对应资料为准。

## 三个架构边界

- **规则指导判断，运行保障由真实机制提供。** Markdown 说明负责人如何判断和操作，不能替代进程管理、文件锁、权限控制或幂等机制。任务分工不等于文件已加锁，授权记录不等于权限已落实，记录过操作也不保证重复执行安全；需要这些保障时使用宿主或项目的实际机制，能力不足就说明限制并调整执行方式，不通过补写规则宣称已有保障。
- **任务状态记录结论，执行现场、成果和验收分别核对。** “已完成”是依据当前成果与必要核验作出的结论，不因执行者写入状态而成立。进程退出不等于成果正确，成果存在不等于验收通过，状态更新也不能证明进程已停止；依赖任务只能使用经必要核对且当前有效的成果。
- **负责人持续判断，任务列表随目标和证据调整。** 根据当前目标、有效证据及现场选择下一步，必要时补充、合并、重排、取消或重新打开任务，并核对依赖和授权；预先生成的计划不替代判断，局部任务全部通过后仍需判断整体目标，不能为完成清单而执行已失去必要性的工作。

## 1. 开始条件与推进判断

负责人每次依据当前目标、成果和现场作出判断，并执行下一项已授权且能推进目标的工作，不只更新记录或给出计划：

1. 核对目标及范围是否变化；已有决定继续有效，不因新消息机械重做澄清。
2. 检查新成果及已有依据，找出当前目标还缺什么；收到结果不等于接受结果。
3. 按问题性质选择补充调查、实现修复、方案调整、用户决定或环境处理。
4. 从满足开始条件的工作中选择下一步，能独立进行时才并行；完成后重新判断。
5. 满足整体完成条件则交付；需要等待时明确原因、解除条件和还能继续的工作。

开始一项任务前确认：

- 能说清本任务服务的目标、输入、边界、完成条件和责任方。调查任务允许目标仍有疑点，不要求全部需求澄清后才调查。
- 开始实现前按 [clarification.md](clarification.md) 核对关键决定依据：用户描述足以实施或已明确委托就直接推进；关键歧义和未委托的实质取舍先讨论。规划结果内部审查通过不能替代用户决定，待决方向不能因方案写完整就视为已认可。
- 必要前置成果已核对且仍适用，相关资料和执行条件可用；不能把执行者已返回或状态写成“完成”当作就绪依据。
- 操作在已有授权内，执行配置可用，写入范围和所有权清楚，不与运行中的工作冲突。需要用户决定的事项只阻挡依赖该决定的部分。

未满足就先解决缺口或记录等待，不跳过条件。确认只针对真实业务取舍、权限或成果，不为每项任务新增审批。用户只要求分析、设计或局部工作时，完成条件也限定在该范围内。

## 2. 结果检查与反馈

执行者交回实际成果位置、必要依据和未解决问题。委派者检查结果是否对应本次目标、范围和完成条件；负责人协调跨任务检查，行为变更按 [roles.md](roles.md) 安排独立核验，具体方法见 [verification.md](verification.md)。

- 能客观判断的内容核对实际文件、diff、命令及运行结果；记录未执行的检查，不用格式完整或退出码正常代替目标达成。
- 需要综合判断的内容由相应角色比较目标与真实成果；用户偏好、业务选择和必要人工体验结论交用户判断。
- 接回方案时区分内部质量审查与用户决定：用户已明确的内容不重复确认，仍待决定的部分标明为建议或假设，先讨论再用于正式实现；遵守用户先审阅或自主决策的具体要求。
- 反馈说清缺项、事实依据、影响及需要补充或修复的结果，不只回复“失败”或要求原样重试。
- 核对通过才把成果交给依赖任务使用；缺项结果保留待核对或待处理。已经核对且可独立使用的部分可以明确交接，不把整项结果伪标为完成。

目标、方案、实现或验证环境变化时，判断哪些旧结论及下游任务受影响。受影响的结论先标为需要复核，再安排相应检查；未受影响的可信依据可以复用，不强制每次重跑全部检查。不依赖哈希或版本引擎，记录成果位置、关键变化与复核范围即可。

运行中的任务若依据已失效，由负责人协调暂停、取消或更新边界；旧任务迟到的结果先核对是否仍适用，不能直接合并或覆盖新结论。

## 3. 问题分流与停止条件

| 问题 | 处理方式 |
| --- | --- |
| 返回结果缺项或证据不足 | 原执行者补充成果或依据，检查后再交接 |
| 实现不符合方案或存在缺陷 | 实现者修复，完成后重新核验受影响部分 |
| 方案不可行或遗漏重要目标 | 规划者分析并调整方案，负责人更新相关分工与依赖 |
| 缺少可查事实 | 自行或委派补充调查，不先把事实问题交用户决定 |
| 缺少业务选择、范围取舍或权限 | 负责人展示具体问题和影响，等待用户决定；其他独立工作继续 |
| 环境、外部依赖或执行配置不可用 | 核对真实原因，在已有权限内修复；不能解决则记录阻塞及解除条件，配置替代遵循委派规则 |
| 用户改变目标或取消工作 | 更新目标与适用方案，协调受影响任务和旧结论；只取消局部工作时保留其他有效任务，整个任务中止按第 6 节执行 |

修复后的成果实际交回，再启动针对新成果的核验，不能让修复与依赖该修复的核验同时启动、检查到旧成果。

重试前说明本次修正或重试依据，按问题、风险和宿主限制明确必要的次数、时限或其他停止条件，不全局固定重试次数。明确的瞬时故障可以有限重试；同样输入重复失败且没有新依据时停止原样重试，改为分析原因、调整方案或记录外部阻塞。正常澄清和用户反馈不计为失败重试，不以反复换模型代替问题分析。

## 4. 并行与依赖

- 为有关任务说明需要哪些前置成果，不机械给所有步骤编号或建立依赖图。存在循环或含糊依赖时由规划者澄清、拆分或调整方案，不能把任务全部挂起后停止分析。
- 需要多项成果时，全部相关成果核对有效后才开始；只有事先明确输入可互相替代时，才允许任意一项满足后继续，不能把多个必需结果当作任选一个。
- 无依赖且写入所有权不冲突的任务才并行；同一文件或共享资源存在冲突时划分边界、串行或先完成整合，不让执行者互相覆盖。
- 局部成果分别通过后，仍需检查整合结果和相互影响。整合导致行为变化时复核受影响内容，不直接沿用整合前的通过结论。
- 等待用户或外部条件时继续其他独立工作；若没有可执行工作，说明等待什么、由谁处理、怎样恢复，不空转派发或重复询问已有答案。

## 5. 状态与完成判断

用现有任务记录表达状态，按需要选用下列词语，不新增机器字段、固定任务卡或逐步落盘要求：

| 任务状态 | 含义 |
| --- | --- |
| 待开始 | 尚未执行，前置条件满足后可开始；返工时说明重新安排的原因 |
| 进行中 | 确实已经开始执行，需接回时关联真实执行者 |
| 待核对 | 成果已返回，必要检查尚未结束 |
| 待处理 | 依赖、用户决定、缺陷、环境或权限等阻挡推进，附原因与解除条件 |
| 已完成 | 本任务成果满足完成条件，依据已核对且当前有效 |
| 已中止 | 已决定不继续，保留原因、成果和现场；仍运行的执行者单独披露 |

任务完成可以因相关变化重新打开，说明原因并保留旧依据及失效情况。“待处理”不等于失败，“已中止”不证明进程已全部终止；检查本身仍区分通过、失败、阻塞和未运行。

负责人交付前核对整体目标，而非只统计任务状态：

- 当前约定范围内的成果实际存在，目标有对应依据，相关整合和必要验证已完成，结论适用于当前成果。
- 没有影响本次交付的未决问题、必要检查或必需依赖；不得自行删除目标、降低标准或把关键缺失列为风险后宣称完成。
- 需要用户选择或验收的事项已有针对具体内容的明确结论；已有有效确认不重复索取，不把未回复、空反馈或无关回复当作批准。
- 已处理或明确安排剩余执行者，不留会继续改变本次已核验成果的失控写入；交付说明实际结果、验证及重要限制，产物按需提供。

目标未达成时继续有依据的工作；确需用户或外部条件才能继续时，如实报告已完成部分、差距及解除条件，不称整体完成。用户明确调整范围后按新约定判断，保留调整依据，不冒充原目标已经实现。

## 6. 恢复与中止

恢复时先核对任务记录、当前文件与成果、目标及授权、现有证据和真实执行者，确定哪些已完成、仍运行或需要复核，再选择下一项满足条件的工作。状态不明时先查询或查证，不重复派发可能写入同一范围的任务，不盲目重做已发生的外部操作。任务记录不能证明进程停止或操作未发生。

中止时停止新派发，尽力取消可控执行者，核对仍可能运行或写入的工作，保留成果与现场，记录中止原因、遗留影响及后续处理。取消请求已提交不等于已终止；无法取消、无法查询或仍在运行时明确披露，不能只改记录就称全部停止。中止不自动回滚、删除成果或撤销外部操作。

`status` 仅只读报告现场与记录差异，不借查询触发上述推进、修复或记录更新。`resume` 才核对后继续，`abort` 执行中止；操作及记录位置见 [task-record.md](task-record.md)。
