# 任务推进规则

本文件是开始、交接、分流、依赖、复核、等待、完成、恢复和中止的权威规则来源。首次开始或恢复时读取；收到成果、用户反馈、失败或重要现场变化时重新评估相关规则。规则编号用于引用和后续规则引擎映射，不表示固定阶段顺序。

## 判断输入与执行边界

负责人根据真实现场提供以下输入，保留必要依据；当前可以用文本记录，不要求 JSON、数据库或新增状态文件。

| 输入 | 含义及依据 |
| --- | --- |
| 当前目标与约定 | 原始要求、范围、规模及来源、完成条件、用户决定、自主决策授权和后续变更 |
| 工作与依赖 | 每项工作的目标、输入、边界、责任方、完成条件、必需或可替代的前置成果、写入范围 |
| 委派选择与控制 | 当前需求默认方式、任务或角色覆盖及用户依据；实际使用方式、Agent ID 或 thread ID、逻辑委派者、用户暂停或接管范围 |
| 当前成果与检查 | 实际成果位置、覆盖的目标、检查结果和证据、适用的成果与环境、尚未覆盖的部分 |
| 问题与影响 | 问题事实、性质、影响的目标及工作、责任方、处理动作、解除条件或重试依据 |
| 执行现场 | 真实执行者及运行情况、配置依据、环境与权限、资源冲突、取消结果；查询不到的部分保留未知 |
| 用户结论 | 对具体选择、当前方案或成果的明确反馈及适用范围；方案内容引用或版本、负责人验收通知、认同来源及核对依据、待调整与失效范围，不能从一般对话推定 |

证据是否充分、方案是否自洽、问题属于哪类、变更影响哪些结论，由负责人及相应角色调查判断。后续引擎可依据这些有依据的输入评估允许动作，不能从文件存在、状态文字、执行者自报或进程退出推定成果正确。

条件判断区分**成立、不成立、未知**。成立表示命中本条处理动作，不代表任务成功；不成立和未知分别按本条对应分支处理，例如 PR-09 不受影响时复用旧依据、PR-11 已同步时不重复写入。对开始、交接和完成的必需条件，只有成立才满足门槛；不成立安排修正，未知先补充调查或核对，两者都只阻挡依赖该条件的工作。

所有并列必需条件都成立才放行；替代条件只有事先明确可替代时才能任选其一，有多个必需替代组时每组均须满足。不存在的依赖、关键待决或交付验收要求不构成缺口，但其不存在也应以当前任务事实为依据，不能把未查明当作不存在。方案用户验收统一适用 PR-19，不能以没有额外交付验收要求为由省略。

任务状态沿用：待开始、进行中、待核对、待处理、已完成、已中止。检查结果分别为：通过、失败、阻塞、未运行。任务状态、检查结果、用户结论和执行者运行情况分别判断；“待处理”说明原因及解除条件，“已中止”不证明执行者已停止。

Markdown 规则不提供进程管理、文件锁、权限隔离、幂等或原子状态更新。实际操作使用宿主或项目能力；无法查证操作是否发生时先查证，不能假定可安全重放。

## 事件处理次序

1. `status` 只适用 PR-15；`abort` 优先适用 PR-16，停止新派发。任何工作入口收到用户暂停或接管时，先按 PR-18 停止相关自动推进。
2. 用户改变目标、重要现场变化或旧结果迟到，先按 PR-09 判断旧依据是否仍有效；恢复先按 PR-14 核对现场。跨 thread 介入按 PR-18 核对来源及影响，方式选择或切换按 PR-17 处理。
3. 接回成果按 PR-04、PR-05 核对并按 PR-06 分流；方案就绪或收到相关反馈时评估 PR-19，负责人主动通知用户验收。向用户取决定前核对 PR-03，涉及检查结论时适用 PR-07。
4. 按 PR-11 同步关键记录，再由 PR-01 选择下一项工作；开始前同时满足 PR-02、PR-03、PR-08，依赖方案的实施及后续执行还须满足 PR-19，重试还适用 PR-10。
5. 准备等待或交付时分别评估 PR-12、PR-13。拒绝开始、交接或完成的条件优先于相应允许动作；不能用其他规则的局部通过覆盖缺口。

## PR-01 持续推进

- **触发事件**：开始、恢复核对结束、成果接回、反馈、失败或重要变化处理后。
- **判断依据**：当前目标与差距、有效成果、问题及依赖、已有授权、执行现场。
- **成立条件**：当前范围内仍有必要且具备开始条件的工作，包括调查、修复、补证据或处理环境。
- **处理动作**：负责人选择并实际执行下一项工作；不能只汇总报告、更新状态或提出下一步后结束。已运行的工作按需接回，不重复派发。
- **不成立或未知**：先调查无法判断的条件；目标已达成评估 PR-13，否则评估 PR-12，不能把披露差距当成继续执行的替代选项。
- **结果影响**：保持目标驱动的执行循环；新建议仅在影响约定目标、质量或必要验证时纳入当前必需工作，避免无限打磨。

## PR-02 开始条件

- **触发事件**：开始一项调查、规划、实现、核验或其他实际工作前。
- **判断依据**：工作与依赖、当前约定、规模对应的必要准备、所需工具和技能、权限、配置及写入现场。
- **成立条件**：目标、输入、边界、责任方和完成条件清楚；相关前置成果有效；依赖方案的实施及后续执行已满足 PR-19；规模要求已落实为相应准备；工具及必需技能可用并按要求使用；操作已获授权；PR-17 选定方式及配置可用、写入无冲突且未处于 PR-18 的用户暂停或接管范围。调查可用于澄清疑点，不要求先形成完整方案。
- **处理动作**：自行执行或派发任务，提供适用约束及规则；只有真实开始后才记录进行中。执行配置按用户指定及已解析的角色配置提交。
- **不成立或未知**：补齐输入、准备或能力，协调冲突；不支持的配置按用户已有替代授权处理，否则暂停受影响派发，不静默换模型、降档、忽略覆盖或改由主线程代做。
- **结果影响**：只阻挡不具备条件的工作。披露必需技能、独立核验或能力缺失，不代表相关要求已经满足。

## PR-03 用户决定与授权

- **触发事件**：规划、开始依赖关键决定的工作、请求用户选择或处理用户反馈时。
- **判断依据**：用户描述、明确反馈、项目规范、相关自主决策委托、待决问题及其影响。
- **成立条件**：相关决定已明确或属于已有委托；没有依赖尚未解决的实质选择；用户要求先审阅的内容已取得对应结论。
- **处理动作**：沿用已有决定，工程细节在授权内处理，不重复确认；自主设计委托及一般执行授权不能替代 PR-19 对当前方案的明确认同。
- **不成立或未知**：可查事实先查、工程矛盾先内部处理；真实目标取舍、偏好、范围或权限缺口由负责人展示具体材料和影响，取得用户决定。未回应、空反馈、取消提问或无关回复均不算批准；负面反馈按事实进入 PR-06 或 PR-09。
- **结果影响**：等待仅阻挡依赖该决定的工作；用户满意不能代写。需要其他手动技能时按已有显式授权使用，未授权不隐式读取或调用。

## PR-04 成果接回与交接

- **触发事件**：执行者返回调查、方案、实现、核验或修复成果。
- **判断依据**：本次完成条件、实际文件或运行结果、证据覆盖范围、未解决问题；thread 成果还核对相关新增消息及用户变更，适用时包含 PR-05、PR-07、PR-18 的判断。
- **成立条件**：准备交接的成果满足对应完成条件，必要依据已核对且当前有效。
- **处理动作**：明确接受的成果及可用范围；任务全部条件满足才记已完成。把已核对成果及约束交给依赖工作。
- **不成立或未知**：返回后先记待核对；缺项、矛盾或证据不足按 PR-06 处理，不直接接受执行者的完成声明。
- **结果影响**：部分成果可独立使用时明确交接其范围，剩余部分继续处理；依赖方案的使用还须满足 PR-19，不能以部分接收绕过验收。不得把整项或整体任务伪标为完成。按 PR-11 同步后继续 PR-01。

## PR-05 方案接收

- **触发事件**：接回新方案、调整方案，或复用既有方案用于相关实现前。
- **判断依据**：原始目标、用户决定、事实与约束、方案关键关系、验收依据、可执行的验证方法及规模要求。
- **成立条件**：覆盖相关目标；关键参数、单位、行为及依赖关系自洽；验收要求与自由裁量边界一致；必要验证可执行或已有明确补齐安排；待决方向与已定工程选择分清。
- **处理动作**：接受方案内部质量判断，明确可提交用户验收的内容及范围，交由负责人按 PR-19 主动通知并组织验收；不据此启动实现。
- **不成立或未知**：参数失配、规则冲突、重要遗漏或验证方法不足交规划者查明并修订；不得事后挑选有利条款放行。修订涉及未授权目标取舍时另适用 PR-03。
- **结果影响**：内部审查通过只表示可提交用户验收，不代表用户认可或实施放行。方案部分独立且质量合格时可按该范围提交验收；更新方案后按 PR-09 处理受影响结论。

## PR-06 问题分流

- **触发事件**：发现缺项、失败、矛盾、用户异议或执行障碍。
- **判断依据**：实际问题、原因分类、影响范围、责任方及已有授权；问题的重要性依据约定目标与必要验证判断。
- **成立条件**：问题性质及受影响工作已有事实依据。
- **处理动作**：按下表安排具体处理，写清应修正的结果；不能只标为风险或把工程问题转成用户偏好。
- **不成立或未知**：先调查原因，保留未知；不能仅按发现问题的角色、实现者自述或主观严重度归责。
- **结果影响**：影响完成条件的问题保持未解决，直到修正并核对或用户明确调整相关目标；不影响约定交付的建议可另列，不阻挡完成。

| 问题性质 | 责任方与动作 |
| --- | --- |
| 交回成果缺项、必要证据不足 | 原执行者补充；证据适用范围不明时由核验者查明 |
| 实现不符合有效方案、行为有缺陷 | 实现者修复，交回后核验受影响内容 |
| 方案不可行、关键参数或条款冲突、目标或验证设计遗漏 | 规划者分析修订；不得仅因影响轻微跳过处理 |
| 可查事实缺失、原因不明 | 负责人自行或委派调查，查明后再分流 |
| 未委托的业务选择、偏好、范围取舍或权限 | 负责人按 PR-03 组织用户决定 |
| 环境、依赖、工具或配置不可用 | 已有权限内处理；不能解决时明确阻塞及解除条件 |
| 用户改变目标或取消工作 | 分别按 PR-09 更新或 PR-16 中止；局部取消保留其他有效工作 |

## PR-07 检查结论与证据

- **触发事件**：接回检查结果、接受证据或汇总核验结论。
- **判断依据**：每项必要完成条件、实际执行的检查、证据覆盖范围、当前成果及环境、必要的核验独立性。
- **成立条件**：对应行为有充分有效证据，检查确实执行，必要的独立核验已落实；没有把推断当作实测。
- **处理动作**：仅将证据覆盖的行为记为通过；按整体目标检查遗漏及相互影响。
- **不成立或未知**：已查明不符合记失败；条件阻挡检查记阻塞；未执行记未运行。一个条目包含多个行为而证据不同时拆分结论，不能写“通过（部分推断）”；失效旧结论保留历史但不参与当前通过判断。
- **结果影响**：必要项失败进入修复，必要项阻塞或未运行进入补查或环境处理；均不能支持整体完成。替代验证只覆盖已证明的部分，核验者选择方法和判断证据充分性。

## PR-08 依赖、并行与整合

- **触发事件**：启动依赖工作、安排并行、开始修复后核验或接受整合成果前。
- **判断依据**：前置成果、必需或替代关系、有效性、写入所有权、运行中的执行者及整合影响。
- **成立条件**：全部必需前置成果已核对有效；依赖方案的工作已满足 PR-19 对相关范围的验收要求；可替代输入的约定已满足；并行工作无前后依赖且写入所有权无冲突。修复后的核验使用已交回的新成果。
- **处理动作**：启动具备条件的工作；分别可用的局部成果按明确范围交接，整合后检查相互影响。
- **不成立或未知**：先协调边界、串行、整合或补齐前置成果；不让修复与依赖其结果的核验同时启动。循环或含糊依赖交规划者澄清，不能全部挂起后停止分析。
- **结果影响**：分工不代表资源已加锁；整合或新改动影响旧结论时适用 PR-09，不能直接沿用整合前通过结论。

## PR-09 变化、旧结论与迟到结果

- **触发事件**：目标、方案、实现、依赖或验证环境变化，用户局部取消，或旧任务迟到返回。
- **判断依据**：变化事实、原结论适用范围、下游依赖、运行中的任务和用户授权；包含工作 thread 中已核对的用户介入及 PR-17 的方式切换。
- **成立条件**：变化影响已接受成果、检查结论或正在执行的任务依据。
- **处理动作**：先将受影响结论标明需要复核，重开相应工作；协调更新、暂停或取消受影响执行者，安排必要的重新检查。改变已认同效果、范围、接口、交互、关键设计或验收标准的实质方案调整，使相关认同失效，修订后重新适用 PR-05、PR-19；已认可方案内的技术细节及修正实现偏差无需重新验收方案。迟到结果先核对适用性。
- **不成立或未知**：未受影响的可信依据继续复用；影响不明先调查，相关结论暂不支持放行。
- **结果影响**：记录变化与复核范围，不覆盖新成果、不抹去旧依据，不机械重跑全部流程。目标调整以用户有效决定为依据。

## PR-10 重试与排障边界

- **触发事件**：准备重试失败操作、修复或重新派发同一问题。
- **判断依据**：失败原因、新修正或瞬时故障依据、操作副作用、任务风险及宿主限制。
- **成立条件**：本次重试有新依据或属于可有限重试的明确瞬时故障，操作结果已查清，且未超过按本次问题说明的次数、时限或其他停止条件。
- **处理动作**：说明本次变化和边界，再执行重试；修复成果接回后重新核验受影响部分。
- **不成立或未知**：停止原样重试，先查证实际操作及原因，调整方案或处理外部障碍；没有新依据不能反复换模型或重复调用。
- **结果影响**：停止原样重试不等于整个任务停止；能调查或调整时继续 PR-01，确需外部介入才按 PR-12 等待。正常澄清不计失败重试。

## PR-11 关键记录同步

- **触发事件**：开始或恢复、接受或退回成果、发现交付问题、目标或方案变化、通知方案验收或收到相关用户结论，以及进入等待、完成或中止前。
- **判断依据**：本次已核对事实、接受范围、结果依据、未解决问题、责任方和实际下一步。
- **成立条件**：这些变化尚未反映在唯一权威任务记录中，或记录与已查明现场不符。
- **处理动作**：同步成果、证据、问题、责任方、任务状态及下一步；在依赖工作开始或最终报告前完成相应更新。退回与部分接受也记录范围和原因；当前方案内容引用或版本、负责人验收通知、用户认同的来源及适用范围、待调整或失效范围按 PR-19 同步；委派方式及执行者关联、跨 thread 已接回位置、待同步变更、用户暂停或接管情况一并记录。
- **不成立或未知**：已同步无需重复落盘；事实未查明保留未知并安排核对。记录不可写时先处理或沿用已获授权的位置，不另建竞争状态或假称已保存。
- **结果影响**：已完成状态须有对应成果和依据，不能保留“尚无成果”等失真占位；不要求逐工具调用记流水账，记录更新后仍按 PR-01 推进。

## PR-12 等待条件

- **触发事件**：准备因缺口结束当前执行并等待。
- **判断依据**：全部剩余必要工作及其阻挡条件、运行中的执行者、已有授权、合理排障边界。
- **成立条件**：用户明确要求暂停、接管或先审阅相关范围，或 PR-19 的方案认同尚未取得，或剩余工作确需用户决定、权限、外部条件，或在合理排障边界内无法解决且需外部介入，或必需成果仍由真实执行者运行中；同时已无其他可自行执行的必要工作。等待执行者时安排实际接回。
- **处理动作**：报告已完成部分、差距、具体等待对象、解除条件及恢复入口，不称整体完成；用户仅暂停局部范围时继续其他独立工作。
- **不成立或未知**：仍有可执行工作则继续 PR-01；能调查的未知先查明。轻微缺陷、已披露风险或某一局部尚未验收不能阻挡其他独立工作；不得以持续推进为由实施尚未通过 PR-19 的方案。
- **结果影响**：用户未回应保持对应事项未决，不重复索取已有答案；不能将无限重试包装成持续推进，也不能以报告差距替代授权内的处理。

## PR-13 整体完成

- **触发事件**：准备宣称当前约定范围完成或交付。
- **判断依据**：原始目标及有效变更、当前整合成果、必要检查、未决问题、必要用户结论及执行现场。
- **成立条件**：目标均有当前有效成果与充分依据；必要检查已通过；没有影响交付的未决缺陷、检查或依赖；必要用户结论已取得；没有仍会改变已核验成果的失控写入。必要用户结论包括 PR-19 的方案认同、用户明确要求审阅或验收、尚未解决的实质选择及交付约定要求的结论；仅分析且未产出设计方案时不增设方案验收。
- **处理动作**：同步记录后交付实际结果、依据和重要限制。仅分析、设计或局部任务按其约定范围判断，不扩展成实现。
- **不成立或未知**：继续 PR-01 或按 PR-12 等待；可分别说明技术核验情况和待用户结论，不将局部通过称为整体完成，不自行删目标或降标准。
- **结果影响**：文件齐全、任务全勾选、执行者全部退出或风险说明都不能替代成立条件。感知成果仍需展示；方案验收与最终成果验收分别判断，后者没有必要约定时不额外增设统一批准，也不代写用户满意。设计任务可先交付待验收方案，但未认同前不宣称验收通过或整体完成。

## PR-14 恢复

- **触发事件**：用户要求 `resume` 或恢复此前中断的工作。
- **判断依据**：唯一记录、当前文件及成果、有效证据、目标与授权、真实执行者及外部操作现场；沿用已记录的需求默认方式和任务覆盖，接回 thread 未读消息及用户控制变化，旧记录缺少方式时先核对现存执行者。
- **成立条件**：已核对哪些成果有效、哪些仍在执行、哪些需要复核；已核对当前方案与 PR-19 认同的对应关系；待继续工作满足开始条件且不会重复未知写入或外部副作用。
- **处理动作**：修正记录差异，按 PR-09 处理变化后进入 PR-01；恢复已中止任务时先核对剩余范围。
- **不成立或未知**：先查询或查证，未知执行者和未知外部结果不视为已停止或未执行，不重复派发冲突工作。
- **结果影响**：有效成果及同一方案的有效认同复用，不因恢复重做全部流程或要求重复验收；缺少认同或发生实质变更时适用 PR-19。无法查询时明确受影响范围及解除条件，按 PR-12 判断等待。

## PR-15 只读查询

- **触发事件**：用户要求 `status`。
- **判断依据**：记录与必要现场，可只读查询真实执行者和成果。
- **成立条件**：本次范围为查询状态。
- **处理动作**：报告目标进展、记录与现场差异、问题和下一步建议。
- **不成立或未知**：未查明之处如实说明，不用旧状态推断事实；用户要求继续时再适用 PR-14。
- **结果影响**：本次不适用 PR-01 的主动执行及 PR-11 的写入动作，不派发、修复或更新记录。

## PR-16 中止

- **触发事件**：用户要求 `abort` 或明确取消整个任务。
- **判断依据**：取消范围、真实执行者、仍可能写入的工作、成果及外部操作现场。
- **成立条件**：整个任务已被明确取消；局部取消按 PR-09 处理。
- **处理动作**：立即停止新派发，尽力取消可控执行者并查询结果，保留成果与现场，按 PR-11 记录原因、遗留影响和后续处理。
- **不成立或未知**：取消范围不清先澄清受影响部分；无法取消、查询不到或仍在运行时分别披露，不能称全部已终止。
- **结果影响**：任务可记已中止，但不冒充进程已停止；发送停止消息或归档 thread 均不证明执行终止。不自动回滚、删除成果或撤销外部操作，恢复需适用 PR-14。

## PR-17 委派方式选择与切换

- **触发事件**：准备独立委派、进一步拆分任务、恢复或用户调整委派方式时。
- **判断依据**：用户对任务或角色的明确指定、当前需求整体指定、已记录选择及范围、现有执行者、宿主能力和配置支持情况。
- **成立条件**：按“具体任务或角色指定 → 当前需求整体指定 → 默认子 Agent”确定方式；具体任务指定优先于角色覆盖，同一范围采用用户最新明确调整，选择来源清楚，方式和所需配置可用。新增局部任务未被具体指定覆盖时沿用需求默认方式，不因派发者所在 thread 自动继承方式；配置继承另按 roles.md。切换已运行工作时还须查明旧执行者及副作用，确认不会产生冲突写入。
- **处理动作**：无需询问默认选项，记录需求默认方式和覆盖，按需派发子 Agent 或 thread；允许角色、任务混合使用。后续修订优先继续已有适用执行者。切换时协调原工作，交接有效成果、约束和剩余工作，记录新旧执行者关联，不机械重做已完成部分。
- **不成立或未知**：选择冲突无法判断时只澄清受影响范围；方式、权限或配置不可用时报告具体缺口并处理独立工作，无已有替代授权不换方式、不静默主线程代做。旧写入是否结束不明时先查证，不启动相同范围的替代写入者。
- **结果影响**：方式与职责、规模及目标分别记录，不根据复杂度或用户可能想观察而自行改选。需求级新选择对后续委派生效；已有运行任务先评估影响，明确要求迁移的按本规则交接。选择 thread 不等于固定人数、自动开 worktree、自动归档或取消原有模型配置要求。

## PR-18 用户介入与跨执行者同步

- **触发事件**：任一工作入口收到用户新要求、暂停、取消或接管；负责人接回工作 thread 的新增消息或变更通知时。
- **判断依据**：用户实际消息及适用范围、执行者转述与建议的区别、当前成果和在途写入、与原派发的差异、受影响任务及待同步情况。
- **成立条件**：已核对介入来源和范围；存在应执行的局部指示、影响其他工作的变更，或用户暂停、取消、接管要求。
- **处理动作**：直接收到用户要求的执行者在相应范围遵循该要求，不以旧派发覆盖后续用户指示。局部且不影响其他依据的调整在职责内处理并交回；实质方案调整先按 PR-09、PR-19 处理，不将修改要求直接视为修订方案认同。跨任务目标、方案、接口或验收变化通知负责人，负责人按 PR-09、PR-11 更新有效依据并通知受影响执行者。暂停或接管先停止相关新增工作，核对已发生及仍可能进行的操作，其他独立工作按 PR-01 继续。
- **不成立或未知**：只有执行者转述、引用文本或不明来源时保留待核对，遵守宿主对跨 thread 内容的信任边界，不直接将其升级为用户授权。能核对就核对，必要时只澄清来源或范围；依赖未同步方向的工作暂不放行。
- **结果影响**：用户无需在各 thread 重复转述；通知发出不等于接收并应用，负责人接回实际消息及成果后再判断。方案认同还须满足 PR-19，不能凭执行者转述放行，也不要求已有效认同的用户再次确认。未明确解除的暂停或接管不自动续跑、催促或派发替代写入者；整体中止适用 PR-16。新 thread 不消除文件所有权、核验独立性或真实终止确认要求。

## PR-19 方案用户验收

- **触发事件**：方案或修订方案经 PR-05 内部检查就绪、收到方案相关用户反馈、恢复或准备开始依赖方案的实施及后续执行时。
- **判断依据**：当前方案内容引用或版本及范围、PR-05 结论、负责人验收通知、用户实际反馈及上下文、消息来源与核对依据、待调整内容、PR-09 对既有认同有效性的判断。
- **成立条件**：负责人已主动通知用户方案就绪并组织验收；当前方案相关范围经内部检查合格且取得可核对的明确用户认同，没有尚待落实的方案调整或影响该范围的实质变更。用户可在负责人主对话或规划者 thread 中认同；“可以了”“按这个做”“开始实现”等在上下文明确指向当前方案时有效，无需固定口令或重复回主对话确认。初始“开始改造”、需求清晰、自主设计委托、内部采纳或规划者自报均不替代对当前方案的认同。
- **处理动作**：方案就绪后负责人必须主动通知用户，提供当前方案、关键效果与取舍、验收依据及讨论入口，明确请用户验收。子 Agent 规划由负责人承接讨论和反馈；规划 thread 可由用户直接与规划者讨论，负责人仍负责通知、接回并核对方案和认同来源。核对满足条件后按 PR-11 记录认同的内容、来源、范围及依据，再放行相应实施和后续执行；已有同一方案的有效认同直接复用，不重复索取。
- **不成立或未知**：尚未通知则负责人先通知；未回应、空反馈、取消提问、无关回复或提出调整均不算认同。先讨论、修订并经 PR-05 检查，再请用户验收当前方案。仅有转述或跨 thread 来源不可核实时按 PR-18 查证，遵守宿主信任边界，必要时只请用户确认缺失的来源或范围。待认同期间可继续独立调查、解释、方案修订和用途明确的讨论预览，不能自行或后台委派实施未认可方案，也不能用后续核验或部分成果接收绕过门槛；无独立工作时按 PR-12 等待。
- **结果影响**：门槛适用于所有规模和两种委派方式；轻量方案可用几句话表达，无需独立文档。只放行已认同且独立可执行的范围；实质变更按 PR-09 使受影响认同失效并重新验收，方案内技术细节及实现纠偏不重复验收。方案认同不等于最终成果验收或扩大权限；仅分析、设计任务仍按原范围交付，不因此自动进入实现。
