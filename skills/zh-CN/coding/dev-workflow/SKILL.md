# dev-workflow

## 主旨与范围

持续持有用户目标，按需组织工作，以实际成果和有效证据判断是否完成。

先理解用户希望得到什么，再判断怎样才算达到、缺哪些信息、采用什么方案、如何组织执行与验证。流程和检查服务于目标，不从已有检查表反推或缩小目标。“好看、自然、好用”等要求要具体化并观察实际成果，不能替换成能运行、无报错或结构齐全。

仅在用户显式调用时使用。默认组织软件开发交付；用户只要求分析、设计或局部工作时按该范围完成，不擅自进入实现。遵守目标项目约定和已有授权，保留用户修改，不自动 commit、push、部署或扩大外部写入范围。

## 操作与任务记录

```text
$dev-workflow start <需求>
$dev-workflow resume <任务名或记录路径>
$dev-workflow status <任务名或记录路径>
$dev-workflow abort <任务名或记录路径>
```

这些是对话操作约定，不是 CLI：

- `start`：检查项目指令及相关上下文，建立唯一权威任务记录，开始调研与组织工作。
- `resume`：读取记录，核对实际成果、待决问题和仍在运行的任务，继续最近未完成工作。
- `status`：只读报告目标进展、当前工作、关键问题和下一步，不改记录或派发任务。
- `abort`：取消可控执行者，保留成果与现场，记录中止；无法取消或确认终止时明确披露。

首次执行或恢复前读取 [references/task-record.md](references/task-record.md)。默认记录位于 `{项目根}/artifacts/dev-workflow/{任务名}/task.md`，已有合适记录时沿用，不新建第二份状态。方案、交付说明、日志和截图按需生成，不强制固定文件数量。

首版采用负责人维护记录与判断的方式，不提供自动调度、程序门禁或自动恢复引擎，不能把记录更新当成机器校验通过。

## 推进规则

首次开始、恢复，以及收到任务结果、用户反馈、失败或重要现场变化时，读取 [references/progression.md](references/progression.md)。负责人依据当前目标和实际成果，决定并执行下一项满足条件的已授权工作，不只给出计划或更新状态；需要等待时说明原因、解除条件及还能继续的工作。

开始前核对目标、输入、边界、完成条件、有效前置成果与写入冲突。交回结果先核对再交给依赖任务；缺陷交实现者、方案问题交规划者、可查事实先调查、真实业务选择及权限交用户判断。修复后再核验新成果；没有新依据的重复失败停止原样重试。

多项必需前置成果均有效才继续，可替代输入需事先明确。相关变更使旧结论需要复核时重新打开受影响工作，未受影响的依据继续复用。整体目标、必要验证及需要的用户验收均满足后才宣称完成，不能以任务全部勾选代替目标达成。上述为指令层面的推进与门禁规则，按需记录，不新增固定阶段或全任务审批。

## 需求规模判断

用户可以主动说明需求规模，已明确描述时优先沿用；未说明时，由负责人根据原始需求、已有上下文及适量阅读判断 `轻量 / 常规 / 复杂`。看目标不确定性、影响面、依赖、取舍和验证成本，不只数文件，不要求用户选档。规划者提供事实及建议，规模由负责人统一判断和调整。

读取 [references/scale.md](references/scale.md)，把判断及简短理由写入权威记录。规模决定调研深度、分工和产物详略，不降低目标、必要验证或授权要求。发现变复杂时调整组织，不清空工作或另起一套流程。

## 四种职责

| 角色 | 核心责任 |
| --- | --- |
| 负责人 `owner` | 用户目标、沟通、授权、组织、记录与交付 |
| 规划者 `planner` | 调研事实、影响与取舍、方案、实施安排和验收设计 |
| 实现者 `builder` | 完整实现、必要测试与文档、整合和自检 |
| 核验者 `verifier` | 独立检查实际成果、证据充分性及目标达成情况 |

开始组织角色及派发前读取 [references/roles.md](references/roles.md) 和 [assets/roles.json](assets/roles.json)，解析目标角色的模型与思考强度。职责不等于固定 Agent 数量，不为角色齐全机械创建执行者；轻量任务可由主线程承担简短规划，常规和复杂任务优先独立规划。行为变更使用未参与实现的执行者核验，纯说明性修改可明确自检；能力不足时披露缺口，不冒充独立核验。

## 默认工作形态

### 明确

把原始需求、已有对话、资料入口和已知约束交给规划者，不要求先澄清完整。规划者自主查已授权范围内的资料、代码、调用链和参照物；负责人也可自行或委派查明沟通所需的局部事实。

调研与澄清交替：能查明的事实先查，业务选择、偏好和范围取舍由负责人依据证据询问用户，再反馈规划者。复用上下文，不把正常澄清算成失败重试。

形成与任务相称的目标、方案、必要实施安排和验收依据；需要用户决定时展示具体内容，已有明确决定与授权不重复确认。不设最少字数、固定章节或伪代码行数，不因难验证而降低目标。

### 实现

围绕方案完成实际成果、必要测试和相关文档，沿用项目工具与约定。局部工作可委派，复核后整合，不能只按“文件都改了”判断完成。发现方案问题交规划者分析，涉及目标或授权取舍时由负责人联系用户。

### 核验与交付

读取 [references/verification.md](references/verification.md)。从用户目标和真实成果判断差距，选择必要检查及证据；局部通过不等于整体成功，失败、阻塞、未运行如实说明。

实现问题修复后重新检查受影响内容；方案问题回到规划；用户目标变化先澄清。感知成果或用户要求人工验收时展示当前成果并取得用户结论。未达目标则继续改进或协调目标变化，不能用风险说明代替完成。

三种工作形态用于表达重点，不要求每次循环从头执行；按目标、依赖和现场判断下一步，关键记录及时更新。

## 任务与按需委派

读取 [references/tasks-and-delegation.md](references/tasks-and-delegation.md)。任务先说清**目标、输入、边界、完成条件**，再判断是否值得委派。无固定助理角色，四种主职责均可发起有边界的任务。

需要独立调查、不同能力或有效并行时才拆分，不因搜索、阅读和总结有多个步骤就创建多个 Agent。只传必要上下文，普通任务使用自包含消息，只有程序确需解析时才要求结构化输出。

主角色派发按字段采用“用户对本次任务的明确指定 → 目标角色配置 → defaults”；`inherit` 表示继承**直接委派者**。局部委派默认继承，不重新套用角色配置。主线程兼任职责不代表切换配置；宿主不支持时披露限制，不静默换模型或降档。

Owner 派发前简述角色、任务、模型与思考强度；真实启动后结合进度说明配置依据，区分配置要求、实际提交与宿主确认，细节保存在权威记录，正常进度不重复播报。委派者保留综合判断及最终交付责任，不能把完整职责原样转包。

## 执行边界

- 必要确认针对真实目标取舍、具体方案、授权或实际成果；正常对话、未回应和空反馈不能冒充批准。
- 判断实际成果与依据，不以格式、文件存在或执行者自报完成代替结果核对。变更后重新判断受影响的旧结论，不能机械沿用。
- 核对实际改动与任务范围，保留用户及其他执行者修改；写入冲突先协调，不通过重置或删除证据掩盖问题。
- 所需成果或验证未完成时如实记录，不宣称交付完成；记录本身不证明真实执行或用户确认。
- 不内置语言、框架或数据库专项规范。需要其他手动技能时提示用户显式调用；已有同时明确授权时按依赖使用，不重复询问或隐式加载。
- 对话重点说明目标进展、关键判断、阻塞和下一步；执行细节按需查询，不用身份表与固定报告占据交付。
