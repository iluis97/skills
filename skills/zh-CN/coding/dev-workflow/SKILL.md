# dev-workflow

## 主旨与范围

持续持有用户目标，按需组织工作，以实际成果和有效证据判断是否完成。先理解期待，再确定完成条件、缺失信息、方案、组织和核验方式。“好看、自然、好用”等要求需要质量描述、参照和真实观察，不能缩小成能运行、无报错或结构齐全。

仅在用户显式调用时使用。默认组织软件开发交付；仅分析、设计或局部工作按用户指定范围完成。遵守项目约定及已有授权，保留用户修改，不自动 commit、push、部署或扩大外部写入范围。其他手动技能按显式授权使用，不通过读取正文绕过调用限制。

## 操作入口

```text
$dev-workflow start <需求>
$dev-workflow resume <任务名或记录路径>
$dev-workflow status <任务名或记录路径>
$dev-workflow abort <任务名或记录路径>
```

这些是对话操作，不是 CLI。未指定操作但明确要求推进新需求时按 `start`；查询保持只读，恢复先核对现场，中止保留成果并确认可控执行者情况。

## 开始或恢复

1. 检查项目指令、用户原始要求、已有修改、授权及相关事实；查明必需工具和技能是否可用。
2. 读取 [references/progression.md](references/progression.md) 和 [references/task-record.md](references/task-record.md)。推进规则是开始、交接、分流、等待、完成和恢复中止的权威来源；按 PR-14 恢复，`status`、`abort` 分别适用 PR-15、PR-16。
3. 开始新任务时读取 [references/scale.md](references/scale.md)，将用户说明或负责人判断落实为工作准备与验证深度。“中等”对应“常规”，已有明确规模直接采用，不因单文件或实现简单静默削减投入。
4. 建立或沿用唯一记录，默认 `{项目根}/artifacts/dev-workflow/{任务名}/task.md`。方案、截图和日志按实际需要生成；精简产物仍要完成相应职责。

## 准备与组织工作

准备规划时读取 [references/clarification.md](references/clarification.md)。清晰要求直接沿用，工程细节在授权内处理；可查事实先查，未委托的关键选择提供讨论材料，不把假设直接用于正式实现。需求清晰或自主设计委托不省略 PR-19 的方案用户验收。需要可选 `$grilling` 时按已有显式授权衔接，缺失或未授权不隐式调用，普通澄清仍可继续。

组织角色及首次派发前读取 [references/roles.md](references/roles.md)、[assets/roles.json](assets/roles.json) 和 [references/tasks-and-delegation.md](references/tasks-and-delegation.md)。后续按角色及配置变化补读；同一任务已读且未变的资料不机械重复加载。

独立委派方式按 PR-17 选择：**用户对具体任务或角色的指定 → 当前需求的整体指定 → 默认子 Agent**。未指定直接采用默认，不新增选择提问；允许混合使用，未覆盖的工作继续采用需求默认方式。选子 Agent 时读取 [references/subagent.md](references/subagent.md)，选 thread 时读取 [references/threads.md](references/threads.md)，仅读取本次使用的方式。方式不决定任务数量，指定 thread 也不将每个步骤拆成独立任务。

| 职责 | 承担的工作 |
| --- | --- |
| 负责人 `owner` | 持有目标、组织、沟通、授权、主动通知并组织方案验收、接回判断、记录和交付 |
| 规划者 `planner` | 调研、方案、关键关系与取舍、实施安排及验收设计 |
| 实现者 `builder` | 完整实现、必要测试与文档、整合和自检 |
| 核验者 `verifier` | 独立观察真实成果、核对证据、检查目标差距及遗漏 |

职责不等于固定人数。常规和复杂任务默认独立规划，已有充分方案可复用并说明复核依据及有效用户认同；行为变更需要未参与实现的执行者核验，纯说明性修改可明确自检。主线程兼任不代表切换模型，缺少执行能力不代表相关要求已满足。

任务交代目标、输入、边界、完成条件，以及适用的规模、委派方式及来源、目标依据和必读角色资料；让执行者实际获得约束，不假定角色名或继承对话会自动带入规则。主角色按用户指定和配置解析模型与思考强度，局部委派的配置要求默认继承直接委派者；实际能否应用取决于所选方式及宿主，不能把新 thread 的默认值冒充原执行者配置。计划、实际提交和宿主确认分别说明。

用户可在工作 thread 中直接介入，按 PR-18 同步影响；暂停或接管的范围不自动续跑。方式不可用时不静默改为另一种方式；中途切换先按 PR-17 核对旧执行现场和有效成果，再交接。

## 执行与接回

按推进规则 PR-01 持续执行；开始条件、决定依据和依赖分别适用 PR-02、PR-03、PR-08。收到成果先按 PR-04 核对，方案还需 PR-05 的自洽与覆盖检查；缺项和缺陷按 PR-06 交责任方处理。

**方案经内部检查就绪后，负责人必须主动通知用户并组织方案验收；取得对当前方案的明确认同后，才可开始相关实施及后续执行。** 按 PR-19 核对认同的方案、来源和范围。子 Agent 规划由负责人承接讨论；规划 thread 可由用户直接讨论和认可，负责人核对接回后放行，无需用户回主对话重复确认。多轮调整后的“可以了”可按上下文认定；修改要求、未回应或初始开工指令不算当前方案认同。轻量方案无需独立文档；已有同一方案的有效认同可复用，实质变更重新验收受影响范围。

开始核验前读取 [references/verification.md](references/verification.md)，并让核验者读取。检查结论按 PR-07 处理；变化按 PR-09 复核受影响结论，重试按 PR-10 提供新依据和边界。执行者返回后同步关键成果与问题，再交给依赖工作。

负责人接回时说明接受范围、依据、剩余问题及责任方，随后执行实际下一步。已有可执行的必要工作时继续处理；等待方案认同期间可调查、解释和修订，不能后台实施未认可方案。局部待验收不阻挡其他独立工作。精简交接文字和文件，不省略核对与纠偏。

## 记录与交付

按 PR-11 在关键事件同步唯一记录，不逐工具调用记流水账。等待和完成分别依据 PR-12、PR-13，不以任务全勾选、文件存在或执行者自报判断达成。PR-19 的方案验收与最终成果验收分别判断；展示感知成果，团队先处理可检查的工程和体验问题，必要的用户选择或交付验收交用户判断；未回应不算通过。仅分析或设计的工作不因方案认同自动进入实现。

当前由负责人及执行者按 Markdown 规则实际操作，尚无自动规则引擎、强制门禁或运行保障。规则编号支持后续实现和验收引用，不代表已有程序化判断、文件锁或恢复机制。
