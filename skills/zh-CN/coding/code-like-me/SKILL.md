# code-like-me

## 核心目标与适用范围

专注于软件开发 Code 阶段，按照用户的个人编码习惯完成实现与必要验证。以当前问题为中心，以现有项目为基础，以业务正确性为底线，以理解成本衡量代码质量，并按实际影响控制修改和验证范围。

用户仅要求分析、建议或只读复查时，核对依据并按指定范围输出，不因此修改代码或运行测试。需求和设计明确时直接落实，不要求重新设计或逐步确认。

## 1. 规则优先级与关键约束

编码决策按以下优先级处理：

1. **用户明确要求**：当前任务的功能、实现约束、技术选型和修改范围。
2. **项目规范**：项目架构、技术栈、编码规范、接口契约和模块约定。
3. **相邻实现**：当前模块中正确、维护良好且与任务相关的稳定习惯。
4. **个人编码偏好**：项目没有明确约定时，采用本技能的组织方式与判断标准。

- 各层决策均需保证业务正确性、必要的安全约束和目标环境兼容性，语法、框架 API 和标准库用法符合项目目标版本。
- 默认保持既有参数、返回、异常、序列化和副作用契约；任务明确要求变更时，同步处理受影响的调用方、测试和兼容性。
- 区分强制规范、稳定的局部习惯与历史遗留问题，通用规则按目标语言的惯用方式实现。

### 禁止项

- **偏好越界**：禁止以个人偏好覆盖项目规范或必要保障。
- **盲目沿用**：禁止仅凭历史代码存在某种写法就继续采用，需判断其正确性和适用性。
- **跨项目照搬**：禁止直接套用其他项目的包名、框架、业务模型或技术选型。

## 2. 开始任务与读取上下文

先明确目标行为、已定方案、影响范围、需保持的契约及验收要求，检查工作区状态和目标文件已有修改。按业务复杂度、影响传播和失败后果安排分析、实现与验证：

| 任务情况                                     | 执行重点                                                   |
|----------------------------------------------|------------------------------------------------------------|
| 局部修改，契约清楚，无共享状态或外部副作用   | 阅读目标实现和必要上下文后直接修改，核对相关分支与边界     |
| 涉及业务分支、多个调用方或数据访问           | 梳理调用关系、正常与失败路径，核对数据范围和受影响行为     |
| 涉及接口变更、权限、事务、并发或跨系统一致性 | 先明确契约、依赖、状态变化和失败处理，再实现并验证关键风险 |

- 同时符合多种情况时保留必要检查；发现新影响或风险时调整深度。少量权限或事务代码也可能影响广泛，多个文件的机械修改不必因此引入架构设计。
- 围绕任务阅读项目规范、目标模块、必要调用方和测试；涉及版本或依赖能力时核对构建配置。先理解职责与依赖，输入、返回、异常或副作用变化时追踪受影响的上下游。
- 从当前模块多个一致且维护良好的实现识别命名、职责划分、流程、分支、集合转换、异常日志和注释习惯；相邻实现不一致时判断其组织意图与适用性，依据不足时遵循项目规范和语言惯例。
- 能从项目、调用方或契约查明的信息自行确认；仅在缺失信息影响正确性且无法判断时提问。
- 既定方案有实际问题时说明原因和影响，授权范围内的实现细节自行处理；改变未获授权的业务要求、接口或技术选型前先确认，其他独立工作继续。
- 只修改任务必需内容，保护用户已有修改；历史问题仅在影响当前任务时处理，扩大范围应与实现正确性直接相关。

通用流程、编码偏好与完成前核对均在本入口。按已识别的任务内容补读以下资料，与入口规则叠加应用，并在相关分析或修改前落实；出现新影响时补读对应主题。同一任务中已读取且未变化的资料无需重复读取。

| 读取条件                                                                           | 包内资料                                                                                                             |
|------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------|
| 涉及数据访问、事务、缓存、异常、日志、消息、外部调用、并发、资源生命周期或性能逻辑 | [references/data-and-exception.md](references/data-and-exception.md)：仅读取涉及主题，落实数据、失败处理与运行时保障 |
| 处理 Java 代码                                                                     | [references/java.md](references/java.md)：Java 专属规则；依赖相关规则仅在项目已使用对应依赖时生效                    |

其他语言遵循项目规范、语言惯例和本入口的通用规则。

### 禁止项

- **按修改量定深度**：禁止仅凭代码行数或文件数量判断执行深度，或因修改量小而省略已识别风险的必要检查。
- **流程形式化**：禁止将评分、分级报告或设计文档设为每个任务的固定前置步骤。
- **无关阅读**：禁止持续读取无法帮助确认需求、契约、影响或编码习惯的文件，或凑足固定阅读数量。
- **偏好误判**：禁止从单个特例、生成代码或其他作者代码推断用户偏好，或脱离职责和组织意图机械模仿外形。
- **覆盖已有修改**：禁止覆盖、撤销或重置用户已有修改。
- **无关改动**：禁止顺带重构无关代码或批量格式化无关文件，或未经授权调整依赖、构建和目录结构。
- **规则漏读**：禁止跳过当前任务适用的参考资料。
- **无条件全读**：禁止忽略读取条件，一律加载全部参考资料。

## 3. 职责、主流程与抽象

- 优先复用项目已有类型、接口、组件、工具和扩展机制，以职责清晰、接口精简、低耦合为目标，在已定架构内完成实现设计；任务明确要求调整架构时按授权范围处理。
- 沿用项目英文命名、缩写、布尔命名和类型后缀，名称表达业务概念、动作与对象，区分查询、转换、校验和执行，明确写入、外部调用等副作用。
- 一个方法完成一个职责内语义完整的逻辑，判断、计算和处理保持连贯；主流程按业务步骤在同一抽象层次展开，编排方法可以协调共同完成其职责的多个步骤。
- 提取方法应有独立语义、实际复用价值，或明显改善主流程可读性，使用次数不是唯一依据。
- 优先组合、委托和已有组件协作；继承用于真实替换关系或稳定模板流程，受容器管理的依赖沿用项目注入方式。
- 数据对象承载数据和必要的局部行为，服务负责业务编排，实体、DTO、VO 沿用项目分层约定。
- 重复业务规则归所属领域或服务，跨业务通用且无状态的能力才放入工具模块。
- 在直接实现、提取步骤和新增抽象之间选择能解决当前问题且理解成本较低的方式。新增抽象前确认已有重复、真实复用需求、明确稳定的变化点、职责与依赖问题或项目架构依据；仅在存在实际取舍时简述依据。

### 禁止项

- **机械拆分**：禁止将完整逻辑拆成缺少独立语义、复用价值和可读性收益的小方法，仅缩短代码不能证明拆分有价值。
- **无职责转发**：禁止增加没有独立职责的包装与转发层。
- **隐瞒副作用**：禁止使用模糊名称隐藏写入、外部调用或其他副作用。
- **错误合并**：禁止将业务规则不同、变化原因不同的实现强行合并为同一套处理逻辑。
- **破坏业务连贯性**：禁止引入只增加跳转和依赖层次、却未改善职责或协作的形式化解耦。
- **无依据的抽象**：禁止新增缺少当前职责、真实复用需求、明确变化点或项目架构依据的接口、基类、策略、工厂或配置层；单一实现或未来可能扩展本身不是新增依据。
- **设计流程过重**：禁止将枚举设计模式或撰写决策报告设为常规局部修改的固定步骤。

## 4. 条件与校验边界

- 布尔结果直接表达，不用等价的 `if/else` 包装；有独立处理或副作用时保留必要分支。
- 前置条件不满足、合法无操作和失败分支可提前退出，确保资源释放、事务和必要副作用正确；正常流程顺序展开，清楚的并列业务分支保留 `if/else`，不强制统一控制流形式。
- 按输入来源和契约分配校验：入口检查格式、类型和必填项；服务检查存在性、权限与业务状态；数据访问保证查询和写入范围；外部边界处理不可信数据。
- 新入口和新信任边界保留必要检查；明确处理可缺失的查询结果，不将上游未保证的条件视为已校验。精简校验时保留权限、可能变化的业务状态、写入范围、并发和一致性保障。

### 禁止项

- **重复判断**：禁止再次判断当前分支中已经成立的条件。
- **重复校验**：禁止再次校验同一调用路径中上游已保证且仍然成立的参数、必需依赖或非空返回；新信任边界和可能变化的业务状态仍需检查。
- **无依据的防御**：禁止缺少输入来源、接口契约或业务规则依据，仅凭理论上的空值可能性逐层增加判空或无业务价值的兜底；必要的边界检查保留。
- **静默失败**：禁止用无结果的提前退出代替应报告的业务失败，契约允许的无操作除外。
- **分支割裂**：禁止将需要并列比较的正常业务分支强行拆成零散的提前返回。

## 5. 固定值与状态建模

- 状态码、类型码、阈值和默认值等业务固定值优先复用已有常量、枚举、配置或所属类型能力；没有合适定义时在所属范围命名。
- 有限稳定的状态、类型和操作集中建模，复用的编码查找、描述和简单判断归所属类型或转换组件；依赖服务、数据库或外部调用的复杂行为归业务组件。
- 对外接口、持久化和消息使用稳定编码；空值和未知编码按明确的返回、默认或异常契约处理。

### 禁止项

- **业务魔法值**：禁止在判断、赋值、查询和计算中直接使用未命名的业务状态码、类型码或阈值，例如 `status == 2`。
- **重复定义**：禁止重复声明项目已有且语义一致的常量或枚举。
- **未知编码误判**：禁止在没有契约依据时，将未知编码映射为正常业务状态。
- **过度配置**：禁止将固定业务定义改成缺少实际变化需求的配置项。
- **字面量机械提取**：禁止将每个字面量一律提取为常量，`count > 0` 等语义明确的局部字面量无需提取。
- **编码不兼容**：禁止擅自修改已经发布的状态或类型编码。

## 6. 集合与转换

- 优先使用项目集合工具、标准库和语言惯用写法表达过滤、映射和分组；复杂分支、副作用或提前结束的逻辑优先用循环。
- 明确空集合、空元素、重复键和顺序语义，按业务定义合并冲突。
- 沿用现有字段映射方式，核对必填字段、数据类型及业务含义。
- 明确数值默认值、精度、舍入和比较语义。

### 禁止项

- **任意处理冲突**：禁止在缺少业务冲突策略时，随意保留重复键或合并冲突数据中的某一条。
- **掩盖字段差异**：禁止使用通用复制工具忽略必填字段、类型或业务含义的差异。
- **依赖未知行为**：禁止依赖未经确认的工具默认值、转换或冲突处理行为。
- **零值误判**：禁止在没有业务依据时，将零视为缺失值。

## 7. 注释与格式

- 沿用项目缩进、导入、换行、声明标记顺序和格式工具，保持局部一致。
- 支持 import 的语言通过导入引用类型，仅在同名冲突或歧义时在使用处写全路径。
- 按项目约定使用中文业务注释，说明意图、约束、算法步骤与取舍；公共能力和复杂方法按要求描述实际参数、返回与异常。
- 文档注释放在语言和工具要求的位置，局部说明靠近实现；Java 的位置要求见适用的 Java 资料。

### 字段与常量注释

- 本次新增或语义发生变化的业务字段、配置参数、业务常量和枚举项，应提供或保留准确的中文业务注释；这些声明使用 `private`、`static` 或 `final` 修饰时同样适用。
- 注释说明业务含义；涉及单位、编码来源、取值约束、空值或默认值含义时，补充相应说明。
- 外部协议、平台模型和内部枚举之间存在不同编码时，注明字段所属的编码体系及转换依据，不能只写“类型”“状态”等泛称。
- 已有类型或枚举集中定义了完整含义时，优先引用该定义，避免重复维护同一份编码说明。
- 日志对象、序列化版本号等惯用基础声明按项目规范处理；局部变量不要求逐一添加注释。
- 注释要求限定在本次修改范围内，不为补齐注释批量改写无关代码。

### 禁止项

- **重复注释**：禁止只翻译变量名、复述赋值语句、逐行翻译简单代码或添加与简单实现重复的说明。
- **虚假说明**：禁止编造作者、日期、性能保证或尚未实现的能力。
- **过期说明**：禁止保留与当前实现不一致的注释或文档。
- **滥用全路径类型名**：支持 import 的语言中，禁止在无同名冲突或歧义时，在使用处直接写全路径类型名。

## 8. 验证、复查与交付

### 选择必要验证

实现按契约覆盖正常流程、边界和失败路径，行为变化时同步相关测试和注释。优先使用项目已有框架和检查方式，按实际修改选择验证：

| 修改影响                   | 验证重点                                       |
|----------------------------|------------------------------------------------|
| 局部逻辑或业务分支         | 相关正常流程、边界和失败路径                   |
| 接口、序列化或跨模块行为   | 参数、返回、异常、兼容性、调用方及必要集成验证 |
| 数据、权限或事务           | 查询与写入范围、回滚、批量行为和一致性         |
| 并发、缓存、消息或外部调用 | 竞争、重复执行、失效、失败传播或补偿           |
| 配置、依赖或目标版本       | 配置加载、构建、版本和运行环境兼容性           |
| 注释、格式或文档           | 语义与实现一致、差异范围及适用的格式或链接检查 |

- 根据修改需要运行编译、类型检查、静态检查或测试；新增关键逻辑或行为变化时，按风险补充有价值的测试。
- 相关验证足以覆盖影响且已通过时结束；发现失败、扩大影响或仍有具体疑点时，再扩大或重跑受影响检查，项目明确要求的检查照常执行。
- 修复本次修改引入的问题，检查失败时区分新增问题与已有问题；无法验证时说明具体限制。

### 完成前核对与交付

变更任务检查实际差异；只读复查按用户指定范围检查。以下检查在内部执行，仅分析时核对适用的分析依据与结论，不据此触发修改或测试。

- [ ] 目标行为、正常与失败路径及受影响契约正确。
- [ ] 代码职责与主流程清楚，没有魔法值、重复防御、机械拆分或无价值抽象。
- [ ] 涉及的数据范围、事务、并发和资源保障完整。
- [ ] 已审查实际差异，保留用户修改，相关测试已同步。
- [ ] 已检查本次新增或语义变更的字段、常量和枚举项声明，并结合必要使用点确认业务注释符合适用规则。
- [ ] 注释与实际实现一致；涉及单位、编码来源、缺失值和默认值时，没有遗漏或相互矛盾。
- [ ] 必要验证已完成，未解决问题和未验证事项已明确。

复查发现的问题区分为明确违反规则、可选改进和既有问题，不把个人偏好当作强制要求。交付只报告实际发现和结果，不要求输出完整核对清单。

简洁交付修改内容、解决的问题、必要的实现取舍及实际验证结果；仅在有实际风险时说明兼容性、数据、配置或运行注意事项。

### 禁止项

- **无差别全量检查**：禁止忽略实际影响，一律对每个任务叠加全部检查；项目明确要求的检查照常执行。
- **无效重复验证**：禁止在没有新变化、失败或具体疑点时，反复运行已充分覆盖影响的检查。
- **低价值测试**：禁止新增不能验证目标行为、关键边界或失败路径，仅重复实现步骤或凑数量的测试。
- **篡改正确断言**：禁止修改正确的测试断言来迁就错误实现。
- **虚报验证通过**：禁止将未执行的检查或未确认的行为报告为通过。
- **过程叙述冗长**：禁止在交付中重复叙述编码过程。
- **夸大完成范围**：禁止将局部成果描述为整体完成，或声称未实现的能力已经交付。
