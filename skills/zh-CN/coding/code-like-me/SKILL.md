# code-like-me

## 目标

专注于软件开发 Code 阶段，在遵循需求、既定设计、项目规范和接口契约的前提下，按照用户的个人编码习惯完成代码实现。

核心要求：

- **贴合个人风格**：像用户一样思考和组织代码，保持命名、职责划分和逻辑组织的一致性。
- **遵循项目约定**：优先复用现有类型、接口、组件、工具和成熟实现。
- **保证实现质量**：职责清晰、逻辑完整、接口兼容、边界明确、异常处理合理。
- **控制修改范围**：只修改任务所需内容，避免不必要的抽象、封装和重构。
- **保证实现正确**：遵循业务规则，考虑数据一致性、事务、并发和资源生命周期。
- **完成必要验证**：根据修改范围执行测试、编译、静态检查和差异审查。

按用户要求完成实现与必要验证；仅要求代码分析或建议时，按指定范围输出。

## 1. 规则优先级与适用范围

### 1.1 规则优先级

编码决策遵循以下优先级：

1. **用户明确要求**：当前任务的功能要求、实现约束、技术选型和修改范围。
2. **项目规范**：项目架构、技术栈、编码规范、接口契约和模块约定。
3. **相邻实现**：当前模块中经过确认、维护良好且与任务相关的实现习惯。
4. **个人编码偏好**：项目没有明确约定时，按照本技能中的个人编码习惯实现。

始终保证业务正确性、接口兼容性和运行环境兼容性。

不同规则发生冲突时，按照上述优先级处理，同时保证必要的正确性与安全约束。

### 1.2 适用范围

- 通用规则适用于各语言，按照对应语言的惯用方式实现。
- 语言专节仅在使用对应语言时叠加应用，未列出的语言以项目规范为准。
- 已有项目优先延续局部约定，新增模块根据实际需求设计。
- 不照搬参考项目的包名、框架、业务模型或技术实现。
- 个人习惯以多个一致实现为依据，不从单个特例、生成代码或其他作者代码推断。
- 质量规则是实现约束，不代表历史代码全部满足这些要求。
- 保留用户已有修改，仅修改完成当前任务所必需的内容。

## 2. 执行流程

### 2.1 明确实现边界

开始编码前确认：

- 需要实现或修改的功能。
- 涉及的模块、类、方法和文件。
- 已明确的业务规则与实现方案。
- 接口、数据结构和兼容性要求。
- 必须保持的既有行为及副作用。
- 用户明确指定的修改范围和验收要求。

执行原则：

- 需求和设计明确时，直接进入项目上下文阅读。
- 缺少信息但可以从项目现有实现、调用方或接口契约中判断时，优先自行确认。
- 仅当缺失信息会影响实现正确性，且无法从上下文判断时才提问。
- 不擅自改变已确定的业务规则、接口约定或技术方案。
- 实现过程中发现既定方案存在实际问题时，说明具体影响，必要时先确认。

### 2.2 阅读项目上下文

根据任务影响范围阅读项目，避免只看目标方法就直接修改。

优先检查：

1. 项目说明、开发规范和相关文档。
2. 构建文件、语言版本、框架版本及依赖约束。
3. 目标模块的目录结构和职责划分。
4. 目标类、方法及其上下游调用方。
5. 同模块两到三个与任务相关的相邻实现。
6. 相关测试、异常处理和数据访问方式。
7. 涉及数据库、缓存、消息、事务或并发时的相关实现。

阅读原则：

- 先理解当前模块的职责与依赖关系，再选择实现方式。
- 参考相邻实现时，判断其正确性、适用性和维护质量。
- 区分项目强制规范、稳定的局部习惯和历史遗留写法。
- 不因为历史代码存在某种写法，就默认应该继续沿用。
- 不为了解整个项目而无目的地阅读大量无关文件。
- 语法、框架 API 和标准库使用必须兼容项目目标版本。

### 2.3 识别个人编码习惯

个人编码习惯主要从以下方面判断：

- 类、方法、变量和常量的命名方式。
- 方法职责划分与代码组织方式。
- 主流程的展开顺序。
- 条件判断、提前退出和分支处理习惯。
- 集合处理、对象转换和数据访问方式。
- 异常处理与日志表达方式。
- 注释语言、格式和文档习惯。
- 抽象、封装、复用与依赖组织方式。

判断原则：

- 优先参考当前模块中多个一致的实现。
- 相邻实现存在差异时，结合业务职责和维护场景选择。
- 不机械模仿代码形式，应理解其背后的组织习惯。
- 个人偏好不能成为引入不合理设计的理由。

### 2.4 分析修改影响

编码前根据任务范围检查：

- 调用方是否依赖现有参数、返回值或异常。
- 是否涉及对外接口和数据序列化契约。
- 是否影响数据库字段、查询条件或持久化行为。
- 是否影响缓存、消息及其他外部系统。
- 是否涉及事务边界、并发执行和资源生命周期。
- 是否存在依赖原有副作用或执行顺序的业务逻辑。
- 是否需要同步修改相关测试。

优先保持现有契约。

确实需要改变既有行为时，确保相关调用方、测试和依赖模块得到正确处理。

### 2.5 选择实现方式

实现前遵循以下原则：

- 优先复用项目已有类型、接口、组件、工具和扩展机制。
- 优先采用组合、委托和现有组件协作。
- 根据实际职责决定是否新增类、方法或其他抽象。
- 简单需求直接实现，复杂流程梳理稳定步骤与变化点。
- 保证主流程按业务步骤在同一抽象层次展开。
- 明确对象所有权、依赖方向、生命周期和失败传播。
- 不为了理论上的扩展性引入当前没有实际价值的设计。

### 2.6 完成代码修改

- 围绕当前需求完成逻辑完整的实现。
- 保持现有代码风格和模块边界。
- 按接口契约实现必要的参数校验和失败处理。
- 保证正常流程、异常流程和边界条件完整。
- 修改行为时同步检查相关注释和测试。
- 控制修改范围，不顺带重构无关代码。

### 2.7 验证与审查

完成实现后：

1. 检查代码差异和修改范围。
2. 检查方法职责、逻辑完整性和命名。
3. 检查业务固定值及已有常量的使用。
4. 检查异常处理、边界条件和资源释放。
5. 检查接口兼容性和相关调用方。
6. 根据影响范围执行编译、测试或静态检查。
7. 修复本次修改引入的问题。

## 3. 通用编码规则

### 3.1 设计原则与模式

#### 职责与契约

- 以职责清晰、接口精简、低耦合为目标，按需运用 SOLID 与迪米特法则。
- 受容器管理的依赖沿用项目注入方式。
- 修改既有能力时保持接口契约，不额外收紧输入条件或暗改返回、异常和副作用语义。
- 明确模块、类、方法的职责边界，避免业务逻辑散落在不相关的位置。
- 数据对象承载数据与必要的局部行为，服务负责业务编排。

#### 复用与协作

- 优先使用已有组件、扩展机制、组合和委托。
- 继承用于真实替换关系或稳定的模板流程。
- 重复业务规则归入所属领域或服务。
- 跨业务通用且无状态的能力才放入工具模块。
- 优先复用现有抽象，不为了复用而强行统一不同业务行为。

#### 抽象与封装

按照当前需求直接实现。

新增抽象应至少满足以下一项：

- 解决已经存在的重复业务知识。
- 隔离明确且稳定的变化点。
- 明确改善模块职责或依赖关系。
- 满足项目已有架构约定。
- 解决真实存在的复用需求。

禁止：

- 仅为以后可能扩展而引入接口、抽象基类、策略、工厂或配置层。
- 为单一实现创建没有实际价值的抽象。
- 为简单调用增加无独立职责的包装和转发。
- 为减少几行代码引入额外层次。
- 为形式上的解耦破坏业务逻辑的连贯性。

#### 组件协作

复杂流程需要检查：

- 依赖方向是否合理。
- 资源所有权和生命周期是否明确。
- 调用顺序是否符合业务要求。
- 并发执行是否安全。
- 异常和失败是否正确传播。
- 替换与扩展是否破坏现有契约。

### 3.2 命名与逻辑组织

#### 命名规范

- 类型、方法、函数和变量应表达明确的业务概念与用途。
- 沿用项目现有英文命名、缩写和类型后缀。
- 方法或函数名体现动作与对象。
- 布尔命名沿用项目惯例。
- 名称应准确区分查询、转换、校验与执行。
- 不得通过模糊命名隐藏写入操作、外部调用或副作用。

#### 单一职责与逻辑完整

一个方法或函数围绕一个明确职责，完成一段语义完整的逻辑。

- 同一职责内的判断、计算和处理保持连贯。
- 主流程按业务步骤在同一抽象层次展开。
- 编排方法可以协调共同完成其职责的多个步骤。
- 提取方法应有独立语义、复用价值，或明显改善主流程可读性。

禁止：

- 仅为了缩短方法机械拆分。
- 仅为了减少代码行数提取方法。
- 将一个完整业务流程拆成大量相互跳转的小方法。
- 增加没有独立职责的转发和包装。

#### 条件与流程控制

- 布尔结果直接表达，不用等价的 `if/else` 包装。
- 不重复判断当前分支中已经成立的条件。
- 有独立处理或副作用时保留必要分支。
- 前置条件不满足、合法无操作和失败分支可优先提前退出。
- 正常流程保持顺序展开，减少不必要的嵌套。
- 提前退出必须保证资源释放、事务和必要副作用正确。

禁止：

- 用静默退出代替业务失败。
- 将需要并列比较的正常业务分支强行拆成零散的提前返回。
- 为追求少量代码而牺牲业务逻辑的可读性。

清晰的 `if/else` 可以保留，不强制统一控制流形式。

### 3.3 固定值与业务编码

- 状态码、类型码、阈值、默认值等业务固定值，优先复用已有常量、枚举、配置或所属类型能力。
- 没有合适定义时，在所属范围内命名。
- 有限稳定的状态、类型和操作集中建模，减少散落值与重复分支。
- 复用的编码查找、描述获取和判断归入所属类型或转换组件。
- 对外接口、持久化和消息使用稳定编码。
- 不擅自修改已经发布的编码。

禁止：

- 在判断、赋值、查询和计算中散落业务魔法值，例如 `status == 2`。
- 重复定义项目已有常量。
- 将未知编码随意视为正常状态。
- 为了消除重复而将固定业务定义改成没有实际需求的配置项。
- 机械提取每一个字面量。

`count > 0` 等语义明确的局部字面量无需提取。

### 3.4 数据与状态建模

- 数据对象承载数据与必要的局部行为。
- 服务负责业务编排。
- 实体、DTO、VO 和对外契约遵循项目分层约定。
- 有限稳定的类型、状态和操作集中建模。
- 状态类型封装自身属性相关的简单行为。
- 涉及服务依赖、数据库或外部调用的复杂行为归入业务组件。
- 明确空值、未知编码的返回、默认或异常契约。
- 不随意改变已经发布的状态编码。
- 避免散落状态判断和重复的编码转换逻辑。

### 3.5 校验与防御边界

根据输入来源、类型、接口契约和业务规则设置校验。

#### 校验职责

- **入口层**：负责格式、类型、必填项及基本参数合法性。
- **服务层**：负责数据存在性、权限、状态和业务约束。
- **数据访问层**：负责查询范围、写入条件及数据访问正确性。
- **外部集成边界**：负责外部数据格式、缺失值及不可信输入的处理。

#### 校验原则

- 新入口和新信任边界保留必要检查。
- 允许缺失的查询结果必须明确处理。
- 可能变化的业务状态必须检查。
- 精简校验时保留权限、业务状态、写入范围、并发和一致性保障。
- 不将上游未保证的条件视为已校验。

禁止：

- 重复检查同一调用路径中上游已经保证且仍然成立的条件。
- 重复检查必需依赖和已经校验的参数。
- 对契约明确保证非空的返回值逐层判空。
- 仅因为理论上可能为空，就增加多层防御。
- 为不可能发生的情况增加没有业务价值的兜底。

### 3.6 异常与日志

#### 异常处理

- 按既有异常契约报告失败。
- 复用项目已有校验工具、业务异常和错误码。
- 错误消息说明具体业务原因。
- 捕获异常用于恢复、补充上下文或转换异常语义。
- 其他情况沿用项目统一异常处理机制。
- 面向调用方的错误消息不得暴露堆栈或底层敏感细节。

禁止：

- 无业务或接口依据地返回空集合、空值、默认对象、零值或成功结果。
- 跳过异常数据或吞掉异常后继续执行。
- 捕获异常后不处理、不记录也不重新抛出。
- 使用宽泛异常捕获掩盖真实失败。
- 重复记录同一个异常。

契约明确允许的空结果、恢复和降级正常保留。

#### 日志表达

- 沿用项目日志框架与日志级别。
- 使用参数化日志记录关键变化、外部失败和排查上下文。
- 涉及序列化或较重计算时先检查日志级别。
- 同一业务流程各环节使用统一、可检索的业务关键字前缀。
- 保留关键业务标识，写明处理步骤或处理结果。
- 当前层需要记录异常时保留堆栈。
- 日志应能够帮助定位问题，而不是重复输出代码执行过程。

禁止：

- 无意义的高频日志。
- 重复输出已经记录的异常。
- 输出凭据、令牌或完整敏感对象。
- 仅为了增加日志数量而记录无排查价值的信息。

### 3.7 集合、转换与数据访问

#### 集合处理

- 优先使用项目已有集合工具、标准库和语言惯用写法。
- 过滤、映射和分组使用清晰的表达方式。
- 复杂分支、副作用或需要提前结束的逻辑优先使用循环。
- 明确空集合、空元素、重复键和顺序语义。
- 合并数据时按照业务定义冲突处理策略。
- 不为了消除冲突随意保留其中一条数据。

#### 数据转换

- 优先沿用项目现有对象转换和字段映射方式。
- 核对必填字段、数据类型及字段业务含义。
- 不使用通用复制工具掩盖字段差异。
- 明确数值默认值、精度、舍入和比较语义。
- 不依赖未经确认的工具隐含行为。
- 不无业务依据地将零视为缺失值。

#### 数据访问

- 复用项目现有数据访问组件和服务查询。
- 可批量查询的数据不要在循环中逐条查询。
- 批量操作考虑批次大小、事务和失败处理。
- 查询条件必须符合业务数据范围。
- 更新和删除明确操作范围及重复执行行为。
- 保留必要的返回值检查和并发控制。

#### 事务管理

- 按业务原子性划定事务边界。
- 遵守框架事务管理和回滚规则。
- 明确外部调用、缓存和消息发送的失败补偿机制。
- 避免将不必要的外部调用放入长事务。
- 需要保证多个写操作一致性时，使用项目已有事务机制。

#### 缓存管理

- 重复且可可靠失效的热点中间结果可以缓存。
- 优先复用项目已有缓存组件。
- 明确缓存键、生命周期、写后失效和并发语义。
- 数据库写入后维护缓存时，优先复用提交后回调机制。
- 明确无事务场景和回调失败时的处理方式。
- 避免数据库回滚后仍保留本次写入产生的缓存变化。
- 不照搬其他业务的缓存容量或 TTL。

### 3.8 性能与资源管理

- 优先识别实际性能瓶颈，不凭主观判断增加优化逻辑。
- 优先减少重复计算、无效查询和不必要的数据转换。
- 数据库操作考虑查询次数、索引使用和数据范围。
- 避免在循环中执行可批量完成的数据库或外部调用。
- 根据实际需求选择合适的数据结构和处理方式。
- 并发优化必须同时考虑线程安全、数据一致性和资源竞争。
- 资源使用遵循项目生命周期管理方式，确保正确释放。
- 缓存优化必须明确一致性和失效机制。
- 不以增加代码复杂度换取缺乏实际收益的微优化。

### 3.9 注释与格式

#### 格式规范

- 沿用项目缩进、导入、换行和声明标记排列方式。
- 使用项目现有格式工具。
- 不格式化整个项目或与当前任务无关的文件。
- 类引用通过 import 引入。
- 仅当存在同名类冲突或导入产生歧义时，才在使用处写全路径。
- 无冲突时不直接使用全路径类名。
- 保持局部代码风格一致。

#### 注释规范

- 中文业务注释说明意图、约束、算法步骤与设计取舍。
- 公共能力、复杂方法或函数、关键字段按照项目要求描述实际参数、返回和异常。
- 文档注释放在语言和文档工具要求的位置。
- 局部说明靠近具体实现。
- 行为变化时同步更新相关注释。
- 注释应解释代码不容易直接表达的信息。

禁止：

- 逐行翻译代码。
- 为简单代码添加重复说明。
- 编造作者、日期、性能保证或未实现能力。
- 保留与实际实现不一致的过期注释。

## 4. 各语言的补充规则

通用规则适用于所有语言，语言专属规则根据实际开发语言加载。

### Java

处理 Java 代码时，在选择实现和修改前阅读：

`references/java.md`

Java 专属规则与通用规则叠加执行。

重点遵循：

不加载无关语言的专属规则。

## 5. 修改范围与用户代码保护

### 5.1 修改前检查

- 检查工作区状态和已有未提交修改。
- 识别用户已经修改但尚未提交的文件。
- 确认当前任务涉及的文件和模块。
- 了解目标文件是否存在其他正在进行的改动。

### 5.2 修改过程中

- 只修改完成当前任务所必需的文件。
- 保留用户已有代码和未提交修改。
- 不覆盖、不撤销、不重置用户已有修改。
- 不修改与需求无关的格式、命名和注释。
- 不擅自升级依赖、调整构建配置或改变目录结构。
- 不进行顺手重构。
- 发现相关代码存在历史问题时，判断是否影响当前任务，再决定是否处理。

### 5.3 修改后检查

- 检查实际文件差异。
- 确认没有意外修改其他文件。
- 确认用户原有修改没有被覆盖。
- 检查新增和修改的代码是否符合当前模块约定。
- 确认必要的测试和注释已经同步。

如果当前任务确实需要扩大修改范围，应确保扩大部分与实现正确性直接相关。

## 6. 验证与质量检查

### 6.1 验证策略

根据修改类型和影响范围选择必要验证。

| 修改类型     | 验证重点                           |
|--------------|------------------------------------|
| 简单逻辑修改 | 相关分支、边界条件                 |
| 业务逻辑修改 | 单元测试、业务规则和异常路径       |
| 接口修改     | 调用方、参数、返回值及兼容性       |
| 数据访问修改 | 查询条件、数据范围、事务和批量行为 |
| 并发逻辑修改 | 竞争条件、重复执行和一致性         |
| 跨模块修改   | 相关模块测试及集成测试             |
| 配置修改     | 配置加载、环境兼容性               |
| 依赖修改     | 构建、版本兼容和运行环境           |

### 6.2 测试原则

- 优先使用项目已有测试框架和测试方式。
- 优先运行与本次修改直接相关的测试。
- 业务逻辑变化时覆盖正常流程、边界和失败路径。
- 接口行为变化时检查相关调用方。
- 对新增关键逻辑，根据实际情况补充针对性测试。
- 不为了追求测试数量编写没有实际价值的测试。
- 不随意修改原有测试断言来适应错误实现。

### 6.3 编译与静态检查

根据项目实际情况选择：

- 编译或构建检查。
- 单元测试和集成测试。
- 静态代码检查。
- 类型检查。
- 格式检查。
- 必要的模块级验证。

优先执行与本次修改直接相关的检查，不无故执行耗时且无关的全量任务。

### 6.4 验证结果真实性

- 只报告实际执行过的检查。
- 不得将未执行的测试描述为已通过。
- 检查失败时区分本次修改引入的问题与项目已有问题。
- 无法执行验证时说明具体原因。
- 测试环境、依赖或权限阻塞时明确指出限制。
- 不能确认的行为不作通过结论。

## 7. 完成前检查清单

完成代码修改前，逐项检查：

### 实现正确性

- [ ] 实现符合用户明确要求和既定业务规则。
- [ ] 接口、返回值、异常和副作用符合原有契约。
- [ ] 调用方和相关依赖没有受到意外影响。
- [ ] 正常流程、边界条件和失败路径处理完整。

### 代码组织

- [ ] 方法或函数职责单一、逻辑完整。
- [ ] 命名准确，符合项目习惯。
- [ ] 方法拆分具有明确语义。
- [ ] 主流程层次清晰，没有不必要的跳转。
- [ ] 优先复用已有抽象和工具。
- [ ] 没有为了形式上的扩展性引入不必要的设计。

### 数据与异常

- [ ] 业务固定值使用已有定义或在所属范围命名。
- [ ] 没有散落的业务魔法值。
- [ ] 校验符合实际信任边界，没有重复防御。
- [ ] 异常处理符合项目契约，没有吞错或静默失败。
- [ ] 事务、缓存、并发和资源释放保持正确。
- [ ] 数据访问范围和更新条件正确。

### 修改范围

- [ ] 仅修改当前任务需要的内容。
- [ ] 没有覆盖用户已有修改。
- [ ] 没有顺带修改无关代码。
- [ ] 没有不必要的依赖、配置和目录变更。
- [ ] 注释与最终实现一致。

### 验证结果

- [ ] 已根据修改范围执行必要测试。
- [ ] 已检查编译或静态检查结果。
- [ ] 已检查实际代码差异。
- [ ] 已确认未解决问题和验证限制。

## 8. 最终交付

完成实现后，简洁说明：

### 修改内容

- 修改了哪些功能或文件。
- 解决了什么问题。
- 必要时说明关键实现取舍。

### 验证结果

- 实际执行的编译、测试和静态检查。
- 对应执行结果。
- 未执行的检查及具体原因。

### 风险与注意事项

- 仅说明实际存在的兼容性、数据、配置或运行风险。
- 没有额外风险时不必强行增加该部分。

交付要求：

- 以实际代码修改为准，不夸大完成范围。
- 不重复解释已经明确的需求。
- 不输出冗长的编码过程。
- 不隐藏未解决问题和验证失败。
- 让用户能够快速了解修改内容、验证情况和需要关注的事项。
