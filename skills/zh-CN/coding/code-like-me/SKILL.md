# code-like-me

## 范围与底线

专注于软件开发 Code 阶段，按用户与项目的编码习惯完成实现与必要验证。业务正确性、安全、权限、契约、用户授权和如实报告是底线，不因场景放宽。

开始前明确目标行为、已定方案、影响范围、需保持的契约和验收要求，检查工作区状态与目标文件已有修改。用户仅要求分析、建议或只读调查时，按指定范围输出，不修改代码或运行测试。需求和设计明确时直接落实，不重新设计或逐步确认。

## 1. 优先级与契约

各层决策按以下顺序处理：

1. **用户明确要求**：功能、约束、技术选型和修改范围。
2. **项目规范**：架构、技术栈、编码规范、接口契约和模块约定。
3. **相邻实现**：当前模块中正确、维护良好且相关的稳定习惯。
4. **个人编码偏好**：项目没有明确约定时，采用本技能的组织方式。

- 默认保持既有参数、返回、异常、序列化和副作用契约；授权变更时同步调用方、测试和兼容性。
- 内部 API 变更且无外部兼容要求时，同批迁移全部调用方并删除旧路径，不保留平行实现；有外部兼容要求时按契约保留并说明范围。
- 实现以用户可观察的行为和结果为验收对象，实现便利不能替代需求结果。

### 禁止项

- **偏好越界与跨项目照搬**：禁止以个人偏好覆盖项目规范或必要保障，禁止直接套用其他项目的包名、框架、业务模型或技术选型。

## 2. 开发场景与改动边界

场景按用户明确指定、方案文档（设计、需求、验收文档）、用户上下文的顺序确定；以主要目标判断，不凭关键词猜测。方案已给出目标、边界或证据时直接采用。跨场景按依赖顺序组合；只读调查不套用改动幅度。无法判断且影响授权时，说明采用的场景和依据，不要求用户逐项确认。

| 场景 | 目标与改动边界 | 完成证据 |
|---|---|---|
| 功能实现与变更（feat） | 行为达成、接口与结构可理解；含新行为、必要集成和经授权的契约变更；可先定数据形状和接口 | 真实入口的正常、边界和失败路径；调用方同步；未做范围 |
| 缺陷修复（bugfix） | 根因消除、行为恢复；只改证据支持的缺陷路径，不顺手重构、格式化或调依赖 | 同面复现前后对比、受影响回归、根因说明 |
| 重构（refactor） | 行为不变、结构收益明确；改目标结构涉及的调用图，调用方同批迁移 | 行为特征测试或等价性对比、真实路径冒烟、结构收益说明 |
| 性能优化（perf） | 指标达标、行为契约不变；改测量确认的瓶颈路径及必要调用方，可改算法、数据结构、批量、缓存、并发 | 基线、目标、同环境前后对比、运行次数与波动、功能回归 |
| 只读调查（readonly） | 结论清楚、依据充分；零文件修改，不改依赖、构建或配置 | 结论、证据位置、未确认项 |

- 场景决定目标与改动授权，风险决定分析与验证深度；两者叠加，不互相替代。不以改动行数判断深度：少量权限、事务或并发代码也可能影响广泛，多个文件的机械修改不必因此引入架构设计。
- 最小化只在场景边界内生效：缺陷修复以最小改动为主；功能实现和性能优化不因“少改”保留别扭模型或放弃有证据的结构性改造。

### 调研与资料

- 先识别适用的用户要求和项目规范；项目指令引用的规范也须阅读。能从项目、调用方或契约查明的信息自行确认，仅在缺失信息影响正确性且无法判断时提问。
- 从当前模块（任务所在包或服务）多个一致且维护良好的实现识别命名、职责、流程、分支、集合转换、异常日志和注释习惯；相邻实现不一致时判断其组织意图、正确性与适用性，依据不足时遵循项目规范和语言惯例。
- 仅当任务处理 Java 代码时完整读取 [Java 编码规则](references/java.md)；其他语言不加载该资料。

### 禁止项

- **场景错配**：禁止把最小改动当作所有场景的通用否决，或用功能、性能、重构的授权扩大目标无关的改动。
- **按修改量定深度**：禁止仅凭行数或文件数量判断深度，或因修改量小省略已识别风险的必要检查。
- **无关改动**：禁止顺带重构无关代码、批量格式化无关文件，或未经授权调整依赖、构建和目录结构；历史问题仅在影响当前任务时处理。
- **流程形式化**：禁止把评分、分级报告或设计文档设为每个任务的固定前置步骤。
- **规则漏读与无关阅读**：禁止跳过适用规范或适用资料，也禁止无依据加载不适用的资料。
- **偏好误判与覆盖修改**：禁止从单个特例、他人代码或历史写法推断偏好，禁止覆盖、撤销或重置用户已有修改。

## 3. 设计与实现

- 优先复用项目已有类型、接口、组件和扩展机制；在已定架构内实现，不擅自调整架构。
- 控制流按业务语义展开：前置条件、合法无操作和失败分支可提前退出；清楚的并列业务分支保留 `if/else`，不强行拆成零散提前返回；布尔结果直接表达。
- 涉及新增或调整数据形状时，先定核心数据结构、状态、所有权和接口，再写业务流程；跨模块前先定调用方式和错误契约。
- 新需求不能只做局部补丁：现有模型无法自然容纳时，按“需求第一天就存在”的方式重新整合数据形状、接口和流程，同批迁移调用方，不保留临时双路径。重设计需要方案依据、测量证据或明确授权；缺陷修复不主动重设计。
- 功能实现或结构性改造没有先例且选择会影响结构时，先用最小成本比较两三个候选数据形状或接口边界，选定后删除试验代码。
- 演进既有实现时先做减法：在场景授权范围内删除无引用代码、失效校验和占位，再在更简单的基线上新增；不为此扩大或缩小场景目标。
- 以读者负担检验结构：新读者能否不逐层追踪就回答“X 从哪来、什么能改 X”。不能时优先合并只转发一次的包装、缩小可变状态范围，或消除需要多处同步的隐藏状态。

### 校验、状态与数据

- 新入口和新信任边界保留必要检查；精简校验时保留权限、可能变化的业务状态、写入范围、并发和一致性保障。
- 业务固定值优先复用已有常量、枚举、配置或类型能力；没有合适定义时在所属范围命名。不把缺少实际变化需求的固定业务定义改成配置项，不擅自修改已发布的状态或类型编码，语义明确的局部字面量无需提取。形态清楚、局部且短期不增长的直白代码不强行建模。
- 同一实体出现多个需同步的阶段标记，或按类型、渠道持续增长的分支时，优先用枚举、状态机、表或多态集中表达，判断标准是减少分支和非法状态。
- 集合处理：复杂分支、副作用或提前结束的逻辑用循环；没有业务依据时，不把零值视为缺失值，按业务定义处理重复键与冲突。
- 批量访问优先批量完成，并明确批次、事务范围和部分失败处理。

### 异常、事务、并发与资源

- 捕获异常用于有依据的恢复、补充排查上下文或转换异常语义；其他情况交给统一异常机制，转换时保留原因链。
- 外部调用、缓存修改和消息发送与本地事务边界分清：按业务原子性划定事务，不在长事务中放入无关外部调用，不把本地事务回滚误认为外部副作用或缓存已自动撤销。
- 数据库写入后维护缓存时优先复用提交后回调，防止回滚残留。
- 并发冲突优先消除共享状态、缩小范围或分离所有权，再考虑锁；重试与消息重投明确幂等键、终态与副作用语义。
- 本层创建并拥有的资源，在正常、异常、提前返回及取消路径释放；不擅自关闭借用或由容器管理的共享资源。

### 禁止项

- **机械拆分与无职责转发**：禁止把完整逻辑拆成缺少独立语义、复用价值或可读性收益的小方法，禁止增加没有独立职责的包装层。
- **错误合并与破坏连贯性**：禁止将业务规则不同、变化原因不同的实现强行合并，或引入只增加跳转而未改善职责的形式化解耦。
- **无依据的抽象**：禁止仅凭单一实现或假设未来扩展新增接口、基类、策略、工厂或配置层；方案、契约或测量证据明确要求的结构除外，借场景新增与目标无关的扩展点仍属此类。
- **重复校验与无依据防御**：禁止再次判断或校验同路径上游已保证且仍成立的条件、参数、依赖或非空返回，也禁止缺少输入来源或业务规则依据的逐层判空和兜底。
- **吞异常与失败伪装成功**：禁止空捕获、捕获后既未恢复也未按契约传播便继续执行，或将真实失败转换为空集合、空值、默认对象、零值、成功返回或跳过异常数据（契约明确允许的除外）。
- **类型逃逸与静默失败**：禁止用强制转换、忽略编译警告或动态类型绕过检查；禁止用无结果的提前退出代替应报告的业务失败，契约允许的无操作除外。
- **业务值、编码与冲突**：禁止在判断、赋值和计算中直接使用未命名的业务状态码、类型码或阈值，禁止重复声明项目已有且语义一致的常量或枚举，禁止无契约依据地把未知编码映射为正常状态，也禁止缺少业务策略时随意保留或合并重复数据。

## 4. 注释、日志与格式

注释语言以项目约定为准，无相反约定时使用中文；支持 import 的语言通过导入引用类型。Java 类、接口、方法（含私有方法）及构造器的 Javadoc 范围与位置要求见 [Java 编码规则](references/java.md#javadoc)。

- 本次新增或修改的业务分支必须有靠近实现的中文注释，说明业务场景、处理意图或原因，并对应到各分支，不只翻译判断表达式或笼统说明整个判断结构；条件简单或命名清楚不能作为省略依据。
- 纯 NPE、越界等基础技术防护可豁免；判空或边界判断同时承载业务含义时仍须注释。
- 本次新增或语义变化的业务字段、配置参数、业务常量和枚举项，应提供或保留准确的中文业务注释；涉及单位、编码来源、取值约束、空值或默认值时补充说明。
- 已有类型或枚举集中定义完整含义时优先引用；原始编码字段注明所属定义；局部变量不要求逐条注释。
- 注释要求限定在本次修改范围内，不为补齐注释批量改写无关代码；生成代码按项目约定处理。
- 为保持注释与实现一致而调整本次修改紧邻的注释（如删除后重排序号）属修改范围内。

### 日志

- 记录关键业务变化、外部失败和排查所需上下文；同一业务流程使用统一、可检索的关键字前缀，保留关键业务标识和处理步骤或结果。
- 明确沿调用链的记录职责，当前层负责记录异常时保留堆栈，不重复记录同一异常；不增加缺少排查价值的高频过程日志，不把记录日志当作异常恢复或继续正常流程的替代。

### 禁止项

- **重复注释**：禁止只翻译变量名、复述赋值语句或逐行翻译简单代码。
- **虚假与过期说明**：禁止编造作者、日期、性能保证或尚未实现的能力，禁止保留与当前实现不一致的注释或文档。
- **滥用全路径类型名**：支持 import 的语言中，无同名冲突或歧义时禁止在使用处写全路径类型名。
- **日志泄密**：禁止在日志中输出凭据、令牌或完整敏感对象。

## 5. 验证与交付

按契约覆盖正常、边界和失败路径；行为变化时同步测试和注释，优先使用项目已有框架和检查方式：

- 根据修改需要运行可用检查；新增关键逻辑或行为变化时按风险补充有价值的测试，项目无测试框架时说明限制，不引入新框架。
- 相关验证足以覆盖影响且已通过时停止追加；发现失败、扩大影响或仍有具体疑点时，再扩大或重跑受影响检查。
- 缺陷修复先落失败用例或可复现证据，用运行证据定位根因后再改代码；修后在相同条件复验并回归受影响路径。不能复现时收紧条件或增加观测，不先猜原因。
- 连续多次修复仍卡在同一检查或现象时，先验证这些修复共同假设的前提，不继续叠加修复。
- 非平凡机械批量改动先手工完成一个单元并验证，再写确定性脚本或 codemod 完成其余部分；脚本应可重跑。重复出现的检查优先固化为项目已有脚本，不擅自引入工具链。
- 多步改动拆成以可检查状态结束的小单元，前一个单元通过后再进入下一个。
- 性能优化先明确指标、目标值与测量条件，大改每步只改变一个主要变量，排除缓存命中或未执行代码等测错对象。
- 性能结论记录基线、运行次数、同环境前后对比、波动范围与限制因素；结构性改造前后保持行为契约，除非任务明确授权变更。

### 完成判定

变更任务以最终实际差异及其影响范围为依据；只读调查按用户指定范围核对，不以代码差异为前提。不能只凭局部代码外形、最初计划或对修改的记忆判断。

功能验收、规范复查和验证结果分别判断，不能相互替代；有未满足或未确认项时明确剩余事项，不声称整体通过。

简洁交付修改内容、解决的问题、实际复查与验证范围及剩余限制，不重复叙述编码过程。对校验项、规则项的增删或调整，以及存在实际取舍的实现选择，简要说明处理内容、必要性、影响及验证结果；其余实现选择无需逐项说明。不以“已按技能检查”代替实际结果。

### 禁止项

- **无差别全量检查与低价值测试**：禁止忽略实际影响叠加全部检查，禁止新增只重复实现步骤或凑数量的测试；断言应针对可观察行为和契约结果。
- **篡改断言与虚报验证**：禁止修改正确断言迁就错误实现，禁止将未执行的检查或未确认行为报告为通过；编译通过、子代理自报、缓存结果不能替代实际行为验证。
- **无基线或测错对象结论**：禁止在缺少基线、运行次数或波动范围时报告性能提升或回归，禁止把小于波动的差异或测错对象（缓存命中、未执行代码、噪声）当成优化效果，也禁止把未测量支持的结构性重写当作性能优化。
- **夸大范围与隐瞒失败**：禁止将局部成果描述为整体完成，禁止省略仍未解决的问题或验证失败。
