# 任务识别与执行流程

开始处理任务时阅读，围绕用户目标确定执行深度、项目上下文和修改范围。仅要求分析或建议时，完成对应分析，不进入代码修改。

## 1. 确定边界与执行深度

先明确目标行为、已定方案、影响范围、需保持的契约及验收要求；检查工作区状态和目标文件已有修改。

根据业务复杂度、影响传播和失败后果选择执行深度：

| 任务情况                                     | 分析与实现方式                                             |
|----------------------------------------------|------------------------------------------------------------|
| 局部修改，契约清楚，无共享状态或外部副作用   | 阅读目标实现和必要上下文后直接修改，核对相关分支与边界     |
| 涉及业务分支、多个调用方或数据访问           | 梳理调用关系、正常与失败路径，核对数据范围和受影响行为     |
| 涉及接口变更、权限、事务、并发或跨系统一致性 | 先明确契约、依赖、状态变化和失败处理，再实现并验证关键风险 |

- 同时符合多种情况时，保留其中必要的检查；发现新的影响或风险时调整深度。
- 少量权限或事务代码也可能影响广泛；多个文件的机械修改不必因此引入架构设计。
- 深度判断用于安排分析、实现与验证工作。
- 能从项目、调用方或接口契约查明的信息自行确认；仅在缺失信息影响正确性且无法判断时提问。
- 发现既定方案有实际问题时，说明原因和影响，授权范围内的实现细节自行处理。
- 需要改变已定业务要求、接口或技术选型且未获授权时先确认，其他独立工作继续。

### 禁止项

- **按修改量定深度**：禁止仅凭代码行数或文件数量判断执行深度。
- **遗漏风险检查**：禁止对已识别的风险省略必要检查，修改量小也不构成省略依据。
- **流程形式化**：禁止将评分、分级报告或设计文档设为每个任务的固定前置步骤。

## 2. 阅读上下文与识别个人习惯

- 围绕任务阅读相关项目规范、目标模块、必要调用方和测试；涉及版本或依赖能力时核对构建配置。
- 先理解当前模块的职责与依赖，再选择实现方式；涉及输入、返回、异常或副作用变化时追踪受影响的上下游。
- 从当前模块多个一致实现识别命名、职责划分、主流程顺序、条件分支、集合转换、异常日志和注释习惯。
- 依据不足时遵循项目规范和语言惯例；相邻实现不一致时，结合业务职责和维护质量选择，理解组织意图。
- 根据已识别的任务内容，按技能入口列出的读取条件补充对应主题资料；出现新影响时重新判断适用资料。

### 禁止项

- **无关阅读**：禁止持续读取无法帮助确认当前需求、契约、影响或编码习惯的文件，或加载无关资料。
- **凑足阅读数量**：禁止将阅读固定数量的参考文件作为完成上下文分析的条件。
- **偏好误判**：禁止从单个特例、生成代码或其他作者代码推断用户偏好，依据不足时不得虚构个人习惯。
- **机械模仿**：禁止脱离业务职责和组织意图，仅复制相邻代码的外形。

## 3. 完成实现并控制范围

- 优先复用项目已有类型、接口、组件、工具和扩展机制，简单问题直接实现。
- 涉及职责、依赖、复用或抽象取舍时，先应用设计判断，再选择实现方式。
- 按契约完成正常流程、边界和失败路径，行为变化时同步相关测试和注释。
- 只修改完成任务所必需的内容，保留用户已有修改。
- 历史问题仅在影响当前任务时处理；确需扩大修改范围时，扩大部分应与实现正确性直接相关。
- 依据实际影响安排验证，检查最终差异，修复本次修改引入的问题后交付结果。

### 禁止项

- **覆盖已有修改**：禁止覆盖、撤销或重置用户已有修改。
- **无关改动**：禁止顺带重构无关代码或批量格式化无关文件。
- **擅改项目配置**：禁止未经授权调整依赖、构建和目录结构。
