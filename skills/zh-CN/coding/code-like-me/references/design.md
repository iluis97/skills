# 实现设计与抽象

判断是否调整职责、依赖、复用方式或新增抽象时阅读。在已定架构内完成 Code 阶段的实现设计；任务明确要求调整架构时，按授权范围处理。

## 1. 职责与组件协作

- 以职责清晰、接口精简、低耦合为目标，按需使用设计原则与模式。
- 优先组合、委托和已有组件协作；继承用于真实替换关系或稳定模板流程，受容器管理的依赖沿用项目注入方式。
- 数据对象承载数据和必要的局部行为，服务负责业务编排；实体、DTO、VO 沿用项目分层约定。
- 重复业务规则归入所属领域或服务，跨业务通用且无状态的能力才放入工具模块。

### 禁止项

- **错误合并**：禁止将业务规则不同、变化原因不同的实现强行合并为同一套处理逻辑。
- **破坏业务连贯性**：禁止引入只增加跳转和依赖层次、却未改善职责或协作的形式化解耦。

## 2. 抽象与设计模式选择

- 在现有职责内直接完成、提取有独立语义的步骤、新增抽象之间，选择能解决当前问题且理解成本较低的方式。
- 新增抽象前，确认它解决了什么已有重复、真实复用需求、明确且稳定的变化点或职责与依赖问题；项目已有架构要求也可作为依据。
- 仅在存在实际取舍时简述依据，设计模式服务于已识别的问题。

### 禁止项

- **无依据的抽象**：禁止新增缺少当前职责、真实复用需求、明确变化点或项目架构依据的接口、基类、策略、工厂或配置层；单一实现或未来可能扩展本身不是新增依据。
- **设计流程过重**：禁止将枚举设计模式或撰写决策报告设为常规局部修改的固定步骤，实际存在取舍时简述依据即可。
