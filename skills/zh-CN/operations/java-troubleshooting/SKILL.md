# Java 服务运行期问题排查

按“固定范围 → 现象特征 → 分层归因 → 总结结论”推进。结论由证据驱动，具体问题具体分析，不预设原因方向。

先确认部署形态：宿主机直接部署或 Docker 容器。形态只影响观察入口和限额核对，不影响归因思路。

若服务已退出、反复重启或启动即失败，本技能不适用：Arthas 无法挂载，相关证据在容器退出码、重启记录与启动日志中。此时改用 `$log-analysis` 分析启动/退出日志，并核对容器退出状态；用户同时指定时可按顺序衔接执行。

## 1. 范围与现象特征

- 先固定服务与实例（Docker 时固定容器）、异常时间窗（含时区）及受影响范围；时间窗是后续一切时间判断的锚点，优先确定。
- 还原实际表现，而不止于用户的措辞：受影响的是全部请求、少数接口还是单个请求；是持续、间歇还是突发；伴随资源上涨、GC 变化、错误率变化还是进程状态异常；是否与流量高峰或特定输入相关。表现决定优先查哪一层，不按固定顺序跑完全部检查。

## 2. 分层归因

按证据从外向内收窄，每层有证据才下探或折返：

- **宿主机资源**：CPU 负载与 steal、内存与 swap、磁盘 IO（iowait、写入速率）、网络（延迟、重传、带宽）。指标取异常时段与正常时段对比。
- **运行环境限额**：仅 Docker 部署时——核对容器 CPU/内存 limit 与实际用量，确认是否存在 CPU throttling、内存逼近 limit 触发频繁 GC；注意 JVM 对容器限额的感知差异。资源充足但服务仍异常时重点查这层。宿主机直接部署时跳过。
- **JVM 层**：有 Arthas 时优先使用 Arthas 观察线程、GC 与内存；仅当 Arthas 不可用时改用 JDK 原生工具（jcmd/jstack/jstat/jmap）等价观察，不为排查主动安装 Arthas。接入方式、现象与命令映射、生产安全要求见 [references/diagnostics.md](references/diagnostics.md)。按现象选命令，不逐项跑全量。
- **代码与依赖**：用 trace 或堆栈定位具体方法段，用代码解释现象；外部依赖（DB、缓存、HTTP 等）的耗时单独验证，区分服务自身慢与依赖慢。

## 3. 变更关联

仅当异常开始时间附近存在部署或提交，或现象是新出现时，才比对近期变更：圈定嫌疑 commit，核对 diff 是否触及热点路径，并用变更前行为作反证；与变更无关时给出反证，不强行归因。

## 4. 总结结论

结论先行，区分已观察事实、原因推断和未验证事项。关键结论须有可复核证据：指标注明来源与数值、JVM 观察注明命令与输出摘要、代码注明文件与行。

按问题复杂度组织，省略无内容的部分：

```text
结论：<现状、根因及确定程度>
范围与覆盖：<服务及实例；部署形态；异常时间窗与时区；已查层级与限制>
关键发现：<事实，附证据来源与数值>
时间线：<现象、首次出现、相关变更节点；仅在有助于解释经过时提供>
根因：<能解释全部现象的最小原因及证据链>
未确认：<缺失证据及其影响>
建议：<下一步验证或处理方向>
```

## 边界

- 只读优先：Arthas `trace`/`watch`/`profiler` 有运行时开销，短时使用、用完 `stop`，不在高峰期长时间挂载；heapdump 是全量快照，先确认磁盘余量与用户授权。
- 不改 JVM 参数，不重启服务；调优与修复建议交用户决定。
- 需要日志侧证据时，提示用户显式调用 `$log-analysis`，不主动加载其他技能。
