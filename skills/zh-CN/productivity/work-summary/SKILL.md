# work-summary

## 1. 范围与记录依据

- 由用户显式调用。默认整理当前对话中已经实际开展、尚未记录的工作；用户指定需求、日期或提供补充内容时，按指定范围处理。
- 依据可见对话、实际操作结果和用户提供的信息总结，不把讨论、计划或建议写成已完成事项。不自动扫描其他项目或读取其他会话；缺少必要上下文时，请用户补充。
- 未完成的需求可以记录已开展的工作，标明当前状态、已取得的结果及待完成内容。未执行的测试、联调或上线不得写成已经完成。
- 没有可记录内容时说明原因，不编造条目或创建空的每日文件。
- 只维护本地工作记录，不主动调用其他技能或向工时系统、任务平台提交数据。

## 2. 目录与日期

- 目录依次取：用户本次明确指定的目录、环境变量 `WORK_SUMMARY_DIR`、当前用户主目录下的 `work-summary/`。默认目录在 Windows 通常为 `C:\Users\<用户名>\work-summary\`。
- 将目录展开并解析为绝对路径。环境变量需为绝对路径；配置无效或目录不可访问时说明原因，请用户指定可用目录，不静默改存其他位置。本次指定的目录不自动写入全局配置。
- 使用本机日期，文件名固定为 `yyyy-mm-dd.md`；用户明确补记历史工作时使用指定日期。草稿中展示并固定本次目标日期，跨午夜确认时仍保存到已展示的文件。
- 不同项目的同日记录放在同一文件中，每项注明项目。工作记录放在技能安装目录之外，采用 UTF-8。
- 整理草稿时读取已有目标文件；目录或文件不存在时，等用户确认后再创建。新需求追加到文件末尾，修订已有需求时更新原条目，保留其他内容。

## 3. 需求拆分与工时

- 每个条目对应一个可独立说明目标和结果的需求，以具体动作和对象命名，例如“修复登录表单重复提交”。不按对话轮次、文件数量或工具调用次数拆分。
- 同一需求中的排查、实现、验证和返工合并整理；复杂需求在条目内部归纳主要工作，多个独立需求分别列出。
- 每项必须有“预估工时”，单位统一为小时。用户提供的工时优先；未提供时，根据已开展工作的范围、复杂度、排查和验证投入估算，表示完成等价工作的有效投入，不把聊天跨度或 Agent 运行时长直接换算为工时。
- 默认以 0.5 小时为粒度，短小工作可用 0.25 小时；用户明确指定的数值原样保留。复杂需求附简短估算依据，不套用固定复杂度公式。
- 工时只覆盖已经开展的工作，未完成部分不提前计入。信息不足以合理估算时说明缺口，请用户补充或指定工时，不随意填值。
- 项目名称优先使用用户指定的名称，其次使用可确定的当前项目名称；无法确定时标注“未指定”，不据此虚构归属。

## 4. 草稿与确认

1. 确定范围、目录和目标日期，读取已有记录，识别本次新增与修订项。
2. 展示目标文件绝对路径，以及每项拟保存的完整内容。新增项使用临时序号，修订项注明原编号。
3. 展示本次新增工时合计；涉及修订时，列明原工时、新工时及变化量，避免把修订后的总工时再次算作新增投入。
4. 等待用户确认。确认前只在当前对话中保留草稿，不写入正式记录；明确说明草稿尚未保存。
5. 用户调整内容、工时或新增需求后，展示受影响条目及更新后的合计；用户仅提出修改时，等待其确认。用户明确说“按这些修改后直接保存”等，执行指定修改并保存，不重复询问。
6. 用户确认当前草稿后执行保存；跨会话若草稿不可见，请用户提供或重新整理，不声称能够恢复未保存草稿。

首次整理仍需展示草稿供用户确认。确认适用于已经展示的内容及用户明确指定的修改，不扩展到未展示的新需求。

## 5. 重复调用与保存

- 保存前对照项目、需求目标和工作范围核对已有记录，不只凭标题判重。已记录且没有新增进展的内容不重复保存或累计工时。
- 调整已有条目的标题、内容、状态或工时，更新原条目。对同一需求补充新增工作时，合并内容并增加新增部分的工时；区分“增加 1 小时”与“总工时改为 1 小时”。
- 无法确定新增工作属于哪个条目，或无法判断用户给出的是新增工时还是修订总工时且会影响结果时，说明歧义并请用户澄清。
- 新需求按当天编号顺延，使用至少三位数字，如 `001`、`002`；已有编号保留，不因修订重排。新增文件只写一次日期主标题。
- 写入前重新读取目标文件，保留其他会话或用户新增的内容。仅编号变化时按最新编号顺延；目标条目已变化且影响已确认内容时，重新展示差异供用户确认，不覆盖冲突版本。
- 追加只写新条目；修订只替换目标条目。使用工具可提供的冲突检测或排他写入能力；无法保证并发写入时避免同时操作，发现冲突则停止写入并重新读取，不声称已消除并发风险。
- 写入后读取核对目标条目、工时及编号。失败或无法确认结果时，明确说明状态；重试前先检查是否已写入，避免重复追加。
- 完成后返回文件链接、保存日期、新增或修订的编号，以及本次新增工时和修订变化量。只有核对写入成功后才报告“已保存”。

## 6. 每日记录格式

每个需求使用二级标题，便于定位与修订。工作内容、完成结果必填；“估算依据”用于复杂需求，“待完成”用于未完成需求，简单条目不强行扩写。编号在正式保存前分配。

```markdown
# 工作总结 · 2026-11-18

## 001 · 修复登录表单重复提交

- 项目：管理后台
- 状态：已完成
- 预估工时：0.5 小时

### 工作内容

- 增加提交期间的按钮禁用处理。
- 验证成功、失败及重复点击场景。

### 完成结果

提交期间不会重复发送请求，失败后可重新提交。

## 002 · 开发设备接入功能

- 项目：设备管理平台
- 状态：进行中
- 预估工时：3 小时
- 估算依据：包含协议梳理、消息解析和本地验证。

### 工作内容

- 梳理消息字段并实现解析。
- 接入设备状态与频谱数据。

### 完成结果

完成解析逻辑与本地样例验证。

### 待完成

- 使用现场设备联调。
```
