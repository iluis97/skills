# work-summary

## 1. 范围与记录依据

- 由用户显式调用。默认整理当前对话中已经实际开展、尚未记录的工作；用户指定需求、日期或提供补充内容时，按指定范围处理。
- 依据可见对话、实际操作结果和用户提供的信息总结，不把讨论、计划或建议写成已完成事项。不自动扫描其他项目或读取其他会话；缺少必要上下文时，请用户补充。
- 未完成的需求可以记录已开展的工作，标明当前状态、已取得的结果及待完成内容。未执行的测试、联调或上线不得写成已经完成。
- 没有可记录内容时说明原因，不编造条目或创建空的每日文件。
- 只维护本地工作记录，不主动调用其他技能或向工时系统、任务平台提交数据。

### 总结内容排除项

- 默认不在草稿或正式记录中输出测试相关内容，包括测试开发、执行、用例数量、通过率、失败详情，以及以“本地验证”等表述替代的测试结果；标题、状态、工作内容、完成结果和估算依据均适用。
- 不输出未执行事项的声明或范围免责说明，如“未进行真实设备端到端联调”“未部署”“未上线”；也不把约定范围之外的后续事项列为待完成。约定范围内确实尚未完成的工作仍应如实标为进行中，并简述具体待办，避免误报完成。
- 上述排除仅影响总结展示，不改变依据实际工作判断状态、起止时间和有效投入的原则。删除相关文案不自动扣减工时；只有用户明确调整工时或原估算有误时才修改数值。用户本次明确要求记录上述内容时，按其指定范围输出。

## 2. 目录与日期

- 目录依次取：用户本次明确指定的目录、环境变量 `WORK_SUMMARY_DIR`、当前用户主目录下的 `work-summary/`。默认目录在 Windows 通常为 `C:\Users\<用户名>\work-summary\`。
- 将目录展开并解析为绝对路径。环境变量需为绝对路径；配置无效或目录不可访问时说明原因，请用户指定可用目录，不静默改存其他位置。本次指定的目录不自动写入全局配置。
- 使用本机日期，文件名固定为 `yyyy-mm-dd.md`；用户明确补记历史工作时使用指定日期。草稿中展示并固定本次目标日期，跨午夜确认时仍保存到已展示的文件。
- 不同项目的同日记录放在同一文件中，每项注明项目。工作记录放在技能安装目录之外，采用 UTF-8。
- 整理草稿时读取目标日期的全部记录；目录或文件不存在时，等用户确认后再创建。默认只核对目标日期，用户指定跨日需求或历史记录时再读取相应日期文件，不自行扫描全部历史。

## 3. 需求归并、时间与工时

- 默认一个完整业务需求对应一个工作项，以具体动作和对象命名。同一目标下的方案、开发、排查、返工、验证和文档整理合并到工作内容中；仅在目标和交付结果相互独立、可以单独验收时拆分。不按接口、模块、渠道、文件数量或对话轮次拆分。
- 合并工作项时核对范围、去掉重叠内容，不重复计算工时。项目名称优先使用用户指定的名称，其次使用可确定的当前项目名称；无法确定时标注“未指定”。

### 3.1 从对话进程确定起止时间

- 先定位需求对应的实际工作过程，再填时间，不默认要求用户提供。优先使用用户明确给出的实际时间、已保存条目的原始时间；其次使用当前对话关联的消息/操作时间戳及工具、构建、测试日志。可使用当前线程明确提供的记录入口，不为找时间扫描其他会话；文件修改时间、Git 提交时间不能单独证明工作起止。
- 开始时间取该需求最早实际开展工作的节点，包括需求分析、方案评估、排查或实现；不是只取首次改代码或首次成功构建。用户提出需求的时间只有在随后已开始工作时才可作为开始依据，无关闲聊、排队等待不算开始。
- 已完成工作的结束时间取约定范围内最后一次实际交付、必要验证或文档更新完成的节点。之后调用总结、等待确认或改总结文案，不延长原需求的结束时间；进行中的工作填写“尚未结束”。不要把某次成功测试当成整个需求的结束，忽略其后的实际改造。
- 按证据精度自动填写：有明确时分就写 `2026-11-18 09:30`；只能确认工作日期就写 `2026-11-18`，不因缺少时分改成“待补充”。若只能定位到近似节点或时段，标注“约”或简短说明范围，不把日志观测边界冒充精确起止时间。
- 当前时间只用于确定记录日期，或确实正在发生的工作节点，不能回填过去工作的起止。确实连工作日期也无法确认、证据冲突影响记录归属时才集中询问；只有这种缺失才使用“待补充”，并在保存前补齐或取得用户保留标记的同意。
- 合并同一需求时保留最早实际开始时间；补充进展延续原工作项。新增实际工作使已完成需求重新进行时，结束时间改为“尚未结束”，再次完成后取新的完成节点。

### 3.2 根据交付证据判断状态

- 按用户约定的交付范围和对话最后进展自动判断，不把状态作为默认追问项。仅完成分析就记录分析结果，不能写成已开发；实施、必要验证和约定文档已完成，且无已知待办时，开发工作可标“已完成”。不能只依据一句“完成了”，忽略后续失败、未实施的修正或用户追加要求。
- 开发范围已完成时写“已完成”或“已完成（开发及文档整理）”；只有原约定范围包含联调或上线且尚未完成时，才保持“进行中”并列出具体待办。不要自行扩展验收范围或附加未执行事项声明。
- 仍有约定范围内的工作未完成时标“进行中”，在“待完成”列明具体事项。明确受阻或暂停时记录事实及恢复条件，不推定成功，也不把正常等待总结确认当作业务工作未完成。
- 文案修订不改变业务状态和起止时间；用户追加开发、验证或修复要求时，根据新增工作重新判断。

### 3.3 估算贴近实际的有效投入

- 每项必须有“预估工时”，单位为小时。用户提供的数值优先，并区分实际投入、预估投入、增加量和累计总量；未提供时，估算完成本次已开展工作的等价有效投入，不冒充精确计时。
- 先列实际工作构成：必要分析设计、有效实现与调试、实际执行的验证、交付文档，再合并相互重叠的投入。根据现有代码复用程度、业务变化、实际排查难点和验证深度估算，不按文件数、接口数、工具调用数或对话轮次数计费。
- 不把聊天跨度、Agent 运行时长或开始结束的时间差直接换算成工时；不把等待回复、空闲、自动构建/容器启动的纯等待重复计入。阅读结果、定位失败和修复的有效工作可以计入；同一用例重复执行、方案改写或返工不等于重新完成一整项需求。
- 默认以 0.5 小时为粒度，小工作可用 0.25 小时；用户指定数值原样保留。复杂工作在草稿中给出简短、可核对的构成和合计，不套固定复杂度公式，不为凑整放大投入。拿不准时给合理的近似值及主要假设，不无依据加缓冲。
- 保存前交叉核对：工时是否与已完成范围、复用/新增比例、实际排查验证相称；是否包含未执行的联调上线；是否重复计算已记录阶段。工时明显超过已知单人工作时段时先复核，跨日或多人投入应说明，不能直接把墙上时间作为估算上限或计费依据。
- 只估算已开展部分，不提前计入待完成事项。对话足够支持工作范围时自行估算；只有缺口会实质改变估算且无法推断时才询问，不把常规判断交回用户。

## 4. 匹配已有记录

先按项目、需求目标、已记录工作范围和结果匹配，再决定操作；标题不同不代表需求不同。同一需求的不同阶段默认归并，本轮草稿内部也要合并重复内容。

| 操作 | 适用情况 | 保存与工时 |
|---|---|---|
| 新增 | 目标独立，已有记录无法覆盖 | 新增工作项，估算本次已开展工作 |
| 补充 | 已有需求有尚未记录的新进展 | 合并到原编号，只增加新增投入 |
| 修订 | 更正标题、内容、状态、时间或工时 | 更新原编号，默认不增加工时；明确修正工时时列出差额 |
| 跳过 | 已有记录覆盖，没有新进展 | 不写入，不累计工时 |

- 同一需求的新增进展不能因换标题或重新整理就另建条目。工时与工作内容一起判重，不能把累计总工时再次算作新增投入。
- 无法确定归属时，展示可能关联的原记录并澄清，不直接新增。区分用户说的“增加 1 小时”与“总工时改为 1 小时”，有歧义且影响结果时询问。
- 重复调用时继续修改当前对话中可见的未保存草稿，不重新生成相同工作项，也不把草稿当成已保存记录。跨会话草稿不可见时请用户提供或重新整理。

## 5. 草稿与确认

1. 确定范围、目录和日期，读取已有记录并完成归属匹配。依据对话进程先确定时间、状态及有效投入，不把能够自行判断的字段留给用户。在开头统一说明“以下为待保存草稿，尚未写入文件”，展示目标日期及文件绝对路径。
2. 先展示变更清单，列明操作、工作项、变化摘要和工时变化；已有记录注明原编号，跳过项说明已由哪条覆盖。只有单项简单新增时可用一句话说明，避免重复表述。
3. 展示每个拟保存工作项的完整内容。新增标题使用 `1 · 需求名称`、`2 · 需求名称`；已有项使用 `补充 003 · 需求名称` 或 `修订 003 · 需求名称`。草稿序号只用于本轮确认，标题不添加“临时项”“待确认项”等流程标签；跳过项不进入待保存正文。
4. 补充和修订必须说明新增工作及改变的字段，时间、状态、工时等字段列出原值和新值；正文较长时概括文字变化，再展示合并后的完整内容。
5. 分别列明新增工作项工时、补充已有项增加的工时、修订工时的增减量，以及本次总工时变化量；不重复累计未变化的已有工时。没有对应操作的合计可省略。
6. 等待用户确认；确认前不写正式记录。只请用户核对完整草稿，不例行要求重新提供可从对话确定的时间、状态或工时；确有关键缺失时一次说明缺口。用户调整后展示受影响内容及更新后的合计，再等待确认。明确说“按这些修改后直接保存”等时，执行指定修改并保存，不重复询问。

首次整理仍需展示草稿供用户确认。确认适用于已经展示的内容及用户明确指定的修改，不扩展到未展示的新需求。

## 6. 保存与核对

- 写入前重新读取目标文件并再次匹配已有需求，保留其他会话或用户新增的内容。若同一需求已被写入，不继续按新条目追加；重新判断是否还有未记录内容。归属、正文或工时变化影响已确认内容时，展示差异并重新确认，不覆盖冲突版本。
- 若仅新增编号变化，按当天已有最大编号顺延，使用至少三位数字，如 `001`、`002`，保存后说明编号对应关系。补充和修订保留原编号，不因修改而重排；新增文件只写一次日期主标题。
- 新增只追加，补充或修订只替换对应条目，其他内容保持不变。使用工具可提供的冲突检测或排他写入能力；无法保证并发写入时避免同时操作，发现冲突则停止写入并重新读取，不声称已消除并发风险。
- 写入后读取核对目标条目、时间、状态、工时及编号。失败或无法确认结果时明确说明状态；重试前先检查是否已写入，避免重复追加。
- 核对成功后报告保存日期和文件链接，分别列出新增、补充、修订的编号及具体变化，说明新增投入、修订工时变化量和总变化量。只有确认写入成功后才报告“已保存”。

## 7. 每日记录格式

每个完整需求使用二级标题。项目、状态、起止时间、预估工时、工作内容和完成结果必填；“估算依据”用于复杂需求；时间仅能近似确定时补一句“时间依据”；“待完成”仅在有剩余工作时填写。草稿使用展示序号，正式编号在保存时分配。日期标题表示记录日期，起止时间表示实际工作时间，可以跨日；日期精度本身是有效时间，不是缺失。

```markdown
# 工作总结 · 2026-11-18

## 001 · 修复登录表单重复提交

- 项目：管理后台
- 状态：已完成
- 开始时间：2026-11-18 09:30
- 结束时间：2026-11-18 10:00
- 预估工时：0.5 小时

### 工作内容

- 增加提交期间的按钮禁用处理。

### 完成结果

提交期间不会重复发送请求，失败后可重新提交。

## 002 · 开发设备接入功能

- 项目：设备管理平台
- 状态：进行中
- 开始时间：2026-11-17
- 结束时间：尚未结束
- 预估工时：3 小时
- 估算依据：包含协议梳理、消息解析及设备状态接入。

### 工作内容

- 梳理消息字段并实现解析。
- 接入设备状态与频谱数据。

### 完成结果

完成消息解析逻辑。

### 待完成

- 完成约定的设备配置功能。
```
